# CODEBUDDY.md
This file provides guidance to CodeBuddy when working with code in this repository.

## Overview

This repository plays video game music log formats: `.vgm`/`.vgz` (Video Game Music), `.s98`, `.dro` (DOSBox RAW OPL), `.gym` (Genecyst), plus `.m3u` playlists. Both front-ends are C++ around the **libvgm** library, which is **vendored as source** at `libs/libvgm/` (upstream https://github.com/ValleyBell/libvgm.git); `libs/inih` and `libs/wingetopt` are vendored the same way. There are **no git submodules** in this repository, so those libraries can be patched in place - their provenance, revisions and licences are listed in `README.md`. The command-line player's version is in `version.h` (`APP_NAME`, `VGMPLAY_VER_STR`, `VGM_VER_STR`); changelog is in `Updates.txt`; `VGMPlay.txt` is its user readme.

The fork's own product is **VGMToybox** (`vgm-toybox`) — the two names are deliberately distinct: everything the plugin builds is "VGMToybox", while the command-line player keeps the upstream "VGMPlay" identity, so the upstream tool and this fork's plugin never get mixed up.

The repository builds two front-ends on top of the same libvgm libraries:

1. **`VGMPlay64.exe` / `vgmplay`** — the classic command-line player (sources in `vgmplayer/`, `PLAYSTATE_*`-driven render loop in `playctrl.cpp`), upstream's, name and all.
2. **`plugin/`** — **VGMToybox**: a JUCE-based GUI plugin (VST3 + standalone, artefacts `VGMToybox.vst3` / `VGMToybox.exe`) with a transport UI, seekable progress bar, per-chip mute buttons and a DAW-style mixer with multi-output routing. See "GUI plugin" in the architecture section.

The authoritative docs are `README.md` (what the product is, attribution, build), `VGMPlay.txt` (keys, supported formats) and `libs/libvgm/Compiling.txt` (build notes for the library).

## Build commands

Nothing to fetch — `libs/libvgm`, `libs/inih` and `libs/wingetopt` are vendored source, part of this repository.

Everything is built in **one CMake tree**: the root project adds the vendored libvgm with `add_subdirectory(libs/libvgm)` (static libraries `vgm-utils`, `vgm-audio`, `vgm-emu`, `vgm-player`), and libvgm fetches + adds zlib itself (`libs/libvgm/cmake/CPM.cmake`, used in `libs/libvgm/utils/CMakeLists.txt`). `find_package(libvgm)` is only a fallback for when the in-tree copy is missing. `.github/workflows/GHA.yml` builds the command-line player only (`-DTOYBOX_BUILD_PLUGIN=OFF`), because the GUI plugin is a Windows target.

```bash
# Windows: MSVC + Ninja + static runtime, output in .\dist (+ clangd database)
.\build.ps1                      # options: -Arch x86 | -Config Debug | -Clean | -NoPlugin | -Proxy <url>
build.bat -Clean                 # wrapper for cmd.exe
build.bat -NoPlugin              # command-line player only (skips the JUCE download/build)

# manual equivalent (any platform/toolchain)
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build              # or: cmake --build build --target VGMPlay64
```

`build.ps1` locates Visual Studio (`vswhere` + `vcvars64.bat`), configures and builds, then copies `VGMPlay*.exe` + `VGMPlay.ini` + the two text docs into `.\dist\` and writes `compile_commands.json` to the repository root (CMake writes it to `build/`; the root copy lets clangd resolve flags for *all* sources: VGMPlay, libvgm and zlib).

The executable is `VGMPlay64.exe` (x64 MSVC), `VGMPlay.exe` (Win32 MSVC) or `vgmplay` (other toolchains) inside the build directory.

Static runtime: the root `CMakeLists.txt` sets `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` (`/MT`) for every target, so the executable does not require the VC++ Redistributable, a UCRT DLL or `zlib1.dll` — only Windows system DLLs (check with `dumpbin /dependents`). Pass `-DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreadedDLL` to use the runtime DLLs instead.

zlib is compiled from source into the package, so no zlib DLL is needed. Related cache variables: `LIBVGM_ZLIB_FROM_SOURCE` (default `ON`; `OFF` uses a system zlib via `find_package(ZLIB)`), `LIBVGM_ZLIB_TAG` (`v1.3.1`), `LIBVGM_ZLIB_MIRRORS` / `LIBVGM_ZLIB_REPOSITORY` (the build probes GitHub first, then the Gitee mirror, because GitHub is not always reachable), `CPM_SOURCE_CACHE` (source cache, e.g. `H:/cmake_cache`).

The **JUCE plugin** is part of the default build (`TOYBOX_BUILD_PLUGIN`, set to `OFF` by `-NoPlugin`). `plugin/CMakeLists.txt` fetches JUCE with CPM (`JUCE_TAG`, default `8.0.9`; `JUCE_MIRRORS` / `JUCE_REPOSITORY` work like the zlib ones) and builds a VST3 + a standalone application. Its `PLUGIN_MANUFACTURER_CODE`/`PLUGIN_CODE` are deliberately left at the original values: they are the identity a host keeps for a plugin, so changing them would make every DAW project that references this build lose it - the renamed parts are the display name, the bundle id, the target and the artefacts. The saved-state XML tag follows the same rule: it is written as `VGMToyboxState` but the old `VGMPlayState` is still accepted when reading. `build.ps1` exports the Windows system proxy (`HTTP(S)_PROXY`) before configuring, because git/CPM do not read the Windows proxy settings — use `-Proxy <url>` to override or `-NoProxy` to disable.

Notable CMake cache variables: root project `MEDIA_CONTROLS` = `OFF`/`WIN_KEYS`/`WIN_SMTC`/`DBUS` (default `WIN_KEYS` on Windows, `DBUS` on Linux when DBus1 is found, otherwise `OFF`); libvgm-side `BUILD_LIBAUDIO`, `BUILD_LIBEMU`, `BUILD_LIBPLAYER`, `BUILD_TESTS`, `BUILD_PLAYER`, `BUILD_VGM2WAV`, `LIBRARY_TYPE` (`STATIC` default), `SNDEMU__ALL` plus per-chip `SNDEMU_<CHIP>_*` and `AUDIODRV_*` switches. Set `SNDEMU__ALL=OFF` (then enable individual `SNDEMU_<CHIP>_ALL` or `SNDEMU_<CHIP>_<CORE>` options) to compile only selected sound cores.

The root `CMakeLists.txt` pre-sets the in-tree libvgm defaults (overridable): static libraries, `BUILD_TESTS`/`BUILD_PLAYER`/`BUILD_VGM2WAV` off, and on Windows `UTIL_CHARCNV_WINAPI=ON` + `UTIL_CHARCNV_ICONV=OFF` (the libiconv bundled in `libs/libvgm/libs/iconv` is a DLL import library and would add a runtime dependency).

## Running

```bash
dist/VGMPlay64.exe song.vgm [song2.vgz ...]     # Windows (copied there by build.ps1)
build/VGMPlay64.exe song.vgm                    # straight from the build tree
build/vgmplay song.vgm                          # Linux/macOS
```

With no file argument the player prompts for a file name. Command-line options (see `main.cpp`, `OPT_LIST_ARR`): `-h/--help`, `-v/--version`, `-L/--lib-info` (supported formats + sound cores), `-w/--dump-wav`, `-W/--dump-path <path>`, `-d/--output-device <id>`, `-c/--config section.key=Data`, `-C/--cfg-file <path>`.

Runtime keys (from `VGMPlay.txt`): Space/P pause, ESC/Q quit, Left/Right seek 5 s (Ctrl = 60 s), 0–9 jump to 0–90 %, PgUp/B previous, PgDn/N next, R restart, F fade out, Up/Down volume ±0.2 dB (Ctrl ±3 dB), `[`/`]` speed ±1/16, `{`/`}` halve/double speed, Ctrl+X quit after song, Ctrl+P pause after song. All keys work during silent WAV logging too.

## Tests and validation

There is no automated test suite and no linter setup in this repository. CI (`.github/workflows/GHA.yml`) only builds the CMake flow above on Windows (MSVC Win32, MSYS2/MinGW), macOS and Ubuntu, in Release and Debug.

libvgm ships manual test programs behind `-DBUILD_TESTS=ON` (`audiotest`, `emutest`, `audemutest`, `vgmtest`). The closest thing to a smoke test is the VGM renderer test, which takes a **gz-compressed** VGM only (it also exercises the in-tree zlib):

```bash
# in the main build tree (the root CMakeLists disables BUILD_TESTS by default)
cmake -S . -B build -DBUILD_TESTS=ON && cmake --build build --target vgmtest
build/vgmtest song.vgz
```

For end-to-end verification, play a file (or dump audio with `-w`) and compare while listening; WAV dumps written by the app use the same render path as live output, so they are the practical regression artifact.

The plugin's playback engine can be tested without a DAW: `plugin/Tests/PlaybackEngineTest.cpp` renders a file offline with exactly the same `PlaybackEngine` class that the VST3/standalone plugin uses. It renders the plain player and the per-channel mixer, writes the plain render to a WAV and checks the mixer criteria (one track per channel, the unity-gain sum equals the plain mix, the tracks stay in sync through seek/loop/end, mute/solo/pan/gain change the mix as expected). Trap for new checks: libvgm does not reset the oscillators on a seek, so two renders that were both started by a seek are never sample-identical (~-30 dB apart, plain player mode included) - compare levels, or render both sides from the same kind of start. It is not part of the default build and has to be built explicitly:

```bash
cmake --build build --target vgm_mixer_test
build/plugin/vgm_mixer_test song.vgz 5         # renders up to 5 s, writes song.rendered.wav
```

It prints the tags, the chips, the track list, the final position and the peak/RMS of the rendered audio; exit code 2 means the output was silent, exit code 3 means an acceptance check failed.

The **core** has its own test that links no libvgm at all: `plugin/Tests/PlaybackCoreTest.cpp` drives `PlaybackEngine` through `Source/backends/fake/FakeBackend.cpp` (three sine tones of amplitude 0.25 - an rms of 0.176777 is one tone, 0.306186 is all three) and checks the mixer against those analytically known levels plus the two volume stages, seek/end, the plain player and the **output routing** (a track on `Out 3/4` leaves the master mix and appears there alone, all buses together still equal the untouched mix, the master mix follows the master's target bus, a muted master is silent while a direct out plays on, a track aimed at an unconnected bus drops out). Because that target links `playback/`, `fake/` and JUCE but **no** format engine, a core that still depended on libvgm would not link - that is the mechanical proof of the decoupling, and `build.ps1` backs it up by failing when a file outside `plugin/Source/backends/` includes a format engine header:

```bash
cmake --build build --target vgm_core_test
build/plugin/vgm_core_test
```

Linux build dependencies: `libinih-dev` (otherwise the vendored `libs/inih` is used), `zlib1g-dev`, and for the audio drivers `libasound2-dev` / `libpulse-dev` / `libao-dev`; `libdbus-1-dev` for MPRIS media controls. MSVC needs no extra packages (`libs/wingetopt` supplies `getopt_long` on MSVC; MinGW/Linux use the system implementation).

## Architecture

### Two layers, built in a single CMake tree

The repository is not one program but a library + application pair:

1. **`libs/libvgm/`** (vendored upstream source) — four libraries: `vgm-utils` (data loaders with zlib/`.vgz` support, OS thread/mutex abstraction, charset conversion), `vgm-audio` (audio output drivers + `AudioStream` abstraction), `vgm-emu` (sound chip emulation cores + resampling), `vgm-player` (format playback engines). It also still ships a CMake package config (`libvgm::` namespace) and pkg-config files for out-of-tree consumers.
2. **`vgmplayer/`** — the VGMPlay CLI application (`main.cpp`, `playctrl.cpp`, `playcfg.cpp`, `config.cpp`, `mediainfo.cpp`, `m3uargparse.cpp`, `utils.cpp`, `mediactrl*.cpp`), its `VGMPlay.ini` template and its two text documents. Moved out of the repository root so that the two front-ends sit beside each other; the target, name and install rules are unchanged. The root `CMakeLists.txt` only assembles the project (`add_subdirectory(vgmplayer)`, `add_subdirectory(plugin)`) and owns the libvgm setup the two share.

The root project builds libvgm in-tree: `add_subdirectory(libvgm)` creates the four static targets (`vgm-utils`, `vgm-audio`, `vgm-emu`, `vgm-player`) in the same build tree and links them directly, so one configure + build produces the executable. Two constraints inside `libs/libvgm/` exist because of this and must be kept in mind:

- `libs/libvgm/utils/CMakeLists.txt` fetches zlib with CPM and adds it via `add_subdirectory`, then links it as `$<BUILD_INTERFACE:$<TARGET_FILE:zlibstatic>> $<INSTALL_INTERFACE:ZLIB::ZLIB>`. Referring to the zlib target by name would make libvgm's `export()`/`install(EXPORT)` rules fail ("target … is not in any export set"), because the zlib target is not part of libvgm's export set; the same reason applies to the `$<BUILD_INTERFACE:…>` wrapping of zlib's include directories. Only zlib symbols may be taken from that target — do not "simplify" this back to `find_package(ZLIB)`.
- libvgm (and `libs/inih`, `libs/wingetopt`) is vendored source, so a change to it is an ordinary commit in this repository - that is how the zlib/CPM patch is stored, and why raising the upstream revision is a plain merge of the upstream files rather than a submodule bump. `README.md` records where each library came from, at which revision, and under which licence. The MSVC builds of the whole tree must share one runtime: the root sets `CMAKE_MSVC_RUNTIME_LIBRARY=/MT`, which the libvgm and zlib sub-projects inherit.

### Root application data flow

`main.cpp` is startup only: it initializes search paths, loads the INI, merges command-line overrides, parses file/playlist arguments, then calls `PlayerMain()` (implemented in `playctrl.cpp`).

**Configuration**: `Configuration` (`config.hpp/cpp`) is a generic `map<section, CfgSection>` where each section keeps unordered entries plus an *ordered* list used for channel `Mute*`/`Pan*` keys where order matters. Two sources are built as `Configuration` objects and merged with `operator+=`; command line wins over INI (`playerCfg += argCfg`). `playcfg.cpp` then converts the merged config into typed structures: `GeneralOptions` (sample rate/bits, volume, loops, fade/pause times, resampler mode, WAV logging mode and path, log levels, audio driver/device selection, UI options) and `ChipOptions[0x300]` (per-chip core choice, per-channel mute and pan, extra options). The `CFG_CHIP_LIST` table maps libvgm `DEV_ID` values to INI section names (`[YM2612]`, `[NES APU]`, ...); `[Chip]` applies to every instance of that chip, while `[Chip-0]`/`[Chip-1]` target a single instance (stored in slots `0x100 + devID*2 + inst`). `ApplyCfg_General`/`ApplyCfg_Chip` push the result into the `PlayerA` facade via `SetConfiguration`/`SetDeviceOptions`.

**INI search order** (`InitAppSearchPaths` in `main.cpp`): Unix install datadir, executable directory, the directory the app was invoked from, per-user config dir (`%USERPROFILE%/.vgmplay/` on Windows, `$XDG_CONFIG_HOME|~/.config` + `/vgmplay/` elsewhere), then `./`. First `VGMPlay.ini`/`vgmplay.ini` found is loaded; `-C` overrides the search entirely. `VGMPlay.ini` in `vgmplayer/` is the default template and is installed next to the binary.

**Song list**: `m3uargparse.cpp` expands command-line arguments into `songList` (one entry per playable file, with optional playlist back-reference) and `plList` (playlist files); `.m3u` files are recursively read and must only reference supported formats.

### Playback runtime (`playctrl.cpp`, `mediainfo.cpp`)

`PlayerMain()` is the program's main loop and the densest file in the repo. Sequence:

1. `InitAudioSystem()` — `Audio_Init()`, enumerate drivers, choose an *output* driver (`adOut`, default: first driver on Windows / last on Linux) and a *disk writer* (`adLog`, WaveWriter) according to `General.pbMode` (play / log / play+log). `InitAudioDriver()` adds driver-specific setup (e.g. DSound window handle, Pulse stream name).
2. `StartAudioDevice()` — pushes sample rate/channels/bits and buffer settings into the driver, sizes the local render buffer, and calls `PlayerA::SetOutputSettings(sampleRate, channels, bits, smplAlloc)`.
3. Register the four playback engines on the single `PlayerA` instance: `new VGMPlayer`, `S98Player`, `DROPlayer`, `GYMPlayer` (kept alive for the whole run so per-chip options survive track changes). Event/file-request/log callbacks are installed, then configuration is applied.
4. Per song: `OpenFile()` (UTF-8 path → `FileLoader`/`FileLoader_InitW` via `CPCONV`) → `PlayerA::LoadFile(DATA_LOADER*)` → `PreparePlayback()` (loop count, fade/end-silence samples) → `Start()` → `EnumerateChips()` (must run *after* `Start()` to learn which cores were actually created) → `Render(0, NULL)` once (consumes the init block, gives the real start offset) → print song info → optional disk writer → `PlayFile()`.
5. `PlayFile()` loops until `PLAYSTATE_END`, refreshing the status line, reading the keyboard, and draining `MediaInfo::_evtQueue` through `HandleCtrlEvent()`. Audio is produced by the audio driver calling `FillBuffer()`, which locks `renderMtx` and calls `PlayerA::Render()`; when no output driver is available, `manualRenderLoop` makes the main loop render into `audioBuf` itself.

**Threading model**: the audio driver's callback thread renders; the main thread handles display/keys/events; `renderMtx` (an `OS_MUTEX`) guards every player mutation (volume, seek, fade, reset, pause). `MediaInfo::_evtQueue` is the thread-safe-ish hand-off used by media controls to inject commands (see `mediactrl_*.cpp` calling `Event()` from other threads or signals).

**`MediaInfo`** (`mediainfo.hpp/cpp`) is the shared state hub: the `PlayerA` instance, `GeneralOptions`/`ChipOptions`, play-state bit flags, current song/playlist paths, song tags, used-chip list, code-page converters, signal callbacks (`MI_SIG_*`, notified via `Signal()`) and the event queue (`MI_EVT_*` with parameters like `MIE_CTRL_*`, `MIE_PS_*`, `MIE_PL_*`). Media controls subscribe to signals (metadata/play-state/position) and push events back; `playctrl.cpp` translates both directions for keyboard and MPRIS/SMTC.

**Media controls** (`mediactrl.hpp` + `GetMediaControl(sig)`): `MediaControl` is a small base class; implementations are `mediactrl_WinKeys.cpp` (Windows `RegisterHotKey`), `mediactrl_WinSMTC.cpp` (Windows Runtime `SystemMediaTransportControls`, requires `ENABLE_WINRT`), and `mediactrl_dbus.cpp` (Linux MPRIS over DBus). Selected at build time through the `MEDIA_CONTROLS` variable (defines `MEDIACTRL_WINKEYS`/`MEDIACTRL_SMTC`/`MEDIACTRL_DBUS`) and at runtime by `General.MediaKeys` (`Default`/`None`/`WinKeys`/`SMTC`/`DBus`).

**Windows specifics**: the entry point is `wmain` (`USE_WMAIN`); wide `argv` is converted to UTF-8 up front, and all user-facing strings are UTF-8 (`u8printf` in `utils.cpp`). `utils.hpp` `#undef`s `GetFileTitle`/`GetFileExtension` to avoid clashing with the Windows API macros.

### Inside libvgm (read these before touching the library)

- `libs/libvgm/utils/` — `DataLoader.h` (abstract data source), `FileLoader.c`/`MemoryLoader.c` (zlib decompression for `.vgz`), `OSMutex`/`OSThread`/`OSSignal` (POSIX/Win split), `StrUtils.h` (codepage conversion, implemented via iconv or WinAPI).
- `libs/libvgm/audio/` — `AudioStream.h` (`AUDDRV_INFO`, `AudioDrv_*`, `Audio_*`, `AERR_*`) with one file per driver under `audio/drivers/` (WaveWriter is the file logger), plus data forwarding so output and logging drivers can be chained (`AudioDrv_DataForward_Add`, used for WAV dumping).
- `libs/libvgm/emu/` — `SoundEmu.h` (`SndEmu_GetDevDecl`, `SndEmu_Start2`, `SndEmu_Stop`, ...), `EmuStructs.h` (`DEV_DECL`, `DEV_INFO`, `RWF_*` flags), `SoundDevs.h` (all `DEVID_*` IDs), `Resampler.c` (`Resmpl_*`, modes `RSMODE_*`, output format is `WAVE_32BS`). Chip cores are a flat `emu/cores/` directory: an interface/register file per chip (`*intf.c`) plus one or more emulation implementations (e.g. Nuked-OPN2, MAME, EMU cores). Adding a core means adding files there and wiring `SNDEMU_*` options in `emu/CMakeLists.txt`.
- `libs/libvgm/player/` — `PlayerBase` (`playerbase.hpp`) is the abstract engine (`LoadFile`/`Start`/`Stop`/`Seek`/`Render`, `PLREVT_*` event and `PLRLOG_*` log levels, `PLR_SONG_INFO`/`PLR_DEV_INFO`/`PLR_DEV_OPTS` structures). `PlayerA` (`playera.hpp`) is the front-end facade that owns registered engines, sets output settings/volume/fade/loop/speed, and dispatches rendering to whichever engine loaded the file. Format engines: `VGMPlayer`, `S98Player`, `DROPlayer`, `GYMPlayer`; `playerbase.cpp` provides format detection (`PlayerCanLoadFile`). Note this is a C++ class API — there is no flat C `PLR_*` functional API in this version, and `stdtype.h`/`common_def.h` live in the libvgm root.

### GUI plugin (`plugin/`, JUCE)

`plugin/` is a JUCE plugin target (`juce_add_plugin`, VST3 + Standalone) that links the same in-tree libvgm libraries as the command-line player — `vgm-player`, `vgm-emu`, `vgm-utils`, but **not** `vgm-audio`, because a plugin must never open an audio device itself. JUCE is fetched with CPM (`plugin/CMakeLists.txt`), the plugin is enabled by the root option `TOYBOX_BUILD_PLUGIN`.

Files and responsibilities:

- `Source/playback/` — the **format-agnostic core**. `SongBackend.h` is the playback port, the standard every format engine is plugged into: `ISongBackend` (recognise + open), `ISongInstance` (metadata, tracks, capabilities, players), `ITrackPlayer` (one isolated renderable instance), the boundary types (`SongMemory`, `SongInfo`, `ChipInfo`, `TrackInfo`, `BackendCapabilities`) and `IsolationMode`. `BackendRegistry.{h,cpp}` picks a backend for a file image and lists the file extensions (compile-time registration - the product is one signed VST3 binary, so nothing is loaded at runtime). `PlaybackEngine.{h,cpp}` is what the UI and the host use, and **nothing under `playback/` may include a format engine's headers** - `build.ps1` scans `plugin/Source` and fails the build when a file outside `backends/` includes one. The design, the ADRs and the rejected alternatives are in `docs/playback-backend-design.md`.
- `Source/playback/PlaybackEngine.{h,cpp}` — the playback engine. Loads the file **once** into a shared `MemoryBlock` (a container like `.vgz` is unpacked by the backend itself, so every player reads the same plain bytes) and drives the backend purely through the port. Plain player mode runs one un-isolated player (the classic behaviour); mixer mode (the default, since the two are sample-identical) runs **one isolated player per track** when the backend reports `IsolationMode::multiInstance` and sums them with per-track gain/pan/mute/solo (`setMixerEnabled()` rebuilds the players at the current position, the track settings survive - the toggle is the CPU-saving opt-out). Isolation is a backend capability: the engine only says "this player outputs track *n*" and which chips are audible, the adapter turns that into libvgm mute options. Two **independent** gain stages sit at the end of `render()` - `setMixerMasterGain()` (the master strip's fader, applied to the finished sum) and `setMasterVolume()` (the transport card's slider, applied last). The master meter measures **between** the two, so the mixer meters keep showing the mixer's own level while the output volume is pulled down, and neither control drives the other. **Output routing** (docs/multitrack-output-design.md): each track carries a destination in its atomic state - the internal master bus (default) or one of the declared buses - so a track either feeds the master sum or goes straight to its own output bus. The master bus keeps its own scratch buffer and its own section (fader, mute, meter, then its target bus, which can never be itself); tracks on real buses bypass that section but still pass the output volume, which is the plugin's own level on every bus. A track whose target bus is not connected is silent - the host says so by handing out no buffer, which `render()` publishes as the connectivity mask the UI reads.
- `Source/backends/` — the **only** place that knows a format engine. `libs/libvgm/` is the adapter for the shipping formats: `LibvgmBackend` (recognises `.vgm/.vgz/.s98/.dro/.gym`), `LibvgmSongInstance` (a *probe* player that enumerates tags/chips/tracks and produces the timeline facts - it has to be **started** before libvgm reports the complete device list and the loop time), `LibvgmTrackPlayer` (one `PlayerA` + `DataLoader` + int32→float conversion; the former `TrackPlayer`), `LibvgmMuteIsolation.h` (`PLR_MUTE_OPTS` bit order, "suspend a device" options, chip-mute options - a suspended device is not emulated at all, which is what makes a dozen isolated players affordable) and `LibvgmVgz` (inflates a `.vgz` up front). `fake/` is a three-tone backend with no format engine behind it, used by the core test.
- Threading contract (unchanged by the decoupling): the audio thread renders under a *try*-lock and outputs silence while a command is in flight, so everything the UI polls is served **lock-free** - the position is an atomic `render()` publishes once per block, the duration/loop point are cached whenever the file, the loop setting or the sample rate changes (`refreshCachedTimes()`), and the tags are only ever touched from the message thread. Any lock a UI poll *would* take is a chance for the try-lock to fail, and a failed try-lock costs a whole silent block (an audible faint tick - the CLI player has no polling and no lock, which is why it stays clean). The port repeats the same contract into the backends: `ITrackPlayer::render()` must not lock, allocate or log.
- `Source/PluginProcessor.{h,cpp}` — `AudioProcessor` with the multi-output bus layout: `Out 1/2` is the main bus (activated) and the remaining `VGMPLAY_OUTPUT_BUSES - 1` buses start **inactive**, so a host only allocates the ones the user enables (the usual multi-output instrument model, ADR-2) and an untouched install behaves exactly as before. The bus factory lives **inside the class** because `BusesProperties` is a protected nested type of `AudioProcessor`; `isBusesLayoutSupported()` accepts any combination where every bus is stereo or off and at least one is on. `processBlock` hands the engine one stereo pair per enabled bus (a disabled bus has no channels, which reads as "not connected"), and the file path plus the transport settings are saved with the host session in `getStateInformation`. The **standalone ignores restored state on purpose** (`wrapperType == wrapperType_Standalone` makes `setStateInformation` return immediately), so double-clicking `VGMPlay.exe` always starts with an empty player; only a plugin inside a host restores its session.
- `Source/PluginEditor.{h,cpp}` — assembles the window: the top row (open button + status line, the status text is the only UI state the editor still owns), the four cards from `Source/ui/` and the drop overlay. The mixer card owns the **whole area between the chips card and the transport card** and grows with the window (its strips stretch, so a maximised window gets long faders; the chips card never eats into that region). The window opens at 820x650, has a minimum size of 660x520 and **no maximum**, and the editor adds a **maximise button** to the standalone window's title bar (hosts manage their own windows, so only the standalone wrapper is touched). It paints the window gradient and - **behind** the cards and the open button - their soft shadows, which has to happen here because JUCE clips every child to its own bounds; `resized()` ends with a `repaint()` so a card that moved, appeared or changed size also repaints the ring around itself. It translates keyboard shortcuts (space = play/stop, or play/pause while the playback start cursor is off; enter = play/pause; home/left/right seek) and file drops into calls on the panels or the engine and runs the 20 Hz refresh timer that calls `refresh()` on every panel. Every user-visible format list comes from `playback::BackendRegistry` - the open button's tooltip, the file dialog's caption and wildcard, the drag & drop filter (`isSupportedFile`), the drop hint and the info card's "load a ... file" line - so adding a backend changes the UI texts without touching them (the registry is filled in the processor's constructor, which is the composition root and runs before the editor is built).
- `Source/ui/` — the GUI module. Every component here lays itself out, paints itself and **pulls** its state from the engine in `refresh()`. The editor stores no card rectangles that `paint()` and `resized()` have to agree on - that parallel state is what used to leave the chips card and its header unpainted after a file was opened from the file chooser (adding/removing child components only repaints the children).
  - `Theme.h` — the whole palette + card/button/slider metrics and the elevation tokens (`vgmplay::ui::theme`); every drawing site uses these, including the two that must match (`theme::sliderThumbRadius` is shared between the slider thumb and the loop marker).
  - `Format.h` — `formatTime()` (`m:ss.cc`), used by the info card and the status line.
  - `Icons.{h,cpp}` — `drawRepeatGlyph()` (loop button + loop point marker).
  - `SoftShadow.h` — `drawSoftShadow()` / `drawCardShadow()`, the blurred drop shadows behind rounded shapes (`juce::DropShadow::drawForPath()`). Trap: JUCE clips a component to its own bounds, so a shadow that reaches outside its shape must be painted by the **parent** - the editor paints the card shadows, `TransportPanel::paintCardContent()` paints the glow of its loop button. The two guards inside `drawSoftShadow()` (skip when the repaint cannot touch the shadow, and when it sits entirely inside the shape) are what keep the 20 Hz refresh cheap - without them every slider tick would re-blur every card.
  - `LightLookAndFeel.{h,cpp}` — the macOS-flavoured light theme (white cards on `#f2f2f7`, hairline borders, `#0a84ff` accent). One instance per editor, never the process-wide default. Trap: `Slider::textBoxBackgroundColourId` must be **opaque** - JUCE's `createSliderTextBox()` copies it into the `TextEditor` that appears while typing and forces alpha to 1, so a transparent background would turn into an opaque black box with dark text in it (the editor's colours are taken from the `TextEditor::` ids, which the LNF sets to the card/text colours). It draws the horizontal sliders (round thumb), the mixer's **vertical faders** (a rounded cap that travels on the track) and the **rotary pan knobs** (white body, accent arc, pointer, centre tick); small buttons (height < 28 px) get a slight corner rounding instead of the regular button radius.
  - `IconButton.{h,cpp}` — the small icon button (play / pause / stop / loop / play-start / mixer glyphs).
  - `CardComponent.{h,cpp}` — base class of every white card: **paints its own background** (fill, hairline border) and calls `paintCardContent()` for content on top (the soft shadow behind it comes from the editor, see `SoftShadow.h`). Trap: the JUCE copy/move macros suppress the implicit default constructor - every subclass needs `ClassName (void) = default;` or an explicit constructor.
  - `MeterScale.h` — the dB scale shared by the meters, their graduations and every gain control: dB maps **linearly** from -60 dB (bottom) to +6 dB (top), so the fader cap lines up with the tick marks and with the level the channel produces (0 dB sits at 60/66 of the travel, the bottom of the travel is inaudible rather than a hard zero). `gainRange()` builds the `NormalisableRange` the sliders use - linear gain values, dB travel.
  - `ChannelStrip.{h,cpp}` — one mixer channel strip in the DAW layout: track name, pan **knob**, a **vertical** level meter (two bars, L/R) with its **dB graduations** (0 dB emphasised) next to a **vertical** gain fader on the same dB scale (it fills whatever height the strip has), and mute (**red** while on) / solo (**amber** while on) buttons that split the strip width; the master strip is the same class with the knob hidden - it keeps the space of the knob and of the solo button, so its fader and graduations line up with the track strips, and its **mute** button is enabled (it silences what the master bus contributes; tracks on real buses keep playing). Every strip ends in an **output selector**: `Master` (the default) or one of the declared buses, with unconnected ones labelled "(not connected)" - the master strip's list has no `Master` entry, since its mix cannot target itself - and the row is greyed out while the mixer is off (values are kept). The meter bars grow along the dB scale and carry a vertical **gradient** anchored to the bar (green -> amber around -6 dB -> red from 0 dB up), so a loud level turns red before it clips. It never reads the engine: `MixerPanel` feeds it through `setValues()` and forwards the user's changes through callbacks. Repaint discipline at 20 Hz: `setValues()` repaints **only the meter rectangle**, and only when the displayed level actually moved (the panel's decay settles exactly at zero, so an idle mixer repaints nothing at all). Repainting the whole strip instead would drag its child controls - and each of them draws a blurred shadow - into every frame, which is what keeps a GPU busy.
  - `MixerPanel.{h,cpp}` — the mixer card: one strip row per chip (group header + `ChannelStrip`s) inside a `Viewport` with both scrollbars, the master strip pinned at the right (aligned with the first strip row and **following the strips' height**, clamped to the card so it can never overflow), and the card header carrying the mixer on/off toggle (accent glow while on) plus two **routing shortcuts**: "send every track to its own bus" (track 1 -> `Out 1/2`, track 2 -> `Out 3/4`, ... - tracks beyond the declared buses stay on the master) and "send every track back to the master bus". They set the engine's **default routing scheme** (`setDefaultRouting()`): it applies to the loaded song immediately *and* is what every newly loaded song starts with, so the choice survives a file change (untouched, it is "everything to the master", the classic behaviour). The two buttons double as a radio pair showing the active scheme, and both are disabled while the mixer is off, since the routing is inactive then. Strips are rebuilt when another song is loaded and laid out so they **stretch with the card height** (never below `ChannelStrip::preferredHeight`, then the card scrolls); every 20 Hz refresh decays the meters (rise instantly, fall at ~0.82 per tick) and reads the lock-free getters.
  - `SongInfoPanel.{h,cpp}` — the info card: title/tags/file name + position.
  - `ChipPanel.{h,cpp}` — the chip mute card: `rebuild()`s the checkbox list from `PlaybackEngine::getChips()`, hides itself while the list is empty and reports its own height (`getPreferredHeight (width)`, which the editor clamps to the remaining space).
  - `TransportPanel.{h,cpp}` — the transport card: play/pause/stop + loop-forever and playback-start toggles, the seek bar with the loop point marker and the draggable **playback start cursor** above it, the loop/fade/volume row. The master volume slider travels on the mixer's dB scale (`MeterScale.h`), so it matches the master strip fader exactly. DAW-flavoured transport: the start cursor is where Stop (and a finished song) returns to, while Pause stays put - space toggles play/stop, enter toggles play/pause. Dragging the cursor also seeks a stationary transport, so the next Play starts right there (while playing, the marker only moves). Seeking works the same way round: while the transport is not running, every position seek (slider release, left/right, home - all through `seekToSeconds()`) carries the cursor along, so position and cursor cannot drift apart; while playing, the cursor stays where it was placed. The button lights follow the same split: Play lights while playing, and the last stop-like action lights Pause or Stop (a finished song counts as stopped) - the engine only knows "playing", so the panel remembers whether Pause or Stop came last. The toggle next to the loop button switches the cursor feature off and leaves a plain player: the marker hides, the drag strip stops taking the mouse, seeks no longer sync the cursor, Stop returns to the beginning of the song and space toggles play/pause instead of play/stop. That toggle is panel state - the engine has no notion of it - and defaults to on. The cursor is dragged through `StartMarkerDragArea`, a transparent strip child above the seek bar (a child paints nothing and only takes the mouse, which also keeps the left-right resize cursor away from the slider); the card draws the marker itself because the hairline reaches past the strip. It is per-song and resets when another file is loaded. It owns every control that writes to the transport API. The loop button and the loop combo box are two views of the same value (`VgmEngine::getLoopCount()`); `refresh()` compares them against the controls themselves (not against a cached value) and repaints them explicitly, because `setToggleState()`/`setSelectedId()` skip their repaint when they think that nothing changed. Trap: a slider's text box gets its colours and its text formatting **baked in when `setTextBoxStyle()` creates the label** (`LookAndFeel_V2::createSliderTextBox`), and at that point the slider has no parent yet, so the lookup falls back to the *default* (dark) `LookAndFeel_V4` - white text on the white card. Therefore `volumeSlider` gets its `Slider::textBox*` colours, its suffix and its `textFromValueFunction` *before* `setTextBoxStyle()`, plus an `updateText()` afterwards.
  - `DropHintOverlay.{h,cpp}` — the "drop a VGM / VGZ file here" dashed overlay. Being a component of its own is what makes the dashed outline appear/disappear with the drag: the editor only flips its visibility, so exactly that area repaints (the overlay does not take mouse clicks, the editor stays the drop target).
- `Tests/PlaybackEngineTest.cpp` — offline renderer and acceptance test for the engine and the mixer (see "Tests and validation").

Threading contract: the audio thread calls `render()`, which uses a **try**-lock on the engine mutex and outputs silence while a file is being loaded (so the GUI never blocks the audio callback for long). The message thread uses a normal lock for loading, seeking, muting and configuration. Never call into libvgm from the message thread without that lock.

Three traps that already caused bugs — keep them in mind when changing the render path:

- `PlayerA::Render(bufSize, data)` takes a **byte** count and **returns the number of bytes written**, not samples (`bytes / (bits/8 * channels)` gives samples). `SetOutputSettings(rate, 2, 32, maxBlockSize)` selects 32-bit integer stereo output; libvgm packs 24-bit internal samples by shifting them left by 8, so the float conversion factor is `1.0f / 2147483648.0f`.
- `PlayerA::SetSampleRate()` **skips the player that is currently playing**, so a song that is already loaded keeps running at the old rate when the output sample rate changes (audible as wrong pitch and playback speed). `VgmEngine::prepare()` therefore re-loads the current file when the rate or the block size changes, and a file must never be loaded before the first `prepare()` call.
- `PlayerA::GetTotalTime()` returns **-1.0** to indicate an infinite runtime as soon as the loop count is 0 and the file has a loop point (`GetTotalPlayTicks(0)` returns `(UINT32)-1` when `GetLoopTicks() > 0`). Using it directly made the duration 0, which pinned the seek bar to 0 and clamped every seek to 0. `VgmEngine::getPlayLengthSeconds()` therefore falls back to a single playthrough (`PLAYTIME_TIME_PBK`), `getPositionSeconds()` reports the position in the same mode (it jumps back to the loop start at every repetition), and `setPositionSeconds()` clamps against that finite length. `VGMPlayer::Seek()` resets the loop counter when seeking backwards, so the reported position stays consistent. `VgmEngine::getLoopPointSeconds()` = single playthrough length − `PlayerA::GetLoopTime()` (which is the *length* of the loop, not its position); the editor draws a small repeat glyph with a hairline at that fraction of the position slider, so the user can see where the song loops.
- libvgm mixes all chips into one stereo buffer (`Resmpl_Execute` *accumulates* into the destination). There is no per-chip output API yet, which is why the plugin currently has a single stereo bus — see the per-chip multi-out plan below.

Roadmap for the DAW multi-out feature: each chip can already be muted/disabled from outside (`SetDeviceMuting` with `PLR_DEV_OPTS.muteOpts.disable` skips the chip's resampler and therefore its emulation), and `GetSongDeviceInfo` lists the chips with their `PLR_DEV_ID`. A real per-chip stem output should be added in libvgm as a small render tap (a per-device output buffer used in the `_devices` loop of the four `*Player::Render` functions, next to the existing `Resmpl_Execute(&clDev->resmpl, smplStep, &data[curSmpl])`), because rendering the song once per chip (N player instances with solo-muting) would cost N times the CPU and memory.

### Conventions

- Style is C++98-era by design (the codebase still contains MSVC6 compatibility paths): use `std::string`/`std::vector`/`std::map`, the `UINT8/UINT16/UINT32/INT32` typedefs from `stdtype.h`, tabs for indentation, and keep new libvgm code C++98/C90-clean (`REALLY_NEED_CXX14` exists as an opt-in). Avoid C++11+ features in libvgm; the root app is also written without them in active code.
- Error convention is `UINT8`/`UINT32` return codes where the high bit (`& 0x80`) means failure and `0x00`/`AERR_OK` means success; libvgm uses `0xF0`-style codes. Log output goes through `PlayerLogCallback` (`playctrl.cpp`) honoring `General.LogLevelFile`/`LogLevelEmu`.
- Code that must run on old MSVC uses `stricmp`/`strnicmp`/`snprintf` shims defined at the top of the affected `.cpp` files — follow the existing `#ifdef _MSC_VER` pattern rather than introducing new portability helpers.
