# NSF 播放排障记录：三处故障与它们共同的根因（2026-11-08）

> **一次会话里解决的三个独立故障**，都在"我们以为的"和"文件实际说的"之间：
>
> | # | 现象 | 根因 | 修法 |
> |---|---|---|---|
> | 1 | Super Mario USA 只有一记 DPCM，三角波直流 | 文件头 `startSong = 16` 指向空壳曲目，音乐在 1–14；我们没有曲目选择 | `SongMemory::songIndex` + `PlaybackEngine::selectSong` + 信息卡下拉框 |
> | 2 | 同上，但"为什么别人能播" | 他们从第 1 首开始；NSFPlay 系都遵守 `startSong` | 默认第一首（两条加载路径都重置） |
> | 3 | Ai Senshi Nicol 全曲静默、`pc=0002`、零写入 | `isBanked()` 只看镜像大小（20 KB），而头部 bank 表非零、`init=$D02B` 只能经 `$D000` 窗口访问 | 按头部 bank 表判定 banked |
>
> 三处的共同点：**判据必须来自文件或被模拟的实现，不能来自"看起来合理"的启发式**（大小、默认值、名字）。
> 下面的章节保留完整过程，第 12–13 节是可复用的方法与规则。

> **结论（2026-11-08 最终）**：这个 NSF 的文件头写 `startSong = 16`，而第 16 曲是一段
> 单发音效（只有一个 DPCM），音乐在第 1–14 曲。FamiStudio / MDPlayer 看着"正常"，是因为它们
> 从第 1 曲开始；NSFPlay 系（含官方二进制）遵守 `startSong`，于是都"只响一下"。
> **不是我们的后端，不是核心差异，也不是 VGM/VGZ 工作的回归。** 我们的缺口是**没有曲目选择**：
> 用户无法切到第 1–14 曲。证据见第十节。
>
> 下面第二至九节是排查过程的原始记录（当时的假设已全部被否定），保留作为"怎么排除"的样本。

## 一、现象

`test_file/nsf/Super Mario Bros. 2 JP [Super Mario USA] (1988-10)(Nintendo EAD)(Nintendo).nsf`

- 能加载、能"播放"，但**三角波恒为直流偏置**，脉冲/噪声无声；
- 开头有一记 DPCM，之后完全静止；
- 同一文件在其他播放器正常。

## 二、范围（谁坏、谁不坏）

| 播放器 | 核心 | 结果 |
|---|---|---|
| FamiStudio | NotSoFatso | 正常 |
| MDPlayer | 自带 NSF 播放器 | 正常 |
| 官方 nsfplay 二进制 | xgm | **同样失败** |
| 本项目 | `libs/nsfplay`（xgm） | 同样失败 |
| tag `0.8.0` 的构建 | xgm | 同样失败 |

`git log` 事实：`NsfPlayer.cpp` 由 `c55475f` 引入后再未被替换；`cpu->Start` 与 `framesPerSecond`
的调用约定只在 `c55475f`/`da7c91c` 出现过；近期的 NSF 提交（`1644e21`、`98a9e29`、`2499626`、
`24fada2`）都只涉及 DPCM 采样扫描/导出与快照波形，**不在播放回路**。

因此：**不是回归**，是核心能力差异。

## 三、文件与驱动的静态事实

```
NESM v1 · 34 首 · start=16 · load=$8000 · init=$8800 · play=$8000 · 24 KB · banks 全 0
```

`init $8800`：

```
TAX                     ; X = A = 曲目号
LDA #$80; STA $4017
LDA $8829,X             ; 该曲的一个打包字节
PHA; LDX #0; TXA; STA $4015; STA $0600,X; INX; BNE      ; 清 $0600..$06FF
PLA; TAX; ROR×3; AND #$1F; TAY
TXA; AND #$07; TAX
LDA $884B,X; STA $0600,Y ; $884B = 01 02 04 08 10 20 40 80（位掩码表）
RTS
```

`play $8000`：

```
LDA #$FF; STA $4017
LDA $0100; CMP #$41; BNE → $8014      ; 读【栈页】当标志
$8014: JSR $8078 / $8138 / $82A2 / $82FD / $8361
```

五个子程序的门槛（全部读 `$0601..$060D`）：

```
$8078: LDA $060D …      $8138: LDA $0602 …      $82A2: LDY $0605 …
$82FD: LDA $0601 …      $8361: LDA $0603 …
```

## 四、动态证据（探针实测）

`NSF_TRACE=1`（探针新增，见 `plugin/Tests/NsfProbe.cpp`）：

```
[apu] #001 $4017 = 80      ← init
[apu] #002 $4015 = 00
[apu] #003 $4017 = 80      ← 预扫描/正式各一次
[apu] #004 $4015 = 00
[ram] $0600..$060F: 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00
[apu] #005 $4017 = FF      ← play 第一句
[apu] #006 $4010 = 0E      ┐
[apu] #007 $4012 = 4F      │ 一记 DPCM
[apu] #008 $4013 = 43      │
[apu] #009 $4015 = 0F      │
[apu] #010 $4015 = 1F      ┘
[apu] #011 $4017 = FF      ← 之后每帧只有这一条
```

逐帧状态（`NSF_SONG=16`，文件默认曲目）：

```
t=0.44s  … $0608=01  $060A=85
t=0.91s  … $0608=01  $060A=69
t=1.37s  … $0608=01  $060A=4D
t=1.83s  … $0608=01  $060A=31
t=2.30s  … $0608=01  $060A=15
t=2.76s  全零（此后不动）
```

`$060A` 每 0.46 s 减少 0x1C ≈ 每秒 61 次 —— 与 NSF 帧率（60.09 Hz）吻合，说明 **play 被调用的
节奏是对的**；驱动按帧递减计时器，计时器归零后**没有取下一个事件**。

用 `NSF_SONG` 遍历 34 个曲目：每个曲目只产生**一个**事件（不同的 `$0608`/`$0609` 组合，
其中 24、28 完全无事件）。这在真正的音乐 rip 里不合理 —— 说明引擎进入了"单次音效"路径后停摆。

## 五、调用协议已排除

`libs/nsfplay/xgm/devices/CPU/nes_cpu.cpp:285` 的 `NES_CPU::Start`：

```cpp
context.A = song; context.X = region; context.Y = extra_init ? 0x80 : 0;
context.P = 0x26;
run_from (init_addr);
```

我们的 `NsfPlayer::resetToStart` 用同一签名调用（`song = startSong - 1`、`region = PAL?1:0`），
`NSF_SONG` 实验也证明曲目号确实到达了驱动的 A 寄存器。

## 六、尚未定位的核心侧差异（"改库"时要查的位置）

按可能性排序：

1. **`$4017` 写入的帧计数器行为** —— 驱动每帧写 `$FF`（bit7=1 → 5-step，bit6=1 → 抑制 IRQ）。
   xgm 的 `nes_apu.cpp` 对 `$4017` 的处理若与硬件在"5-step/4-step 切换时钳制定时器"这一点不同，
   依赖帧定时的驱动会停摆。文件：`libs/nsfplay/xgm/devices/Sound/nes_apu.cpp`（`Write` 中 `$4017` 分支）。
2. **`$4015` 读回值** —— 驱动可能在别处轮询通道状态；`NsfBus` 对 `$4015` 的读必须落到 APU
   （`NsfBus.cpp:208`），若被总线短路成 0，状态机会卡住。
3. **DMC / 帧 IRQ 的启用时序** —— drive 写 `$4010 = 0E`（IRQ 关闭），但 `$4015` 的 DPCM 启停与
   `$4011` 电平可能影响后续分支。
4. **`NSF2` 位域**：`nes_cpu.cpp` 里 `nsf2_bits & 0x20`（extra init / NMI play）等分支，若被误判，
   会改变播放方式。本文件是 NSF v1，理论上全为 0，值得核对解析。

## 七、下一步（一次编译的测量）

在探针里加三项打印，直接判定 1 还是 2：

```
[frame] 每帧 CPU 时钟数（应为 29780 @ NTSC）
[4017 ] 每次写入后的帧计数器状态与下一帧间隔
[4015R] $4015 的读回值与时刻（首次 200 次）
```

- 若每帧时钟数与 29780 有偏差 → 帧时序问题（第 1 项）；
- 若 `$4015` 读回恒为 0 → 总线短路（第 2 项）。

范围：`libs/nsfplay/xgm/devices/{Sound/nes_apu.cpp, CPU/nes_cpu.cpp}`，以及 `NsfBus.cpp` 的读路径。

## 十、结论与证据（更正）

### 决定性证据

用 NotSoFatso 的 `CNSFCore` 直接跑同一文件（harness 在 `build/nsfref`，不入库），按曲目对比：

| 曲目 | 参考实现（NotSoFatso） | 我们的 xgm 核心 |
|---|---|---|
| **16**（文件默认） | `$4017=FF` → `$4010=0E` → `$4012=4F` → `$4013=43` → `$4015=0F` → `$4015=1F`，之后无写入 | **逐条相同** |
| 1 | `$4015=0F` → `$4015=0B` → `$4015=0F` → 整组 `$4000-$400F` 音符写入 | 每 0.5 s 约 443 次写入（音乐） |

两个核心在曲目 16 上输出**完全一致**，所以差异不在模拟实现。

### 34 个曲目的活跃度（我们核心，1 秒内寄存器写入次数）

```
 1–14   395–507   音乐
 15      182      短乐句
 16–23    71      只有每帧一句 $4017，无内容
 24–32  143–276   短音效
 33–34   314      音乐
```

`startSong = 16` 正好落在"空曲目"段。

### 因此

1. 播放"只有一记 DPCM、三角波直流"，是**文件指定曲目本身的内容**，两个核心一致；
2. 我们的真实缺口是**没有曲目选择**：`NsfPlayer` 只用 `file.startSong`（`NsfPlayer.cpp:375`），
   界面上没有切换入口，用户无法听到 1–14；
3. FamiStudio / MDPlayer "正常"，是因为它们默认从第 1 曲开始。

### 建议的修复

在界面上提供**曲目选择**（多曲格式通用：NSF 34 首、其它格式同理），加载后允许切换并重新初始化。
最小实现：后端暴露 `songCount` 与 `setSong(index)`，界面在标题旁放一个曲目控件。
不建议"自动跳过空曲目"——那会掩盖文件本身的信息，也与规格不符。

## 十一、又一个文件：`Ai Senshi Nicol`（FDS）—— bank 判定

现象：所有 56 首都是"一个三角波直流偏置"，无音符、无音频；同一文件在 FamiStudio / MDPlayer 正常。

测量（探针 `[level]` 与 `--check`）：

```
修复前  writes=0     peak=0.1470（≈三角波直流）   FDS 声道峰值 0.0000
修复后  writes=270   peak=0.3530                FDS 声道峰值 0.0976
```

根因：`NsfFile::isBanked()` 原来只判断"镜像大于 32 KB"。这个文件镜像 20 KB，但头部的 bank 表非零
（`01 02 00 00 00 00 03 04`），且 `init = $D02B` 只能通过 `$D000` 窗口映射到 bank 0 才访问得到。
线性映射下该地址落在镜像之外 → 读到 0 → CPU 落进零页（`pc=0002`）、零写入。

修法：与 NSFPlay / NotSoFatso 一致，**头部 bank 表非零即视为 banked**：

```cpp
if (rom.size () > 0x8000) return true;
for (const auto bank : bankSwitch) if (bank != 0) return true;
return false;
```

回归（本地 11 个 NSF 全部复测）：`1983` 2 秒峰值 0.2243 与改动前一致；`Bio Miracle` 0.3993、
`Entry080` 0.4800、`Gimmick!` 0.4050 均未变化；`46/46` 通过。

教训：**"文件小就一定线性"是错的**。bank 表是驱动与数据的约定，与镜像大小无关；判定要跟被模拟的实现。

## 十二、方法论：用探针把"听感"变成数字

这次能收敛，靠的是把每一层都变成可测量的量，而不是继续换假设。工具在 `plugin/Tests/NsfProbe.cpp`：

| 开关 / 选项 | 给出什么 | 能回答的问题 |
|---|---|---|
| `NSF_TRACE=1` | 前 240 次音频寄存器写入（地址+值）、`$0600..$060F` 页随时间的值 | 驱动到底跑没跑？跑到了哪一步？ |
| `NSF_SONG=<n>` | 指定曲目 | 是这首的问题，还是某几首？ |
| `NSF_TRACE` 的 `[frame]` 行 | 两次 `$4017` 之间的 CPU 时钟数 | 帧时序对不对（NTSC 应为 29780） |
| `NSF_TRACE` 的 `[rom]` 行 | 总线在 `$8000/$8800/$9000/$A000/$C000/$E000` 读回的字节 | 镜像映射是否正确 |
| `[level]` 行 | peak / rms | 到底是"没驱动"还是"驱动了但芯片不出声" |
| `<file> --check` | 每声道峰值 + 混合与声道之和的差 | 哪个声道在出声（例如 FDS 是否为 0） |
| `build/nsfref`（仓库外） | NotSoFatso 的同一份寄存器写入序列 | 两个核心在哪一条写入上分岔 |

**判据表**（这次的实测结论，供下次直接对照）：

```
writes ≈ 60/秒 且只有 $4017       → 驱动只走了一次性事件（曲目本身是空壳 / 音效）
writes = 0，pc 在零页            → CPU 没跑起来（地址映射、bank、入口地址）
writes 正常但 peak ≈ 直流  → 芯片没被启用（FDS 的 $4023、扩展片、声道映射）
peak 正常但界面空                → 快照/可视化层，不是播放层
```

## 十三、经验（每条都能落到代码或流程上）

1. **判据来自文件，不来自尺寸或直觉。** `isBanked()` 曾用"镜像 > 32 KB"，而 bank 是驱动与数据的约定；同一错误也可能出现在"声道数""曲目数""行数"上。
2. **"别人能播"要先问"别人播的是第几首、用哪套映射"。** FamiStudio / MDPlayer 正常，仅仅因为它们从第 1 首开始；把它们的行为当成"正确参考"会指向错误的核心比较。
3. **先分辨"没驱动 / 驱动了但不出声 / 出声了但界面空"。** 三种故障的排查路径完全不同，`[level]` 与 `--check` 一行就能分开；这次没有它，我会继续在核心差异上打转。
4. **把"听感"换成数字再动手。** 三角波直流偏置 = peak 恒等于某个常数；一旦能量化，就能对比修改前后（0.147 → 0.353）。
5. **改动前先想"这条规则的依据是什么"。** 我在 OPN 上八次返工、在 NSF 上两次误判，都是同一个毛病：用推理代替读取（读文件头、读被模拟的实现）。
6. **多曲格式必须能选曲。** 默认曲目只是默认值，不是文件的内容；控件只在 `songCount > 1` 时出现，单曲格式零影响。
7. **对照实现要能跑起来。** NotSoFatso 的 harness（`build/nsfref`）最终证明了"两个核心在空壳曲目上逐条一致"，这是停止追核心差异的关键证据。
