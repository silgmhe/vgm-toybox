# ES5503：一个通道开关会改变整颗芯片的音高

> 第四颗采样类芯片，也是唯一一颗**波表**芯片。芯片本身没有返工；返工的是我的一个先入判断。

## 1. 芯片事实

| 项 | 事实 | 来源 |
|---|---|---|
| 声道 | 32 个振荡器 | — |
| 寄存器 | `reg & 0x1F` = 振荡器，`reg & 0xE0` = 页 | `es5503_w` |
| 0x00 / 0x20 | 频率低 / 高（16 位） | `es5503.c:544-552` |
| 0x40 | 音量（8 位线性） | L554 |
| 0x60 | 当前数据字节，只读 | L558 |
| 0x80 | 表指针 `data << 8`（每振荡器一个） | L561 |
| 0xA0 | 控制：**bit0 = halt**，下降沿即 key-on | L565-572 |
| 0xC0 | bank 位（bit6）+ 表大小（bit3-5）+ 分辨率（bit0-2） | L574-587 |
| 0xE1 | **启用的振荡器数** `((v>>1)&0x1F)+1`，**并改变全芯片采样率** | L597-605 |
| 芯片采样率 | `(clock / 8) / (enabled + 2)` | L189 |
| 每芯片样本读多少字节 | `freq / 2^(9 + resolution - size)` | L287 |
| 数据格式 | **8 位无符号，0x80 中点**（`(data-0x80)*vol`） | L310 |
| 采样结束 | **0x00 即 halt**，任何模式 | L301 |
| RAM 块类型 | `0xE1`（RAM 块：32 位地址，不是 ROM 的 size/offset） | `_VGM_RAM_CHIPS` |
| VGM 命令 | `0xD5`（port + 偏移 + 数据） | `vgmplayer_cmdhandler` |

**实测三首曲子**：时钟 7159090（头部 0xCC），RAM 块全部写在第一个 `0xD5` 之前
（`01 Title Screen`：首个 `0x67` 在第 224 字节，首个 `0xD5` 在第 5388 字节）。

## 2. 这一颗真正特殊的地方

**速率不是这颗芯片自己的事。** 其它采样芯片的速率要么由采样率寄存器决定（OKI、GA20），
要么由每个声部的步进决定（K007232）。这里，芯片采样率是
`(clock/8)/(enabled+2)`，而 `enabled` 是 **0xE1 写的全局值**：

```
32 个振荡器 → 894886.25 / 34 = 26320.2 Hz
 1 个振荡器 → 894886.25 /  3 = 298295.4 Hz      ← 相差 11 倍
```

于是：

- 同一个 `freq` 在 `enabled` 改变后听起来完全不同
- 导出速率必须是**逐音符、逐时刻**的，而且 0xE1 写入时要**重算所有正在播放的样本**
  （收集器里 `retune` 对每个 keyed 声部调用一次）

这也是为什么 `03 Game Over` 会导出 **481937 Hz** 的表——`enabled = 1` 时的真实结果，
行在某一时刻也这么报。

## 3. 一次判断错误（教训）

调研时我发现 `ChipMemoryAssembly.cpp` 的 `rom()` 用 `romOffset` 拷贝，而 RAM 块的
`romOffset` 是 0，于是判断“四个块全落在 0，ES5503 的 RAM 是坏的”。

**错了。** `forRequirements` 里早就有 `requirements.memoryIsRam` 分支，调用的是 `memory::ram()`，
按 `ramOffset` 装配。我读到的是 ROM 那条路径，没有往上翻一层。

**教训**：调研一个“缺什么”之前，先确认**已有的地基在哪儿**。这一次如果直接动手改 `rom()`，
会把已经很正确的 `ram()` 绕过去，还会顺手改坏其它芯片。

## 4. 实现（四步，与前三颗同形）

| 步 | 改动 | 断言 |
|---|---|---|
| 1 | 解码器 `waveFor()` + `state.wave` | 合成 RAM `80 40 C0 00` → 3 点，0x80=0，结束符不计入 |
| 2 | 解码器 `state.sampleRate = entriesPerSecond()` | 32 振荡器 + freq 0x200 → 26320.2 Hz |
| 3 | `SampleFormat::es5503`（与 `ga20` **共用**解码分支） | — |
| 4 | `Es5503Samples.cpp`：32 声部、0xE1 全局速率、按 `(表指针, 大小)` 去重 | 行与菜单逐项一致 |

## 5. 验收

```
01 Title Screen  4 个表   6682.9 – 361542.7 Hz
02 Danger Nearby 1 个表   37835.3 Hz
03 Game Over     1 个表   481937.0 Hz
```

**验证方式**：把行在 22 个时刻上出现过的 `(点数, 赫兹)` 组合收成一个集合，再检查每个导出项
是否在集合里——3/3 命中。这比“看起来差不多”可靠，也比逐时刻对齐更省事。

```
46/46；其他芯片未变（OKIM 5 / K007232 8 / GA20 7 / RF5C164 6 / QSound 2）
```

## 6. 已知限制

- **RAM 是加载期映像**：三首曲子的表都在播放前上传完，所以静态映像正确。若某首歌边播边写 RAM，
  导出会用旧字节——需要 RF5C164 那套按流序重放。解码器的 `attachMemory` 同样表达不了，
  所以限制在两边一致，不是这一颗新引入的。
- **`es5503` 与 `ga20` 是同一编码**：枚举里保留两个名字，是为了将来若出现分叉（例如
  16 位模式）有地方落，但**解码实现只有一份**。
