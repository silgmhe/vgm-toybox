# K007232：长度在数据里，而速率不是音高

> 第二颗做完的采样芯片，也是第一次**先分析、后动工**的一颗（调研笔记见对话，结论在下面）。
> 相对 OKIM6295 它简单得多：没有采样表，没有压缩格式。但交付后仍有两次返工，两次都不是
> 芯片知识不足，而是**把驱动行为的顺序和单位当成了想当然**。

## 1. 芯片事实

| 项 | 事实 | 来源 |
|---|---|---|
| 声道 | 2，每声道 6 个寄存器（ch0 `0x00..0x05`，ch1 `0x06..0x0B`） | `k007232.c:265` |
| 板级寄存器 | `0x0D` loop、`0x0C` 外部端口、`0x10..0x13` 音量、**`0x14`/`0x15` bank** | `k007232.c:304-322` |
| 启动 | 写起始地址即启播；`0x05`/`0x0B` 是 key（这套驱动不用） | 实测 |
| 地址 | **17 位字节地址**，与 bank 组合：`bank<<17 + (start & 0x1FFFF)` | `k007232.c:224` |
| 输出速率 | 固定 `clock / 128`；计数器每样本走 32，重装 `0x1000 − step` | `k007232.c:157,236` |
| 数据格式 | **7 位无符号，`0x40` = 静音**：`(value & 0x7F) − 0x40` | `k007232.c:232` |
| 采样结束 | **bit7 置位 = 结束符** | `k007232.c:246` |
| VGM | 命令 `0xC5`，寄存器字节 bit7 = 芯片号；ROM 块类型 **`0x94`** | 实测文件 |

**决定性实测**（`02 Title Demo`）：

```
4752 字节里 bit7 置位 = 2 个；5557 字节里 = 1 个     ← 结束符，而非有符号数据的 50%
块首字节 40 2D 33 35 ...                            ← 0x40 = 静音 ✓
0x14 = 1 → 0x20000，0x15 = 3 → 0x60000              ← 正好对上 ROM 块 3 与 4
```

## 2. 三次返工

### 一、起始地址是逐字节写的

第一次导出出现 `...064B3` 与 `...064B6`——同一段数据差 3 字节。因为三个地址字节分开写，
我在每个字节写入时都触发了一次导出。

**改法**：只在**高字节**写入时算一次 key-on。

### 二、音高是错的（交付后用户报告）

**现象**：所有 K007232 行的音高超出键盘范围。

**原因**：`state.hz` 被设成了 `frequencyOf()`，而那个函数算的是**每秒消耗多少字节**——
9943 到 29829 B/s，对应 MIDI **123–135**；键盘只画 **36–83（C2–B5）**。

**这不是键盘的问题，是这一行根本没有描述音高。** 采样芯片知道播放速率，但**音高必须从采样
里量**：`hz = 字节率 ÷ 周期`。OKI、ES5503、RF5C 都这么做，只有这颗漏了。

**改法**：`Pitch.h` 新增共享的 `bestPeriod()`（照 OKI 的实现），`cycleFor()` 按
`(bank, start)` 缓存。改后：

```
改前：hz 9943–29829   → MIDI 123–135（键盘外）
改后：hz   79.9–261.6 → MIDI  39–60 （键盘内）
鼓（无周期）→ hz 0，无音符 —— 这才是鼓该有的答案
```

**顺带**：`bestPeriod` 在 ES5503 / GA20 / OKI / RF5C 里各有一份私有拷贝。这次提取到
`Pitch.h`，新调用方不必成为第五份；四份旧拷贝留在原处（后续可迁）。

### 三、导出的 WAV 打不开（交付后用户报告）

文件本身结构合法，但：

```
data        = 524288 字节 = 131072 点   ← 正好是 128 KB 窗口上限
sampleRate  = 218 Hz                    ← step≈0 的速率
```

**两个数字是同一个缺陷**：导出的是**半个地址**。我当时只在地址**高字节**写入时触发（返工一
的做法），而驱动写三个字节的顺序并不保证；写落在高字节与另两个字节之间时，我拼出一个错误
的地址——它的窗口里 128 KB 都没有结束符，音高也还是上一个音符的。

**改法（两处结构性修正）**：

1. **地址序列由"该声部的下一个其它写入"收尾**，不再假定哪个字节是最后一个——与写入顺序无关。
2. **找不到结束符就不导出。** 真实样本一定以 bit7 字节结束；读到上限说明地址读错或该处是填充。
   写出去的结果正是那个打不开的 524 KB 文件，**不写才是诚实的**。

修正后同一首歌的速率也随之精确：`3_064B3` 从 10528 变成 **9943.1**，与行的 9943.2 一致。

## 3. 实现步骤（可复用于下一颗）

1. 从核心源码读出：数据格式、长度来源、地址组合方式、速率公式——**不要从文档推断**
2. 用文件实测验证格式判断（bit7 字节占比、首字节是否为静音值）
3. 解码器：`setRom` + `wave` + `sampleRate`；**区分"速率"与"音高"**
4. 收集器：走寄存器流，按**下一个其它写入**收尾地址序列
5. **找不到结束符/长度的样本一律不导出**
6. 断言：格式首值、长度、周期→音高、鼓无音高
7. 验收：行 vs 菜单，点数与速率逐项相等

## 4. 两条给下一颗芯片的教训

- **驱动写入的先后顺序不是接口的一部分。** 返工一与返工三都源于"假定某个字节是最后一个"。
  能等到序列结束再判断，就不要挑一个字节当信号。
- **速率 ≠ 音高。** 采样芯片的寄存器给的是播放速率；音高要么从采样里量，要么承认没有音高。
  把速率当音高不会报错，只会让所有音超出乐器范围——一个只有肉眼（或用户）才能发现的错误。
