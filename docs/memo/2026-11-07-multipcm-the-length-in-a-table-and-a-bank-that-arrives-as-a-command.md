# MultiPCM：长度在表里，bank 在命令里

> 第五颗采样类芯片（YMW258 / Sega 315-5560，Model 1/2 板上的那声“咚”）。
> 与前三颗的采样芯片相比，它第一次把**长度写进元数据**，也第一次让 **VGM 命令参与地址计算**。

## 1. 芯片事实

| 项 | 事实 | 来源 |
|---|---|---|
| 声道 | 28 | `DeviceChannels` |
| 寄存器 | 间接寻址：`0x01` 选声部、`0x02` 选寄存器、`0x00` 写数据 | `multipcm_write` |
| 每声部寄存器 | 8 个：0 pan、1 样本号、2/3 音高、4 控制（bit7 = key on）、5 音量、6/7 LFO | `multipcm.c:9-18` |
| 声部选择 | `VALUE_TO_CHANNEL[data & 0x1F]`，**每 8 个值有一个空位** | `multipcm.c:24-30` |
| 芯片速率 | 设备自报 **44444 Hz**；`clock / 224` 是 35714 | `multipcm.c:598` + `smplRate` |
| 声部速率 | `rate × (1024 + pitch) / 1024 × 2^(octave − 1)` | `multipcm.c:671`、`314-324` |
| 数据格式 | 8 位**有符号**（`read_byte << 8` → int16）；bit22 表示 12 位打包 | `multipcm.c:867`、`849-864` |
| 长度 | **元数据表**：ROM 开头每 12 字节一个样本，长度存为**二进制补码取反** | `multipcm.c:281-298` |
| bank | VGM `0xC3` → libvgm 转成寄存器 `0x10`/`0x11`/`0x12` | `Cmd_YMW_Bank` |
| ROM 块类型 | `0x89`，块声明 4 MB | `_VGM_ROM_CHIPS` |
| VGM 命令 | `0xB5 <offset> <data>`（3 字节） | `vgmplayer_cmdhandler` |

**实测**（17 首）：元数据 240 条，全部 **8 位**（12 位 0 个）；`end` 171–65535 样本；
`0xC3` 每首 1 次，`mask=0x03, val=0x20`。

## 2. 三处会让导出“看着对、听着错”的地方

### 一、长度是“取反的计数”

```
end = 0x10000 - (ROM[+5] << 8 | ROM[+6])
```

读成普通计数会把长度变成 `0x10000 - n` —— 对 65535 的样本几乎没差，对 8000 的样本就是
57000 个字节的尾巴。**这一颗没有结束符可依赖**，所以长度错了就是整段错，不会“恰好停在 0x00”。

### 二、bank 走的是命令，不是寄存器

VGM 的 `0xC3` 根本不进芯片：libvgm 的 `Cmd_YMW_Bank` 把它翻译成对 `0x10/0x11/0x12` 的写入，
核心再用这些 bank 把 `start` 的 bit19/20 换成高位（`multipcm.c:733-743`）。

```
实测三首：mask=0x03, val=0x20 → 1 MB 模式 → reg 0x10 = 2
         bank0 = 0x200000, bank1 = 0x280000
         元数据最大 start = 0x1FF24B（bit20 与 bit19 均置位）→ bank1
         最终地址 = (0x1FF24B & 0x7FFFF) | 0x280000 = 0x2FF24B
```

不做这一步，第二个兆字节的样本会播放第一个兆字节的字节——和 K007232 那次一模一样，
只是**这次的 bank 是命令**：读取器要新增 `0xC3` 分支，加载器要复刻 `Cmd_YMW_Bank` 的换算，
否则 IR 里根本没有这条信息，解码器和收集器都无从得知。

### 三、octave 1 才是 1 倍

`multipcm.c:314-324` 移的是 `octave - 1`，而这是个 4 位有符号字段：

```
octave 0 → 0.5×     octave 1 → 1×     octave 8 → 128×     octave 9 → 1/256×
```

旧解码器（没有 ROM 时）按 `2^octave` 映射，**整体高一个八度**。它不报错，只是所有音都不对——
和 K007232 的“速率当音高”是同一类缺陷：**看起来合理的数字，其实是另一个量**。

## 3. 速率取设备值，不取除法

按 `clock / 224` 算是 **35714 Hz**，而设备和渲染用的是 **44444 Hz**（`smplRate`）。
这不是第一次：OKIM 那次是 1.6 倍，这次是 1.24 倍。**凡是芯片内部还除了一次的数，
一律取设备自报值**；除法只做设备缺席时的兜底。

写完之后行与导出立刻一致，正是因为两边用的是同一个数。

## 4. 验收

```
17 首 / 255 个样本，单曲 1–19 个；速率 11111 – 132290 Hz；最长 60388 点
01 Advertise（1:08.59）：每 0.5 秒扫一遍行，17 个导出项的 (点数, 赫兹) 17/17 命中
```

**方法说明**：第一遍只扫到 30 秒，3 个样本“未命中”；把扫描覆盖到全曲（68.6 秒）后 17/17。
在判定“不一致”之前，先确认扫描覆盖了曲子的全部时间——这次的假警报就是这个原因。

**断言**：`testMultiPcmWave` —— 4 个样本的长度来自取反计数、`0x40` = +0.5、octave 1 的速率
等于芯片速率、bank 写 `0x11=1` 后 `0x100200` 落到 `0x80200`。

## 5. 已知限制

- **12 位样本不导出**：`multipcm.c:849-864` 两个样本打包进三字节，17 首素材**无一使用**。
  按“没有把握就不写”的原则，这类声部不显示波形、不导出，而不是写出一段不是它的字节。
- **一段字节、多个速率**：同一 `(base, length)` 在一首曲子里会被不同音高播放，一个 WAV 只能
  声明一个速率，导出取**最后一次** key-on（与前几颗一致）。行在某一时刻可能与之不同。
- **RAM 之外**：这一颗没有 RAM 写入，只有 ROM，所以不存在 RF5C 那种“边播边改”的问题。
