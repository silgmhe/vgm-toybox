# 备忘录：混音推子要不要暴露成宿主参数

- **状态**：待评估（本次只记录，不实施）
- **日期**：2026-10-17
- **来源**：`docs/review/2026-10-17-structure-survey-and-design-questions.md` §4.3、§10 第 5 条
- **一句话**：把每条轨道的 gain / pan / mute / solo 变成 `AudioProcessorParameter`，就能在 DAW 里录自动化、用宿主撤销；但这会把"引擎是真相"翻成"参数是真相"，而宿主参数的 id 在整个实例之内不变，混音器的"第 N 条轨道"却每首歌都换人——两者直接冲突。

---

## 2. 为什么"加几个参数"在这里不是小改动

### 2.1 轨道身份不稳定，而参数 id 必须稳定

宿主给参数分配自动化通道，依据是 **参数 id + 序号**，并且在这个插件实例的整个生命周期里不变。混音器的"第 3 条轨道"却是随歌变化的：

- 一首 MD 曲子可能是 `YM2612 ×2 + PSG ×3`，下一首 FC 曲子是 `2A03 ×5`；
- 同一个文件换后端（或换 loop/混音模式）也可能改变轨道数；
- 轨道名（`Pulse 1`、`Ch 3`、`All`）只在当前歌内有意义。

于是固定槽位 `track.03.gain` 的语义只能是"**当前歌的第 4 条轨道**"。在 DAW 里录下的自动化属于工程时间线，不属于某首歌：换歌之后，原来录给 A 曲第 4 轨的推子会悄悄作用到 B 曲第 4 轨上。**这是语义错误，不是实现细节**，而且用户很难察觉（听起来只是"混音怪怪的"）。

反过来，按芯片/设备命名（`device.0.channel.2.gain`）也不稳定：芯片数量、设备序号、是否可隔离都随歌走。

### 2.2 真相要换边

现在是：**UI → engine**，引擎里的原子量是真相，UI 每帧读回来。
参数化之后是：**宿主 → 参数 → engine**，参数成为真相，UI 必须改成读参数（或订阅参数变化），否则会出现"自动化在响，推子不动"。

这不是"接一个 `SliderAttachment`"就完事：混音条的 `ChannelStrip` 现在只认"值 + 回调"，不知道值从哪来（这是好事），但 `MixerPanel::rebuildStrips()` 每次换歌都重建控件，参数附件的生命周期、以及"重建时不要回调写回宿主"这两件事都要处理。

### 2.3 音频线程的入口

`setTrackGain/Pan/...` 现在不取锁，安全性依赖"只有消息线程调"这个未写下来的契约。而宿主会把参数变化送进 `processBlock`（VST3 走参数变化队列，JUCE 在音频线程上应用，实际上按块对齐——但线程是音频线程这点不变）。一旦参数接到这些 setter：

- 音频线程会读 `tracks.size()`，而加载时消息线程正在换掉这个数组——数据竞争，UB，且只在"播放中换歌 / 恢复工程"这种少见的时序里炸；
- 修法要么把"参数 → 引擎"的发布放到消息线程（引入一拍延迟，破坏采样准确），要么把轨道表改成定长槽位 + 原子指针（等于重做轨道容器）。

这是本备忘录里**最容易被低估**的一块。

### 2.4 状态有两条来源

状态 v2 已经存了混音值（`SessionState.cpp:71-79`）。参数化之后同一个数字有两个出处：

- 宿主撤销一次推子动作，只改参数，不改工程 blob；下次 `getStateInformation` 该写哪个？
- 打开工程时 `setStateInformation` 设置的是参数还是引擎？两边不一致时以谁为准？
- 宿主预设（preset）与工程状态的关系也会跟着变。

必须**先写死一个规则**（建议：参数是真相，blob 只存参数表达不了的东西，如每轨输出总线），否则会出现"撤销后重开工程又变回去"这类灵异问题。

## 3. 四条路

| 方案 | 做法 | 成本 | 风险 | 什么时候值得 |
|---|---|---|---|---|
| **A 不做**（现状） | 混音只在插件窗口里调，进宿主工程状态，不进自动化 | 0 | 不能录自动化、不能被宿主撤销、参数面板空白 | 绝大多数"听 VGM"的场景 |
| **B 只暴露与歌无关的少数全局量** | master gain / master mute、mixer 开关、默认路由这几个**数量固定、语义与歌无关**的值做成参数（6～10 个） | ~250 行 + 测试 | 低（不碰轨道身份，不碰音频线程写轨道） | 有人明确要"在 DAW 里骑 master"或"用宿主撤销调音量" |
| **C 每轨参数（固定槽位池）** | 例：32 槽 × (gain/pan/mute/solo/out) ≈ 160 个参数，语义为"当前歌的第 N 条轨道" | 400～600 行，且要重做轨道容器的线程模型 | 高：§2.1 的语义漂移 + §2.3 的音频线程入口 + §2.4 的双写 | 真的出现"多轨交付、每轨走独立总线"的工作流（那已经不是听 VGM 了） |
| **D 不做参数、只补接口** | 加 MIDI CC / OSC 控制推子（不进宿主参数表） | ~150 行 | 中（又是一条线程入口） | 想要硬件控台/控制器，但不想要自动化 | 

D 只是备选：它解决"手上有控制器"，解决不了"自动化与撤销"。

---

## 4. 建议

**本轮维持 A。** 理由不是"参数没用"，而是：

1. 现在没有任何证据表明目标用户要在 DAW 里给 VGM 混音录自动化；先有场景，再动真相来源。
2. 一旦做，B 是 C 的严格子集，先做 B 能回答 80% 的"我想用宿主控制音量"，而且**不需要**解决 §2.1 的轨道身份问题。
3. C 的真正成本不在参数数量，在 §2.3：那是一次轨道容器的重做，应当和"多轨输出工作流"一起设计，而不是顺手加。

**如果决定做，先做 B，并把 §2.4 的规则写进代码注释**（参数是真相，blob 只存参数表达不了的东西），再评估 C。

## 5. 若做 B：最小设计清单

1. `ToyboxAudioProcessor` 加 `juce::AudioProcessorValueTreeState`（或手工 `AudioProcessorParameter` + 一个 6～10 项的布局函数）。
2. 参数与引擎的对应关系一次写清：

   | 参数 | 范围 | 对应 |
   |---|---|---|
   | `master.gain` | 0～+6 dB，默认 0 | `engine.setMixerMasterGain (Decibels::decibelsToGain (x))` |
   | `master.mute` | bool | `engine.setMasterMuted` |
   | `mixer.enabled` | bool | `engine.setMixerEnabled` |
   | `routing.default` | 枚举 | `engine.setDefaultRouting` |

3. `processBlock` 里读 `getRawParameterValue()` 的原子指针，写进引擎的原子量——**不要**加锁，也不要在音频线程调任何会碰 `tracks` 数组的东西。
4. 参数变更通过 `AudioProcessorValueTreeState::Listener` 或 `ParameterAttachment` 通知 UI；`MixerPanel` 的 master 条改为读参数，轨道条不变。
5. `readState` 之后用 `setValueNotifyingHost` 把参数对齐（宿主需要知道值变了），并明确"以 blob 为准"的恢复语义；`getStateInformation` 继续写参数值，保证宿主预设也能带走。
6. 测试：`vgm_app_test` 断言参数数量与 id 稳定、`setStateInformation` 后参数与引擎一致、离线渲染与实时一致。参数属于处理器，核心测试（不链窗口）覆盖不到，这是可以接受的边界。

**估算**：B ≈ 250 行（布局 40 + 同步 40 + UI 60 + 状态互操作 40 + 测试 70）。

## 6. 验收标准（做 B 时）

- [ ] 参数 id 与序号在整个实例生命周期内不变；换歌不改变参数值（它们是全局量）。
- [ ] 宿主撤销/重做一次推子动作，引擎与窗口同步，且不产生重复的撤销步。
- [ ] 打开工程后参数、引擎、UI 三者一致；blob 与参数不打架（规则见 §5.5）。
- [ ] 自动化在 `processBlock` 里生效，且加载/换歌期间无数据竞争（用 sanitizer 或至少 ASIO/实时下反复换歌验证）。
- [ ] 离线渲染（`vgm_mixer_test` 那条路径）结果与实时一致。

---

## 7. 什么时候重开这份备忘录

出现下面任一条，再回来评估（不要因为"别人家插件都有参数"就做）：

1. 有用户明确提出在 DAW 里**录推子自动化**（把场景写下来：什么曲子、多少轨、要自动化什么）。
2. 需要**宿主撤销**混音动作（现在是改了就改了）。
3. 需要把混音结果作为**插件预设**分发（预设目前只能靠工程状态带走）。
4. 出现**控制器映射**需求（MIDI CC / 硬件推子）——那种情况 D 可能比 B 更合适。
5. 轨道数不再随歌变化（例如将来真的有了"固定 16 轨的合成器工作流"），§2.1 的障碍消失，C 的成本会大幅下降。
