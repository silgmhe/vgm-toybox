# DAC 没有样本：YM2612 第六通道进可视化与导出（2026-11-09）

**起点**：MD 游戏的 DAC 行没有波形、导出里也没有它。原以为是“再补一颗采样芯片”，调研后发现这颗
芯片的模型和别人不一样。

## 一、它不是“寄存器指一段 ROM”

其他采样芯片：`start/end` 或 `address/length` 指 ROM，样本有身份。YM2612 的第六通道：驱动一个字节
一个字节写 `0x2A`，没有地址、没有长度、没有循环位。VGM 只记录这些字节的时间，以及（当字节来自
PCM 块时）`0x80-0x8F` 的“取下一个字节”和 `0xE0` 的“把读指针挪到偏移”。

## 二、实测把两个假设打掉了

`02 Green Hill Zone.vgz`，52.9 s，YM2612 @ 7 670 453 Hz：

| 项 | 实测 |
|---|---|
| PCM 块 | 13 132 字节（type `0x00`） |
| DAC 写入 | 447 541 次，覆盖全曲 |
| 写入间隔 | 1–6 tick 抖动，**均值 3.2 → 13 799 Hz** |
| `0xE0` | 228 次，指向 5 个偏移 |
| 静音间隙 | 全曲没有 ≥10 ms 的静音段 |
| 银行里的静音 | ≥32 字节静音只分出 3 段；≥64 字节只剩 1 段 |

两个被打掉的假设：

1. **“整曲时长 / 字节数 = 采样率”**。得 8.5 kHz，但那是把 21 s 的停顿算进流里；写入间隔才是速率。
2. **“按静音切鼓”**。银行里没有边界，切出来是一整段 1.55 s 的循环。

## 三、决定

- **导出单位 = PCM 银行**：一份文件，`ym2612dac_<start>_<len>`，`pcm8Unsigned`（0x80 为中心），
  速率取写入间隔均值。素材可复用；演奏（52 s 的流）是二手结果，不做。
- **没有块的文件**退回按 30 ms 停段：每段内均值定速率、内容 hash 去重。这条路径没有真实文件验证，
  写进文档时注明。
- **可视化 = 最近 4 096 字节的窗口**，速率同一条规则；`0x80` 进窗口（它是击打之间的静音）。
- 多块拼接成一份；4 MB 上限；现有“单个采样最长 5 s”仍然在写入时生效。

## 四、验证

- `testYm2612DacWindow`：64 字节 / 5 tick → 窗口 64 点、首点 0、速率 8 820 Hz、`0x80` 未被吞掉；
  5 000 字节后窗口为 4 096。
- `pcm-ym2612-dac.txt`：`samples 1` + `ym2612dac_000000_0334C`。
- 键盘页截图：DAC 行画出波形（同日手工确认）。

## 五、教训

1. **“再补一颗芯片”之前先问它的数据模型**：这颗没有样本身份，硬套 `start/end` 会导出猜测。
2. **速率不能从总时长推**：停顿不是信号。
3. **可视化与导出共用一个窗口/一条速率规则**：两边算得不一样，用户会先看见“画的和导出的不是一回事”。

## 六、第一版之后的修正：击打，与局部速率

第一版导出的是**整块银行**、速率取整条流的均值（13 799 Hz）。你听完说“偏慢”，但测量支持相反的
方向：流里**鼓身**的写入间隔是 5–6 tick（≈8 kHz），1–2 tick 的那些是**静音**字节——驱动写静音比写
鼓快，整条流的均值因此被拉高。用 13.8 kHz 播一段 8 kHz 的鼓，听起来是**快** 1.7 倍。这一版因此改成：

- **单位 = 击打**：一段非静音字节，前后由 ≥2 ms 的静音分开。阈值是量出来的：1 ms 会把衰减切成碎片
  （916 段 / 18 种），2 ms 得到 428 段 / 11 种，8 ms 则把相邻鼓并成 142 段 / 6 种。
- **速率 = 段内均值**（>64 tick 的停顿不计入），不再用整条流。
- 内容相同的击打只留一份（同一记鼓被重放 95 次）。

实测：447 541 字节 → 428 段 → **11 个不同录音**，最长 3 304 字节，速率 6.9–20 kHz，多数 **7.9 kHz**：
`ym2612dac_00_0046F` 到 `ym2612dac_10_0003F`。

可视化同步改成**最近 256 个间隔**的滑动均值：整条流的均值会让行按 13.8 kHz 滚动，把正在画的鼓拖着走。

## 七、切分撤销之后：一个文件，和一个校准过的速率

切分两版都被否了（碎片 3–165 ms，不像鼓），于是回到“整块银行一个文件”。速率试了三档：整条流均值
13 799 Hz（初版）、响亮字节中位数 22 050 Hz、再乘校准 1.637 → **36 096 Hz**。

1.637 来自用户自己的测量：曲中的军鼓与导出 PCM 里的同一记军鼓对齐，文件长 1.637 倍。这不是推导，
是**校准**——文件的等待量化到整 tick，鼓身落在刻度之间。常量只写一处（`kDacRateCalibration`），
换歌只需要改一个数。

## 八、1.637 被删掉：单位是“驱动 seek 到的区域”

用户拿另外三首（Marble / Spring Yard / Labyrinth）试，速率仍然不对——1.637 是为一首歌的一记军鼓
校准出来的，没有普适性。四首一起量之后，结构露出来了：**银行不是一段样本，而是一张表**。驱动用
`0xE0` 把读指针挪到某个偏移，这些去重偏移就是它的采样表；每个区域写字节的速率固定，同一区域 96 次
访问的差异不超过 0.02 tick。

| 曲子 | 区域数 | 各区域实测 |
|---|---|---|
| 02 Green Hill | 5 | 8.0 / 8.0 / 23.2 / 23.2 / 8.1 kHz |
| 03 Marble | 4 | 23.2 / 8.0 / 7.9 / 23.0 kHz |
| 04 Spring Yard | 4 | 22.9 / 22.8 / 7.9 / 7.9 kHz |
| 05 Labyrinth | 3 | 16.0 / 12.1 / 7.9 kHz |

于是：单位 = 区域（起点取 seek，长度到下一个起点），速率 = 区域内的**均值**（间隔是抖动的，中位数会把
5.5 tick 量化成 8 820），常量 1.637 删除，IR 增加 `dacSeeks`（`0xE0` 的偏移与时间）让收集器看得见
驱动的指针。没有 seek 的文件退回整块银行 / 整条流，一个速率。

仍有的边界：可视化的行用的是最近 256 个间隔的滑动均值（实时指示），与文件里区域的那个数回答的是
不同问题（“此刻多快” vs “这个文件该按多少放”）。
