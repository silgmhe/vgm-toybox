# K005289：四位深的 PROM，装在一个 RAM 块里

> 第七颗、也是**第二颗有 ROM 的波表芯片**（Konami K005289，`k005289.c`）。
> 交付后一次通过，没有返工。真正需要判断的只有三件事。

## 1. 芯片事实

| 项 | 事实 | 出处 |
|---|---|---|
| 声道 | 2 | `k005289.c:184` |
| 波形 | `prom[ch * 0x100 + waveform * 0x20 + step]`，共 2×8×32 字节 | `k005289.c:59`、`195-197` |
| 深度 | **四位**，播放前 `- 8` → -8..+7 | `k005289.c:198` |
| 表选择 | 控制寄存器 bits 5-7（音量在低四位） | `k005289.c:218` |
| 音高 | `clock / (32 * (freq + 1))`，`freq = 0xFFF - value` | `k005289.c:224`、`190` |
| 输出速率 | `info->rate = info->clock`（不是除法） | `k005289.c:151` |
| 时钟 | VGM 头 **0xEC**，实测 3 579 545 | `_CHIPCLK_OFS` |
| 数据块 | **0xC3**，512 字节 | `_VGM_RAM_CHIPS` |

驱动写入 `LD`（锁存，取反）与 `TG`（触发）。**TG 才是 key-on 边沿**：LD 只是把值放进 latch，
TG 才把它搬进 `freq` 并让声部发声（`k005289.c:228-231`）。这与 H 类采样芯片的“写频率不发声”是
同一个形状，代码里因此把 `freq` 与 `latch` 分成两个字段。

## 2. 唯一需要判断的一处：0xC3 是 RAM 块，但比 0xE1 窄

libvgm 有**两张**数据块表：

| 表 | 范围 | 载荷头 | 例子 |
|---|---|---|---|
| `_VGM_RAM_CHIPS` | `0xC0..0xDF` | **16 位地址** | 0xC3 K005289 |
| 同上，`0xE0..0xFF` | | **32 位地址** | 0xE1 ES5503 |
| `_VGM_ROM_CHIPS` | `0x80..0xBF` | size + offset | 0x89 MultiPCM |

`0xC3` 落在第一张表（索引 3 = chip 0x2B）、`C0..DF` 分支 → 16 位地址。实测块头：
`type=0xC3 len=514`（2 字节地址 + **512 字节数据**），头后是 `00 00 | 07 00 07 0A 0C 0D …`——
地址 0，随即是 0..15 的条目值，说明**块里已是展开的字节，不需要拆半字节**。

**读取器不需要改**：它本来就按 `addressSize` 分两支解析 `ramOffset`。**要改的是
`ChipRequirements` 的第五个字段**——若把 0xC3 当成 ROM 处理，512 字节会被读成“size + offset”
头，图像整体错位 8 字节，PROM 里一个波形都读不对，而画面上只是“波形看起来怪”。

## 3. 没有 PROM 也照样响

音高是**算术**，不是从表里量的：

```
hz = clock / (32 * (freq + 1))
```

所以缺 `0xC3` 块时，`hz` 仍然正确，只是没有形状可画。这与采样芯片正好相反（没有 ROM 就没有音高）。
代码因此把三件事分开：

```
state.hz         总是给（有 gate 时）
state.wave       只在拿到 PROM 后给
state.sampleRate 只在有 wave 时给（否则行里的 rate 会是一个没有形状可读的数）
```

断言 `testK005289Wave` 把这条顺序钉住了：**先不装 PROM 断言 `wave == nullptr` 但 `hz` 正确，
再装 PROM 断言 32 点与速率**。如果反过来（没图就不发声），一整首曲子的声部会安静地消失。

## 4. 导出的是“一个周期”

```
state.wave       = 32 点，(entry - 8) / 8        // 四位，静音在 0x08
state.sampleRate = clock / (freq + 1)            // 每秒走多少条目
hz               = rate / 32                     // 与行一致
tableWave        = true                          // 走波表导出路径（§9.11.1 的教训）
```

去重按 **32 字节的内容哈希**：两个声道共用同一张波形时合成一个文件——这正是 PROM 的说法。

## 5. 验收

```
15 首 / 45 个样本，单曲 1–5 个；速率 8363 – 28185 Hz；零样本曲目 0
04 BGM 1（34.69 s）：全曲每 0.5 秒扫行 → 21 个 (32 点, 速率) 组合，5 个导出项 5/5 命中
行示例：K005289 Ch 1  wave=32 pts rate=18839.7 note=74 hz=588.7     ← rate/32 = hz ✓
```

**交付后用户听感一次通过。**

## 6. 已知的小落差

导出的“芯片自身位深”按 `waveform::Kind::stored` 取 **6 位**（FDS 的口径），而这颗是 **4 位**。
结果不受影响——数据本身已经落在 16 级网格上，6 位量化是恒等映射——但严格说这个设置对
K005289 报大了一档。真正要修需要给 `ChannelState` 加一个 per-channel 的原生位深，而不是按
`Kind` 猜；留给需要精确标注的那一次。

## 7. 可复用的顺序（第七次验证）

1. **核心公式先抄，再动手**：块布局、`- 8`、`32 * (freq + 1)`、`info->rate = clock` 全部带行号。
2. **先查“块是哪一类”**：`0xC3` 是 RAM 而不是 ROM，宽度是 16 位而不是 32——两条都读表确认，
   不是“看起来像”。
3. **把“能响”和“能画”分开**：算术音高的芯片缺少图像时不该静音，代码与断言都要表达这一点。
4. **验收用集合**：`(点数, 速率)` 必须出现在行的某个时刻，比“听着差不多”严格，比逐帧便宜。
