# 八次猜测，一个环形窗口

> C352 的行有音符、有满格音量、波形区空白。从第一次报告到最后修好，我猜了八次。
> 真正的答案在 `c352.c` 的十二行代码里，我第八次才去读它。

## 1. 现象

`01 Welcome Racer.vgz`（Namco System 2，C352）的键盘页：

| 看到 | 数值 |
|---|---|
| 音符号 | `G#1`、`A1`、`C#2`、`E2`（有效） |
| 音量条 | 满格 |
| 波形区 | **空白** |
| 其他通道 | 有音符、有波形 |

**一句话**：这些通道在响，但波形不画。

## 2. 八次猜测

| # | 猜测 | 证据 | 为什么错 |
|---|---|---|---|
| 1 | **voice 从未 key-on** | `channelState(0..3)` 报 `flags=0 start=0 end=0` | 它们确实在响，有音符 |
| 2 | **是 mu-law，我跳过了** | `kFlagMuLaw` 分支 return | 改成解码后，波形仍空 |
| 3 | **是 noise，我跳过了** | `kFlagNoise` 分支 return | 改成画 LFSR 后，波形仍空 |
| 4 | **设备错位**（`channels[0..3]` 是别的芯片） | 那首有 `dev=3 dev=28` | `dev=39` 单设备，是 C352 |
| 5 | **行映射错位** | `row` 与 `name` 不对应 | 诊断证明 `row=7` = `Ch 8` = `channelState(7)` ✓ |
| 6 | **`hz` 有值但没波形** | `hz > 0 && wave == nullptr` | **`hz` 是 0** —— 音符走 `period` 路径 |
| 7 | **`period > 0` 但没波形** | 改成 `period > 0` | 抓到的是 `ch=19`，`end < start`，但**不是用户报的那四行** |
| 8 | **读 `c352.c`** | 十二行代码 | **`end < start` 不是坏的，是绕回** |

**八次里七次是猜，只有第八次是读。**

## 3. 真正的答案

```c
// c352.c:434 —— key-on 时设置起始位置
c->v[i].pos = (c->v[i].wave_bank << 16) | c->v[i].wave_start;

// c352.c:206 —— 何时结束
else if (pos == v->wave_end)
```

**`pos` 只向前递增、从不回退**，而比较时只看低 16 位。

所以 `start = 0xFDB4`、`end = 0x7D4D` 的意思是：**从窗口顶部继续播，绕回底部，一直播到 `0x7D4D`**。

**长度 = `0x10000 - start + end + 1` = 32666 字节**，而不是负数。

而我写的是：

```cpp
if (voice.end < voice.start) continue;                    // 跳过
const std::size_t length = voice.end - voice.start + 1;   // 下溢
```

**两道错叠在一起**：先跳过了它，即使没跳过也会算出接近 65536 的长度。

## 4. 为什么这么难找

### ① 空结果是一个合理的答案

C352 有 32 个 voice，一首曲子只用一部分。**"这个 voice 没有波形"在大多数情况下是对的**，所以跳过它时没有任何东西会报错——不崩溃、不越界、测试全绿。

**`46/46` 在这条上完全无效**：测试里没有一行被画出来。

### ② 诊断条件比诊断位置更容易写错

我写了六次诊断，**五次条件错了**：

| 条件 | 抓到了什么 |
|---|---|
| `wave == nullptr` | 前 40 条全是"从未写过"的 voice，配额用尽 |
| `hz > 0 && wave == nullptr` | **空** —— 那几行的音符来自 `period`，`hz` 恰好是 0 |
| `channel < 4` | 抓到了，但那是第一帧，只有 Ch8 播过 |

**每次"没有输出"我都当成"没有这个现象"，而它其实是"条件没抓到"。**

### ③ 两个观察矛盾时，我一直在查其中一个

- "有音符 + 无波形" → 我以为音符是对的，去查波形
- "有波形 + 音符号空" → 我以为波形是对的，去查音符

**正确做法是查它们的连接处**：音符从哪来、波形从哪来、两者为什么在这里分开。

**这次分开的原因是**：音符来自 `period`（`voice.frequency`），波形来自 `wave`（字节区间）。**两条独立的路，一条通一条不通，互不影响。**

## 5. 一个用户描述胜过我八轮猜测

中途用户说："Ch7 听起来像一个低频的正弦波。"

**这一句话直接定位了 noise 通道**——C352 的 noise 是 LFSR，低频驱动时听起来就是嗡鸣。而我前面刚说过"有旋律所以不是噪声"。

**噪声时钟慢了就是有音高。** 这个事实我从没查过。

## 6. 可复用的判断

**① 硬件语义要读源码，不要从现象推。**
`end < start` 我从"区间倒挂"推出"这 voice 坏了"，而源码里 `pos` 只增不减——**三行代码就能证伪的假设，我猜了七轮。**

**② 诊断没输出时，先确认它抓到了目标。**
每次诊断都该带一个"我抓到了这一行"的字段（`hz`、`period`、`note`），否则"空文件"既可能是"没现象"也可能是"没抓到"，而这两者要做的下一件事完全相反。

**③ 同一个数据有两个来源时，先看它们各自是什么，再看它们为什么不一致。**
音符（`period`）和波形（`wave`）是独立的；把它们当成一件事去查，永远查不通。

**④ 空列表、空波形、静音都是合法值。**
凡是"没有数据"也合理的地方，守卫写错不会报错。这类地方需要**断言"应该有时就有"**，而不是靠观察。
