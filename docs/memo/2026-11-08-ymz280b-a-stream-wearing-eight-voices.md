# YMZ280B：八个声部的外壳，一条流的里面

> 第十颗。这颗芯片的难点不在芯片，在**先弄清它在这些 rip 里被怎么用**——以及承认有一件事
> （seek）在信息层面就做不到。

## 1. 素材说了什么

统计十首的写入流：声部 1–7 各被写**一次**（fnum/ctrl/level/pan 全 0），之后再不触碰；只有声部 0
拿到一段很长的 start..stop，并且驱动**边播边把区间往前改写**。

```
01 Credit        59 条写入，v0=17, v1–v6=4, v7=18
03 Skull Fang    52 条写入，v0=52, v1–v6=4（初始化清零）
06 Sonic Diver   53 条写入，v0=24, v1–v6=4, v7=5
```

**所以“只有一个音轨在响”是素材的真相，不是解析错误。** 整首是一段流式 ADPCM，段落切换靠改 start。

启动也不是逐声部的：`0xFF` bit7 是全局 key-on 使能，上升沿启动所有「keyon && looping」的声部
（`ymz280b.c:985-992`），曲子写 `0xFF=0xD0` 后再写 `0x01=0xB0`。

## 2. 四个错误，四层测量

| # | 错误 | 怎么发现的 |
|---|---|---|
| 1 | 镜像按块大小 512 KB 分配，而块在 `dataOfs=0x3AF638`、长 `0x83053` | 块尾 `0x43268B` 恰好等于驱动写的 `stop=0x432683` |
| 2 | 地址当 nibble 除以 2 | 除以 2 后索引落在块前 1.9 MB 的零区 |
| 3 | 显示归一化把“全零解出的爬坡”放大成平滑曲线 | 归一化前峰值 0.047、符号变化 0 |
| 4 | 导出并集从**初始化写的静音区间**开始 | `start=0x394B61` 读到 0x00，播放区间 `0x3BF6DA` 读到 0xB2 |

**“是不是音频”用符号变化次数判定**：256 点里 >20 次是音频，≤1 次是爬坡/直流。这个判据比“看起来像”
严格，也比逐帧比对便宜——它直接把“曲线”与“采样”分开。

## 3. 导出：不要按区间切

并集模型在这颗芯片上不成立：它可能起于从未播放的区域（`06 Sonic Diver` 因此导出成直流），也可能
根本凑不出区间（`02 Spirit of Fang` 零导出）。

正确做法是**整块**：取 ROM 第一个到最后一个非零字节，整段解码一次，速率用最响那个声部的参数。
11 首全部有导出，0.9–72 秒。

**教训**：当“一首歌 = 一段流”时，区间是驱动器的内部记账，不是内容本身；内容就是那块 ROM。

## 4. seek：一个诚实的“做不到”

`VGMPlayer::Seek` 只挪 `_playTick/_playSmpl`，再重放这段时间的寄存器写入。而这些驱动头一秒之后
不再写寄存器——重放得到的芯片状态与 t=0 完全相同：

```
seek=0   引擎 0.20 s   RMS 0.04256
seek=5   引擎 5.20 s   RMS 0.04256
seek=30  引擎 30.20 s  RMS 0.04256
```

位置在动、声音没变。**这是信息缺失，不是 bug**：VGM 不记录“此刻读到 ROM 的第几个字节”。

现在的行为：含 YMZ280B 的歌 `seekSeconds` 直接返回 false，位置停在原处；VSU 等不受影响
（拖到 5 秒得 5.20 s、RMS 0.37470）。

**若要做到真跳**：seek 后按 `target/duration × (stop − start)` 换算字节偏移，重写 start 并**重新
key-on**（`0x01` 清 bit7 再置位），芯片会从新位置开始读。缺的只是从播放器侧写设备寄存器的入口：
`CHIP_DEVICE::write8` 在，但 `GetDevicePtr` 是私有的，需要给 vendored 玩家加一个公开访问器。

## 5. 可复用的判据（第十次）

1. **先数写入**：一首歌的寄存器写入数量级，直接决定它是“多轨演奏”还是“单流播放”。50 条 vs 20000 条，是两种芯片用法。
2. **“位置”不一定是寄存器**：流式芯片的播放进度在芯片内部，写不回去，也读不出来（在 VGM 层面）。
3. **判“有没有音频”用符号变化/RMS，不要用眼睛**：爬坡、直流、真实波形在波形图上都可能像一条线。
4. **导出语义跟着内容走**：一段流就导出整块，不要为了“像采样文件”而切区间。
