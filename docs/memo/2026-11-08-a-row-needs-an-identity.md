# 一行需要一个身份：Keyboard 行错位的根因与教训（2026-11-08）

> 适用：键盘页与 Mixer 的行对应关系。相关代码：
> `LibvgmSongInstance.cpp`（`describeSong`，建 `TrackInfo`）、
> `LibvgmTrackPlayer.cpp`（`captureState`，填 `ChannelState`）、
> `playback/SongBackend.h`（`TrackInfo`）。

## 一、现象演进

同一个缺陷，五次以不同面貌出现，每次都被当成新问题：

| 时间线 | 看到的现象 | 我当时的判断 |
|---|---|---|
| 1 | YM2610 的 `ADPCM-A/B` 行不存在 | 解码器声道数不对 |
| 2 | `FM 1..3` 显示成方波（SSG 的内容） | 名字表借用 |
| 3 | 键盘页 14 行、Duplicate `FM 1/2/3`，Solo 连体 | `channelCount` 改动副作用 |
| 4 | 出现两组 `SEGA PSG`，一组空 | libvgm 递交了两次设备 |
| 5 | PSG 行显示 YM2612 的音符与波形 | 块基准算错 |

**它们是同一个原因的五种投影**：`ChannelState` 与 `TrackInfo` 之间没有任何身份字段，只能靠“推测两个枚举的顺序一致”来对齐。

## 二、三个根因（按重要性）

### 1. 行没有身份 —— 致命

`describeSong` 造行时**知道**两件事：这行属于哪个设备、是该设备的第几个声道。但它只留下了：

- `deviceId`（**链接设备写的是父的 id**，因为行是在 head 的循环里创建的）；
- `channelIndex`（全曲编号，无法反推设备内序号）。

于是快照侧只能猜。猜法换了六种：从 0 起、按父偏移、按 `deviceId`、按 `device` 指针、按累计声道数、按块分块——全部依赖“`instances()` 的顺序 = `describeSong` 的顺序”，而这个前提从未成立：

```
tracks 顺序：文件头/设备表顺序（本例 SEGA PSG 先，YM2612 后）
instances 顺序：命令到达顺序（本例 YM2612 先被写）
```

PSG 与 YM2612 的顺序相反 → 整体错位 4 行。**YM2610 曾“通过”纯属两边顺序恰好相同**。

### 2. 设备身份曾被误当作可区分

libvgm 给链接的 SSG/PSG **与父设备相同的 `deviceId`，甚至是同一个 `PLR_DEV_INFO` 指针**。任何“用设备字段区分父与子”的写法必然失败——这一条让前四次修改全部无效。

### 3. 系统里有“兜底追加”的通道

`capture` 结尾曾有“不属于任何轨道的状态追加到最后”。当映射算错时，它不报错，而是**悄悄长出多余的行**（第二组 `SEGA PSG`）。兜底逻辑会把上游的错误变成另一种形态的错，而不是暴露它。

## 三、修法（最终形态）

```cpp
// SongBackend.h
DeviceId sourceDeviceId;   // 这一行真正属于哪个设备（链接设备用 child.id）
int      deviceChannel;    // 该设备内部声道号；-1 = 整设备
```

- `describeSong` 在 `addTrack` 处写入这两个值（head 路径与 linked 路径各一处）；
- `capture` 用 `trackForVoice(instance.deviceId, channel)` 精确配对；
- **删除**：`channelBases`、按声道数排序、按 id 去重、`trackFor`、末尾追加。它们都是为“猜顺序”而生，身份字段到位后没有存在理由。

字段放在 `TrackInfo` **末尾**，因为 `NsfBackend.cpp` 等处用了聚合初始化，插在中间会静默改变字段含义（这次编译直接报了 `C2440`，算是幸运）。

## 四、教训

1. **身份要写下来，不要推出来。** 只要一处代码“知道”某个事实（哪台设备、第几个声道），就把它存进结构体；让下游去还原等于让每个读者重新猜一次。
2. **顺序不是契约。** 容器顺序、创建顺序、枚举顺序三者可以不同，且会随输入变化。任何依赖顺序的代码，都要问“如果我换个输入，这里还成立吗”。
3. **兜底逻辑要能报错，不能换错法。** “未匹配就追加”把一个映射错误变成了 UI 上的多行；正确做法是“没有轨道就没有行”，让缺陷表现为缺失而不是幻觉。
4. **跨设备/跨型号验证要在通道数不同的组合上做**（规范 §10）：YM2610（13+3）与 Mega Drive（7+4，且顺序相反）是两种必须都过的情形。
5. **别用改共享计数的方式修布局。** 动 `channelCount` 会连带换名字表、换静音掩码，一次改动波及四个消费者。

## 五、这次可复用的检查清单

- [ ] 结构体里有没有“下游需要、但只有上游知道”的事实？有就加字段。
- [ ] 这处匹配用的是 id、名字、还是编号？三者中只有“上游写入的唯一对”是可靠的。
- [ ] 有没有为了绕开缺失字段而加的排序/偏移/去重？字段补上后应当删掉。
- [ ] 兜底分支是“报错/缺行”，还是“多一行”？后者会隐藏缺陷。
- [ ] 验证是否覆盖了“两边顺序相反”的曲目（本例 `sega_md/02 Green Hill Zone`）。
