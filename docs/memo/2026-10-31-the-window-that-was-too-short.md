# 两个列表不一样，先问它们看的是不是同一段

- **日期**：2026-10-31
- **对象**：NSF 的 DPCM 采样列表（`backends/nsf/`、`Tests/NsfProbe.cpp`）
- **目的**：记一个查了两周的"4 对 2"，以及四个被依次排除的假设
- **相关**：`review/2026-10-31-dpcm-sample-review.md`、`memo/2026-10-30-the-register-width-nobody-checked.md`

## 1. 一句话

**FamiStudio 的 NSF 导入只跑 120 秒。那两个采样在第 163 秒才第一次响。** 它没有过滤，是还没听到。

## 2. 现象

| 曲子 | 我们 | FamiStudio |
|---|---|---|
| `Entry080` | 2 个（176 / 688） | 2 个，逐字节一致 |
| `fod_snowburnb` | **4 个**（176 / 688 / 514 / 388） | **2 个** |

第二首差了两个。用户看到的后果是"军鼓导出不对"——他拿到 514 而不是 688。

## 3. 四个假设，依次排除

| 假设 | 怎么验的 | 结果 |
|---|---|---|
| 那两条太短，被当成噪声丢掉 | 打印每次触发的 `$4013` | 四条都 ≥ 20 字节，没有短触发 |
| 那两条是同一段的两份拷贝 | 四段两两比对 | 0–6%，随机水平 |
| 那两条没真正播放，只是被写了地址 | 改成只在 `$4015` 启动边沿记录 | 仍然四条，说明都播过 |
| 我们读得太快，把碎片当采样 | 改成每视频帧读一次（60 Hz） | **仍然四条，无变化** |
| 我们切错了边界，四段本是两段 | 逐段互相关（±200 字节） | 最高 15.4%，随机水平 |

**五个方向都试完，一个都不成立。**

## 4. 真正的原因

把每次新采样出现的时间打出来：

```
$C0C0   58 s     军鼓 688
$C000   58 s     底鼓 176
$C640  163 s
$C380  163 s
```

**FamiStudio 的导入对话框默认 120 秒。** 用户在它的设置里改成 180 秒后，列表变成 4 个——**当场验证**。

`Entry080` 的两个在 12 秒和 35 秒，都在窗口内，所以那首两边一致。**同一套代码，两种结果，差别只在曲子什么时候用那两个采样。**

## 5. 顺带解释的另一件事

用户报"军鼓不对"，导出的是 514 字节（`$C380`）。**因为他播放超过三分钟才点导出**，那一刻刚响的是 `$C380`。真正的军鼓 `$C0C0` 只在第 58 秒附近响过。

**"导出当前窗口那个"这个行为从头到尾是对的，问题是 688 只在一个很窄的时间窗里能被"当前"捕获。**

## 6. 教训

**① 两个列表不一致时，先问"它们看的区间一样吗"，再问"判据一样吗"。**

前三轮我都在查判据：长度阈值、去重、读取频率、边界算法。**没有一个是对的，因为判据本来就一样。** 差别在区间。

这和 `2026-10-30` 那条是一族：**一个数对不上，先问"它是不是别人的"**——这次是"它是不是别的时候的"。

**② 一个能自证的数字，比五轮推理便宜。**

改 180 秒这个动作不到一分钟，我在它之前做了五次实验、写了两个脚本、改了一版代码又回滚。**如果我早点问"你导入时跑多久"，第一轮就结束了。**

**③ 排除假设的顺序应当是"成本从低到高"，不是"可能性从高到低"。**

"导入时长"是最便宜的检验（改一个数字），我把它放在最后，因为它不在代码里。

## 7. 剩下的产品问题

**算法已经不需要改了。** 剩下的是一件体验问题：

> 用户想要的采样，可能只在某一分钟里响过；而窗口只显示"最近触发的那个"。

按"导出当前"的语义，这是正确的；按"我想拿到那个军鼓"的目的，它不可用。

**三个选项，按改动从小到大：**

1. **文件名带地址**（`2A03_DPCM_C0C0.wav`）——导出后能确认拿的是哪个，仍要卡时机；
2. **面板显示当前采样的地址与长度**——同上，边看边判断；
3. **一次性导出全部不同采样**——用户已定"以后单独做"，但这次的数据说明它是唯一真正解决"卡时机"的办法。
