# SegaPCM：寄存器就是播放头，而 bank 藏在控制字节里

2026-11-08。第五颗采样芯片，素材两首（`01 Magical Sound Shower`、`03 Scene Select`）。
听感两轮，两轮都是同一个原因的不同形态。

## 一、芯片是什么

十六个声部，每个声部八个寄存器（`libs/libvgm/emu/cores/segapcm.c`）：

| 偏移 | 含义 |
|---|---|
| `8n+2` / `8n+3` | 左/右音量，七位 |
| `8n+4` / `8n+5` | 循环地址，256 字节为单位 |
| `8n+6` | 结束地址，256 字节为单位 |
| `8n+7` | 地址步进（每输出样本前进 1/256 字节） |
| `0x80+8n+4/5` | 当前地址 |
| `0x80+8n+6` | bit0 = 0 时播放，bit1 禁止循环，**其余是 bank** |

- 速率：`pitch × clock / 32768` 字节每秒（核心 `clock / 128` 渲染，一步 = 1/256 字节）
- 样本：0x80 中心的 8 位无符号，长度由结束地址给出

没有采样表、没有命令流，**寄存器本身就在描述“此刻读到哪”**。所以这一颗的“可视化”只能是
把 ROM 里那段真实采样画出来——没有可合成的形状。

## 二、第一次听感：有的对，有的不对

`03 Scene Select`：Ch1/Ch2 该是 Slap Bass，行里却是直线，导出也没有它。

原因：`segapcm.c:156` 取字节时是 `rom[(control & bankmask) << bankshift | (addr >> 8)]`，
而我只用了地址寄存器。这首的驱动写 `control = 0x0A` 和 `0x12`——**bank 8 与 16**，
即 `0x10000` / `0x20000`；地址寄存器只写 `0x0000`。于是每个声部都从镜像底部读，
全 0 解出来是常量：直线，导出静音。

改：把 `(control & bankmask) << bankshift` 折进地址。验证的办法很直接——算出来的
`0x17100`、`0x20000` 正好是文件里 ROM 数据块的落点，`0x118400` 落在最大一块之内。

## 三、第二次听感：换一首又全是直线

`01 Magical Sound Shower`：0 导出，八行全直。

这次不是漏了 bank，是**bank 的参数每个文件不同**：

| 文件 | VGM 头 0x3C / 0x3E | 生效值 | 关键控制字节 | 正确起点 |
|---|---|---|---|---|
| `03 Scene Select` | 13 / 0xF8 | `(c & 0xF8) << 13` | `0x0A`、`0x12` | `0x10000`、`0x20000` |
| `01 Magical Sound Shower` | 12 / 0x00 | `(c & 0x70) << 12`（0 意为默认 0x70） | `0xD2` | `0x5437C` |

我上一轮把 13 / 0xF8 写成了常量。第二首按那个算，`ctrl = 0xD2` 得到 `0xD0 << 13 = 0x1A0000`，
而镜像只有 512 KB、数据在 `0x40090` 一带——全部落在空区，于是又是直线、又是 0 导出。
第一首碰巧对，所以症状表现为“有的对有的不对”。

## 四、修法：把这两个字节一路带下去

```
VgmCommandReader   读头部 0x3C / 0x3E（mask 为 0 时用 0x70，与 libvgm 一致）
      ↓
VgmSongLoader      emit 时把 (shift | mask << 8) 放进 ChipSlot::flags
      ↓
VgmReplayer        reset 时把它塞进 ChipConfig::flags（rewind 的 reset 也要带）
      ↓
SegaPcmDecoder     按文件决定 offsetOf；收集器读 ir.chips[].flags
```

缺任何一段，取值就退回默认——而默认只对其中一首成立。

**第一次尝试失败的原因**：我给收集器加的那段代码没有真正落进文件（替换没有匹配上），
而我在统计“补丁是否生效”时数的是注释里的字符串，于是误以为已经接好。真正发现它的是
`ctrl=0xD2 → start=0x1A437C` 这个数字：`0x1A0000` 只能来自 `<< 13`。**数字比“补丁已应用”
可靠。**

## 六、可复用的四条

1. **采样芯片先找“字节从哪来”**：这一颗是 `bank | (addr >> 8)`，两个来源都不在地址寄存器里。
2. **header 字段要读，不要假设**：`0x3C/0x3E` 两首文件就差得很远，而差别恰好让其中一首完全失效。
3. **0 表示默认**：mask = 0 不是“没有 bank”，而是“用格式默认的 0x70”（libvgm 同样处理）。
4. **验证补丁是否生效要数字，不要字符串**：这次两轮返工都因为把“注释里有这行”当成“逻辑已接上”。

## 七、未解决（2026-11-08 记档）

上面六节是**已确认**的部分。另有两件事没有解决，本芯片按“部分完成”记档：

1. **导出不全**：只在控制位 key-on 边沿归档，漏掉三类击打——key-on 之后才写音量的、
   靠重写 `0x84/0x85` 在区间内重触发的、只靠 loop 回绕从不重新 key-on 的。
2. **显示与实际发声错位**：行画的是锁存的 `start..end`，而驱动会在区间内跳转，`end` 又
   常指向整个 64 KB bank 的末尾——于是显示一段听到另一段、一行里出现几段相邻采样，
   或只画出一个采样的一部分。

四次尝试全部回退：按 `loop..end` 收集（加载变秒级）、窗口跟随估算位置（漂移）、
地址重写与 end 写入都归档（161 个，合并后又变成整 bank）、窗口上限减半（页回绕的声部变空）。

**根因**：`start` / `loop` / `end` 的真实语义缺一个可验证的地面真值。`loop` 是样本起点
这一点是从块落点反推的（`0x40090/0x40951/0x41C03…` 与 VGM 头 `dataOfs` 逐个吻合），
**尚未逐条对过听感**。

**下次动手前必须先做**：一个只读的取证工具，按时间打印每一条写入与折算后的地址，
配合一次试听逐条对齐。没有这张表，任何改法都只是猜，而这四次已经证明猜的代价是
用户多等一轮。
