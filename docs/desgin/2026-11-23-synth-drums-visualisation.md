# 合成鼓的可视化（fmDrum）：调研与方案

> 2026-11-23。**未开工**。目标：YM2413 / YM3812 的 5 个节奏行（Ch10–Ch14）不再画假正弦，
> 而是像旋律行那样有真实形状，并且能导出。
>
> 按 `2026-11-23-one-chip-is-not-a-class.md` 的规矩：**先只动 OPLL 一颗**。

## 一、这些通道到底是什么

**不是采样。** 五个鼓由 FM 算子 + 芯片内部噪声移位寄存器合成（`emu2413.c:966-1007`，
`calc_slot_bd/sd/tom/cym/hh`），芯片里没有 PCM 数据。

| 鼓 | 寄存器 | 说明 |
|---|---|---|
| Bass Drum | `0x16`（音色号）、`0x26`（block/fnum）、`0x36`（音量） | 用 fnum 调音高 |
| Snare Drum | `0x17`、`0x27`、`0x37` 高四位 | 音高固定 |
| Tom | `0x18`、`0x28`、`0x38` 高四位 | 用 fnum 调音高 |
| Cymbal | —、—、`0x38` 低四位（音量） | 噪声 |
| Hi-Hat | —、—、`0x37` 低四位（音量） | 噪声 |

**触发在 `0x0E`**：bit5 使能节奏模式，bits 4-0 是五个鼓的触发位（**上升沿触发**）。

**没有"音高"这个维度**——这正是它和旋律行的根本区别，也是 `FmVoiceDriver::noteOn(hz)` 现在
接不住它们的原因。

## 二、代码现状

| 层 | 现状 | 缺口 |
|---|---|---|
| 解码器 | `rhythmWrite` 只记 `rhythm[i].end = time + kRhythmGate`（`kRhythmGate = 4410`，100 ms） | **不记任何鼓参数** |
| `capturePatch` | `channel >= melodic` 直接 `return false` | 鼓没有 patch |
| 面板 | `noteWaveform == nullptr` → `cycleFor(fm, …)` | **画通用正弦（假信息）** |
| 导出 | 鼓行不是周期形状，被排除 | 鼓行导不出东西 |
| MIDI | 鼓作为 C4 触发的音符**已正常** | 不要动 |

## 三、要新增的四处

1. **解码器记参数**：节奏模式下，`0x16-0x18` / `0x26-0x28` / `0x36-0x38` 的写入存进
   `Impl::rhythmRegs[]`（**不要覆盖 6-8 的旋律字段**——那些通道已被节奏借走）。
2. **`VoicePatch` 加"一次性"语义**：`bool oneShot`、`uint8_t triggerMask`（`0x0E` 的那一位）、
   `double lengthSeconds`。仍然用 `regs` 装那 9 个寄存器，保持"patch 就是寄存器"的一致性。
3. **`FmVoiceDriver` 加一个节奏方言**：`init` 写 `0x0E = 0x20`（使能，不触发）；
   `noteOn` 写 `0x0E = 0x20 | triggerMask`；`noteOff` 写回 `0x20`。**不需要 `hz`。**
4. **`noteWave::render` 允许无音高**：`hz <= 0` 时跳过 `noteOn(hz)` 走一次性的那条；
   长度取 `lengthSeconds`，不做 release 包络（鼓自己会衰减）。

**面板和导出都自动受益**：只要 `voicePatch` 存在，两条路径都已经会渲染整段波形；改动集中在
"鼓也能产出一个 patch"。

## 四、需要你拍板

**D1（范围）· 只做 OPLL，还是把 OPN 的 6 个节奏一起做？**
**建议只做 OPLL**（上一轮的教训）。OPN 的节奏寄存器与 OPLL 不同（`0x18`/`0x10`/`0x21` 那一套），
表要另写一份。

**D2（长度）· 鼓的形状渲染多长？**
| 选项 | 效果 |
|---|---|
| **A. 固定 300 ms** | 简单、可预测；但短鼓（Hi-Hat）会拖一条静音尾巴 |
| **B. 渲染到静音**（能量低于阈值） | 贴合真实；实现上要边渲边判，成本略高 |
| **建议 A 起步**，长度 250–300 ms，之后按听感调 |

**D3（电平）· 鼓的满度怎么定？**
鼓的幅度与旋律不同源（噪声+FM），**必须实测**：最响的 BD 与 TL=0 的旋律谁更响。
**建议先用与旋律相同的位宽（12/16），实测后再定要不要单独一个常数**——这次先量再改。

**D4（触发保持）· `0x0E` 的触发位保持多久？**
芯片是上升沿触发，保持长时间也可能有副作用（重复触发）。**建议写完立即清回 `0x20`**，
渲染仍会继续（芯片内部已经启动）。

**D5（面板语义）· 鼓行的形状是"时长固定的一条衰减"吗？**
旋律行画的是"整段音符"（1.5 s 保持）。鼓是一次性衰减，**建议按 D2 的长度画整段**，
与旋律行的语义一致（"这一行会发出什么"）。

**D6（导出）· 鼓行要不要能拖/能导出？**
**建议要**——它现在是"有名字有电平但没有文件"的第三种状态。

## 五、未知与风险（先量）

1. **只写那 9 个寄存器 + 触发，`emu2413` 会不会发声？**（必须验证，一分钟的事）
2. **鼓的实际衰减长度**：BD 可能 400 ms，Hi-Hat 只有 60 ms。
3. **鼓的幅度**：与旋律行差多少 dB。
4. **`0x0E` 的 bit5 与触发位同时写**是否必须（可能要先使能再触发）。
5. **节奏模式借走 6-8**：渲染用独立核，不影响旋律行；但解码器侧不能把 6-8 的参数写坏。

## 六、工作量与顺序

| 步 | 内容 | 验证 |
|---|---|---|
| 0 | **量**：手写 9 个寄存器 + 触发，确认能发声、长度与幅度 | 一条临时断言 |
| 1 | 解码器记 `rhythmRegs` | 单元断言：写 `0x16/0x26/0x36` 后 patch 里有这三条 |
| 2 | `VoicePatch` 的一次性字段 + 节奏方言 | 手工 patch 能渲染出衰减 |
| 3 | 面板接通 | 截图：Ch10–14 出现真实鼓形 |
| 4 | 导出接通 | 拖一行出来听到鼓声 |

**粗估：0–2 步半天，3–4 步半天。** 风险集中在第 0 步——**如果核只靠 `0x0E` 触发不出声音，
整个方案要改（那就得走"把鼓当一次旋律音渲染"的路）**。
