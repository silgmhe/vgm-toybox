# 谁在重采样

> 2026-11-22。YM2610 导出仍有滋滋，而播放没有。问：libvgm 是不是自带重采样？我们是不是不该保持阶梯？
>
> 结论：**核不重采样，`PlayerA` 也不重采样——唯一的重采样是我们自己。** 导出让核跑 55 556 再抽到 48 000，而播放让核**直接跑 48 000**。这才是差别。

## 一、三个候选，逐个排除

### 1. 核内部分数重采样器 —— 存在，但 native 时比值是 1

`nuked` 系列（OPM/OPL/`ym3438`）确实自带：

```2290:2293:libs/libvgm/emu/cores/nukedopm.c
    // ratio: sampleRate / (clock / 64) * (1 << resamplerFraction)
    chip->rateratio = (uint32_t)((((uint64_t)64 * chip->smplRate) << RSM_FRAC) / chip->clock);
    if (abs(chip->rateratio - (1 << RSM_FRAC)) <= 1)
        chip->rateratio = (1 << RSM_FRAC);
```

**但 `smplRate = clock / 64`（native）时 `rateratio` 归一到 `1 << RSM_FRAC`，即 1.0——它不做重采样，只是逐个时钟推进。**

**我们导出时传的正是 `noteRateFor(model)`，那就是 native。所以这条不产生阶梯。**

### 2. `fmopn` 的 `freqbase` —— 不是重采样

```2042:2042:libs/libvgm/emu/cores/fmopn.c
OPN->ST.freqbase = (OPN->ST.rate) ? ((double)OPN->ST.clock / OPN->ST.rate) / pres : 0;
```

**它调整的是每个输出样本的相位增量，而不是"生成一批再挑"。** 输出就是该速率下的真实样本。

### 3. `PlayerA` —— 不额外重采样

**`PlayerA` 让每个核**按 host 速率启动**（`SetSampleRate` 传的就是设备采样率），所以 `Update` 直接产出 48 000 的样本，中间没有第二道重采样。**

## 二、所以差别只有一处

| | 核的输出速率 | 之后发生什么 |
|---|---|---|
| **播放** | 48 000（host） | 直接进总线 |
| **导出** | 55 556（芯片） | **我们的 `heldAt` 抽成 48 000** |

**播放那条链里没有任何人重采样。导出的链里有一个，而且是我们写的。**

**这解释了两件事：**

- 为什么播放干净——它没有混叠的机会；
- 为什么加了 Blackman 窗还在——**滤波器再好，也是在补偿一个不该发生的步骤**。26 kHz 削到 0.000 之后剩下的不是混叠，而是**抽取本身带来的时变特性**（分数位置被丢掉）。

## 三、我们为什么会走到这一步

**两条要求被当成了一条**：

1. “导出的音色要和芯片一致” → 曾经用“让核跑芯片速率”
2. “播放和导出要一致” → 播放让核跑 host 速率

**第 1 条其实是“别用面板的 8 kHz 糊弄”，而不是“必须 55 556”。** 核在 48 000 下仍然按 `freqbase` 正确计时，音高和音色都由寄存器决定——**速率只影响混叠，不影响音色。**

## 四、建议的改法

**导出让核直接跑目标速率**（导出设置里的 48 000 / 44 100），与播放同构：

| | 现在 | 建议 |
|---|---|---|
| 核速率 | `noteRateFor(model)` = 55 556 | **`targetRate` = 48 000** |
| 抽取 | `heldAt` + FIR | **不需要** |

**收益：**
- **没有重采样**，播放与导出走同一条路；
- 低通可以整个删掉（那是补偿，不是修复）；
- 文件头声明的速率就是核的速率，不用再传 `RenderedNote.rate`。

## 五、代价：divisor 要重新对齐

**核在非 native 速率下的 `freqbase` 与 native 时不同**，f-number 的换算系数因此不同——这正是前面几轮反复的地方。

**但有一个现成的锚点：面板已经在 8 kHz（非 native）下跑，而且音高是对的。**

| 型号 | 面板（8 k，非 native） | 导出（若改 48 k，也是非 native） |
|---|---|---|
| YM2612 | 144（用户听感确认） | **144** |
| YM2203 | 144（实测） | **144** |
| YM2608 | 288（实测） | **288**？需验证 |
| YM2610 | 144（用户听感） | **144** |

**面板和导出会落在同一个分支上**，这比现在“面板 8 k、导出 55 k”分属两档要稳——**同一张表服务两条路径。**

**唯一要重测的是 YM2608**：它在两种速率下的实测值可能不同（8 k 用 288、55 k 也用 288，但 48 k 未必）。

## 六、这条改动的风险

1. **divisor 要按新速率重测四个型号**，而不是改一个参数——这是它唯一的成本；
2. `RenderedNote.rate` 会恒等于 `targetRate`，**接口可以简化回去**，但那要等确认后再做；
3. **采样芯片（8-bit 采样回放）不受影响**——它们仍走 `heldAt`，那条路径的阶梯是特性。

## 七、不做的事

**不试图用更长的 FIR 解决。** 26 kHz 已经削到 0.000，再加抽头只会更慢、更钝，而问题不在阻带深度——**在于我们为什么要抽取。**
