# PCM 采样导出设计

**入口**：File → Export → All DPCM Samples…
**范围**：NSF 的 2A03 DPCM 已完成；VGM 的 PCM 芯片留了接口，未接
**相关**：`docs/review/2026-10-31-dpcm-sample-review.md`、`docs/memo/2026-10-31-the-window-that-was-too-short.md`、`docs/memo/2026-10-30-the-register-width-nobody-checked.md`

## 1. 需求

**一句话**：把当前曲子里**所有** PCM 采样各导出一个 WAV，一次操作，不依赖播放。

三条约束来自用户，它们决定了整个设计：

1. **不只看播放过的**。打开文件、直接导出，也要拿到全部。
2. **按曲子的长度扫**。设置里 NSF 播放时长是 5 分钟，就要覆盖 5 分钟。
3. **不拖慢打开**。导出这件事不该让播放和载入变慢。

## 2. 采样从哪来（两条路径）

| | NSF | VGM（未接） |
|---|---|---|
| 数据本体 | 整个 ROM 在内存里，`$C000-$FFFF` 随 bank 映射 | `0x67` 数据块，type `C2` = 2 字节地址 + 4096 字节 |
| 采样清单 | **没有目录表**，只有驱动写过的 `$4012`/`$4013` | 同样没有，只有寄存器写入历史 |
| 长度 | `$4013` 八位 × 16 + 1，最大 4081 | 同 |
| 边界 | 寄存器给长度，尾部填充要裁 | 同 |

**“按目录表枚举”对这两条都不成立。** 目录表只存在于 SegaPCM/OKI/K054539 那类芯片上，属于下一轮。

**NSF 的 ROM 是完整的**，所以只要知道驱动指向过哪些 (地址, 长度)，就一定切得出数据。**VGM 要看文件带不带 `0x67` 块**——不带的 VGM 里根本不存在采样数据，只能报“没有”。

## 3. 架构

```
      NsfBus（音频线程）                    NsfPlayer（音频线程）
   ┌─────────────────────┐              ┌──────────────────────────┐
   │ $4015 启动边沿       │              │ scanSong(曲子时长)        │
   │  ├ 抓 4 KB 窗口快照  │─────────────→│  └ 走完整曲 → ScanResult  │
   │  └ 按起点去重存一份  │              │       └ 带上采样列表      │
   └─────────────────────┘              └──────────────────────────┘
                                                   │
                              ITrackPlayer::samples() → DecodedSample
                                                   │
                              playback::writeSamples() → dpcm_<addr>_<bytes>.wav
```

**三层的分界，是为了 VGM 能接进来**：

| 层 | 知道的 | 不知道的 |
|---|---|---|
| `backends/nsf/` | DPCM 的 1-bit 积分、`$4013` 的算术、trim | 文件怎么命名、WAV 怎么写 |
| `playback/` | `DecodedSample`（电平 + 速率 + 名字）、WAV 容器 | 这些电平来自哪颗芯片 |
| `ui/` | 菜单、文件夹选择器、报告 | 一切格式细节 |

**`DecodedSample` 携带的是电平，不是字节。** 字节的编码方式（DPCM 的 1-bit 增量、将来 8-bit 无符号 PCM）留在各自后端。这是“加一颗芯片只改一个后端”的前提。

## 4. 采样列表来自扫描，不来自播放

**这是最关键的一个决定，也是第一版做错的地方。**

第一版把收集挂在 `$4015` 的启动边沿上，**在播放实例里**。结果是：

- 刚打开就导出 → **0 个**（还没播到）
- 播了一分钟 → **1 个**（只到过那一个）

**NSF 有两个 `NsfPlayer` 实例**：

```
扫描线程的 probe   ── 走完整曲（曲子时长）──→ 采样记在 probe 的 Bus 里，随 probe 销毁而丢
播放用的 player    ── 只走用户听到的那段──→ 采样记在它自己身上
```

两者通过 `ScanHandle` 传 `ScanResult`（音高 + MIDI）。**采样必须搭这趟车**：`ScanResult` 带上列表，`applyScan` 用 `shared_ptr` 存（音频线程不拷贝 64 KB），导出优先读它。

**只有扫描还没跑完时**才退回播放实例自己的列表——那是同一个问题的短答案，不是另一个答案。

**为什么扫描不能搬到导出**：note/MIDI 提取靠它，键盘页的音高、DPCM 行的 `analyzing` 状态都等这一趟。**采样是搭车的副产品，不增加打开成本**（`Entry080` 扫描 1 秒，比读文件还快）。

## 5. 扫描多长

**之前**：`NsfPlayer::scanSeconds = 180.0` 和 `NsfBackend::kDefaultLengthSeconds = 180.0` 是两个独立的硬编码，恰好相等。**用户在设置里改 `nsf.durationSeconds`，扫描照样跑 180 秒**——那个常量从不跟随设置。

**现在**：`scanSong(length)`，`length` 在 `NsfSongInstance` 构造时从 `SettingsStore::getNsfDurationSeconds()` 读出，扫描线程在构造末尾启动（`NsfBackend.cpp:257`），所以扫的就是用户设的时长。

**时序是原本就对的，错的是扫描没用那个数。**

## 6. 字节为什么必须拷贝

`CapturedSample` 存的是 4 KB 窗口的**副本**，不是地址。

**原因是 bank**：`$C000-$FFFF` 的内容由驱动随时改写。同一地址隔一会儿再读，拿到的是另一段数据——**而地址、长度、速率全都还对得上**，所以这种错误不会露出来。这一支踩过一次，见提交 `bcad145`（`$4012` 的“写过”不等于“用过”，一个从未播放的地址把真采样切短了）。

**窗口是 4 KB 而不是 `length`**：`$4013` 可能报得比采样长（驱动常写最大值），尾部靠 trim 裁。

**上限 16 个、64 KB 常驻**，用 `std::array` + 计数器而不是 `vector`：音频线程不能分配。写者填完条目再抬计数，计数只增不减，读的人取一份拷贝就够。

## 7. 从字节到 WAV

```
1. dpcm::finalLength(len, bytes)   —— 去尾部填充（0x00/0x55/0xAA/0xFF），再去 padding 字节（16k+1）
2. dpcm::decode(bytes, length)     —— 每字节 8 个 1-bit 增量积分，钳在 ±128，除以 128
3. writeSamples()                  —— float32 单声道，速率取 $4010 对应的表值（PAL/NTSC 各一张）
```

**命名带地址和长度**：`dpcm_C0C0_688.wav`。这一支反复吃过“导出的是哪个”的苦，没有地址就得靠听。

## 8. 输出与反馈

**复用波表导出的报告浮层**，`ExportReport` 加 `samples` 标志：

- 标题从 “Wavetables exported” 换成 “Samples exported”
- “Channels in the snapshot” 换成 “Samples the song started”
- 零个时的句子换成“这首曲子还没有启动过采样”

**共用浮层是对的**（对用户是同一份报告：写了什么、写去哪、什么没写成），**但文案必须分开**——把“波表已导出”压在五个采样文件上，正是这一支花了一整轮 review 在清理的那类话。

**文件夹选择器开着时列表已拷好**：音频线程还在启动采样，回调里再取会是**和计数不一致的另一个列表**。

## 9. 扩展 VGM 的路径

接口已经在那里，接的时候只需要：

1. `LibvgmSongInstance`（或其 track player）覆盖 `samples()`
2. 从 `VgmCommandReader::dataBlocks()` 取 `0x67` 块，按 type 拼镜像：
   - `0xC0-0xDF`：**2 字节地址 + 数据**（已确认 Gimmick! 的 NES VGM 走这条）
   - `0x80-0x9F`：8 字节 ROM 头 + 数据
3. 从 `0xB4` 写 `$4012`/`$4013`/`$4015` 的历史取触发
4. 剩下的（trim、积分、命名、写文件）全部复用

**注意**：`0x67` 的 `type` 和 `size` 要从**项目自己的 `VgmCommandReader.cpp`** 读，不要凭记忆写命令长度表——本轮为此浪费了一整轮（`0x80-0x8F` 是 1 字节而非 3，`0x68` 是 12 字节）。

## 10. ADR

### ADR-001：采样列表来自整曲扫描，而不是播放

**为什么**：需求是“这首曲子有哪些采样”，不是“我听到了哪些”。播放实例的回答带时间戳，扫描的回答不带。

**代价**：扫描是异步的，打开后有几秒窗口期只有部分列表；导出前若扫描未完成，拿到的是短答案。**这是暂时的，不是错的**——退回播放列表已经在注释里写明。

### ADR-002：解码留在后端，容器留在 playback

**为什么**：DPCM 的积分是 NES 的知识；WAV 是容器。混在一起，加一颗芯片就要改 `playback/`。

**代价**：`DecodedSample` 要携带“已经解码好的电平”，内存是字节的 8 倍（4081 字节 → 130 KB）。**只在一个采样真正被导出时才生成**，不常驻。

### ADR-003：扫描时长取曲子时长，不设独立常量

**为什么**：两个 180 相等是巧合，不跟随设置。用户改时长时，扫描必须跟着改。

**代价**：曲子设得很长时，打开文件要多等（10 分钟 ≈ 4 秒扫描）。**可接受**——比“导不全”好，且这是用户自己设的值。

### ADR-004：报告浮层共用，文案分开

**为什么**：用户看到的是同一件事（写了什么、写去哪、什么没成）。两套浮层会立刻分叉。

**代价**：`ExportReport` 多一个标志，浮层里两个三元表达式。**比复制一份浮层便宜**。

## 12. 已知限制

1. **VGM 的 PCM 芯片未接**（SegaPCM、OKI、K054539 等 11 个解码器）。接口在，实现没有。
2. **只扫一遍，只认寄存器**。驱动把采样数据当普通代码访问、或用某个非常规路径触发，都看不见。
3. **16 个采样的上限**。超过就只留前 16 个（按首次播放顺序）。
4. **不带 `0x67` 的 VGM 无法导出**——数据不在文件里，这是格式事实。
5. **NSF 的 DPCM 没有目录表**，所以“ROM 里所有采样（含没用过的）”对 NSF 不成立，只能枚举用过的。用户选择的“按目录表枚举”只适用于 VGM 的 PCM 芯片。
