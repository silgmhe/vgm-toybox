# SegaPCM 取证：一次击打由哪几次写入组成（2026-11-12）

§9.16.2 记着两条未解决的问题，并规定“下次动手前必须先做一个只读取证工具”。这是那次取证的
结果：工具、方法、数字，以及据此要改的两处规则。

## 0. 结论先行

| 结论 | 证据 |
|---|---|
| **击打边沿不是 `control` 的 1→0，而是“每一次把 `0x86` 写成 bit0=0”** | `01 Magical Sound Shower`：bit0=0 的 control 写 **7583** 次，其中真正的 1→0 只有 **6** 次 |
| **因此导出确实漏样本** | 同一首里这些写入共覆盖 **12** 个不同区间，现有规则只产出 **3** 个文件 |
| **`end` 是“相对 bank 的 64 KB 页号”，不是 bank 末尾** | 核心 `(addr >> 16) == end`；本批 end ∈ {0x3B, 0x48, 0x4C, 0x82}，导出长度 1412–24064 字节，与听感一致 |
| **`loop` 在每次击打前都被写成与 `start` 相同** | 两首 14 次边沿里 `loop != start` 出现 0 次 |
| **`0x84/0x85` 的 1.5 万次“播放中写入”不是新击打** | 它们的取值互不对齐（0x549DE、0x5497C…），是驱动在区间内**寻址**；真正的击打随后跟一次 control 写 |

## 1. 工具

`tools/segapcm_forensic.py`（只读，不改任何代码）：

```
python tools/segapcm_forensic.py "test_file/SEGAPCM/01 Magical Sound Shower.vgz" --seconds 5
```

它按 VGM 的时序逐条回放，对每条 `0xC0` 打印：时间、通道、寄存器、值，以及**按核心公式折算出的
start / loop / end / 速率**，并标出 `KEY-ON`、`START-MOVED`、`VOLUME`、`END while playing`。

写这个工具时踩到的第一个坑：**`0xC0` 的 16 位偏移是小端**（低字节在前），与 X1-010 的 `0xC8`
相反。读错字节序时，前 20 条看起来仍然“像寄存器写”，因为地址高字节刚好落在合法范围内——只有把
`start` 和已知的 `0x5437C` 对上，才确认了顺序。

另一个坑：**1.51 头的 0xC0 不是 SegaPCM 时钟**（那时表头只有 0x80 字节）。这批文件的
`pitch × clock / 32768` 与导出的 16 113 Hz 对得上，clock = 4 MHz，是 System 16 上这颗芯片的
实际频率，工具因此在 1.51 文件上直接用它。

## 2. 一次击打在流里长什么样

`03 Scene Select` 第 3 通道、一次典型击打：

```
loopLo  = 7C      loop 指针低位
addrMid = 7C      当前地址中字节     ┐ 五个写构成“把指针放回起点”
loopHi  = 43
addrHigh= 43
end     = 48      结束页
pitch   = 84
control = D2      bit0=0：开始播放（bank 在 bit4-7）
```

下一次击打**再写一遍同样的六个字节**，`control` 仍然是 `0xD2`——bit0 从来没有回到 1。
核心并不需要边沿：它每次混音都从 `regs[0x84/0x85]` 重建地址，所以“把地址写回起点”本身就是
重新开始。

**这就是问题所在**：我们的收集器与解码器都在等 `bit0` 的 1→0；这个驱动从不产生那个边沿。

## 3. 数字

| 文件 | bit0=0 的 control 写 | 其中的 1→0 边沿 | 不同区间（新规则） | 现有导出的文件 |
|---|---|---|---|---|
| `01 Magical Sound Shower` | 7583 | 6 | **12** | 3 |
| `03 Scene Select` | 1780 | 8 | **20** | 7 |
| `05 Magical Sound Shower (Extended)` | — | 6 | 3 个边沿区间 | 3 |

被漏掉的例子（MSShower）：

```
(262288, 265216, pitch 132)    长度  2928
(269315, 272640, pitch 132)   长度  3325
(277478, 294912, pitch 144)  长度 17434   ← 连速率都不同，是另一个样本
(327920, 329984, pitch 132)   长度  2064
```

注意这些 `start` **不是 256 的整数倍**：驱动在播放中把指针挪到区间内部再写 `control`，等价于
“从中间再来一次”。这在真实硬件上是合法的（核心只比较 `addr>>16`）。

Scene Select 的 20 个区间里还包含 `pitch = 0`（不会发声）与 64 字节的碎片——它们是否要成为文件，
是下面的决策点。

## 4. 建议的改法

**A. 收集器**：把击打定义为“写 `0x86` 且 bit0=0”，不再要求 1→0；内容去重照旧（同一段字节仍然
只出一个文件）。这会把 3 → 12、7 → 20 个候选区间，去重后是真实文件数。

**B. 解码器/行**：同一处规则，重复击打要让行与 MIDI 都能看见；行的窗口改为**跟随当前寄存器**
（`start..end` 在击打时刻采样），而不是只在边沿锁存一次。

**C.（可选）过滤**：`pitch = 0`、长度小于 64 字节、以及 `end <= start` 的区间，按“不是样本”跳过
并计数——报告里已经有一个 `skippedSample` 可以说这件事。

## 5. 要你定的四件事

1. **A 的击打定义**（每次 bit0=0 的写都算）——同意？
2. **非 256 对齐的 `start`**（区间中段的重触发）是否作为独立文件导出？（推荐：是，它是驱动真的
   在播的字节；代价是同一个样本可能出现“完整版 + 中段版”两个文件）
3. **过滤条件**：`pitch = 0` 跳过（推荐）；长度 < 64 字节跳过（推荐）；其余保留。
4. **B 是否同步做**（行与 MIDI 的重复击打/窗口跟随），还是先只改导出、行留到下一轮？

## 6. 复现

```
python tools/segapcm_forensic.py "test_file/SEGAPCM/01 Magical Sound Shower.vgz" --seconds 0.2 --channel 3 --all
```

输出即第 2 节的序列；`--summary` 只打印计数。工具只读，不改 ROM、不改文件。

## 7. 已实现（v1，2026-11-12）

收集器改为“每次写 `0x86` 且 bit0=0 都算一次击打”，并在该写上锁存（`0x84/0x85` 是半个地址，
不在此处取）。内容去重与 `pitch = 0` / 长度 < 2 字节的过滤照旧。

| 文件 | v0 文件数 | v1 文件数 |
|---|---|---|
| `01 Magical Sound Shower` | 3 | **12** |
| `03 Scene Select` | 6 | **14** |
| `05 Magical Sound Shower (Extended)` | 3 | **12** |

`plugin/Tests/scripts/pcm-segapcm.txt` 钉住 12 / 14 与首名。

**v1 没做的**：解码器（行与 MIDI）仍以 1→0 为起音，重复击打看不见；寻址式重触发（起点非 256
对齐）作为独立文件导出——留待 v2 决定。
