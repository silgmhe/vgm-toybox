# RF5C164（Sega CD PCM）：一次完整探索的复盘

**日期**：2026-11-14
**结论**：**放弃**。不导出采样、不画波形，只保留音符（音名、门控、音高、电平）。
**相关文档**：设计文档 §9.5 / §9.5.1 / §9.5.2；`docs/memo/2026-11-04-the-sample-that-was-never-the-one-playing.md`；工具 `tools/rf5c_forensic.py`。

---

## 1. 这颗芯片到底是什么

跑的是 GENS 核心 `libs/libvgm/emu/cores/scd_pcm.c`（`rf5c68.c` 是 MAME 版，同语义）。VGM 文件里与它有关的只有四类东西：

| 流里的内容 | 在本曲（`01 - Palmtree Panic Zone Past`） | 语义 |
|---|---|---|
| `0x67` type `0x02` 块 | **1 个，158 720 字节** | PCM bank，交给**播放器**，不是芯片 |
| `0x67` type `0xC1` 块 | **106 个 × 514 字节** | 512 字节页 + 2 字节地址，直接写芯片 RAM |
| `0x68` 命令 | 若干 | `68 66 tt \| pos(3) \| addr(3) \| len(3)`：从 bank 取片写进 RAM（`Cmd_PcmRamWrite`） |
| `0xB1` 寄存器写 | 数万条 | `0x06` 起始页（256 B 单位）、`0x04/0x05` 循环点（**字节**地址）、`0x02/0x03` 步进、`0x08` 通道掩码、`0x07` 总开关/RAM bank |

寄存器语义（均可逐字节验证）：

- 播放头：`Addr = St_Addr << 11`，每芯片采样前进 `Step / 2048` 字节（`PCM_STEP_SHIFT`）；
- 数据格式：**符号-幅值**，`0x80` 是零，`& 0x7F` 取幅值，bit7 为符号（`0x40` 读作 −0.5）；
- `0xFF` 是回绕标记：命中即跳 `Loop_Addr`，若循环点本身是 `0xFF` 则该通道死掉；
- 速率：`Step × 32552 / 2048` 字节/秒（`clock/384` 为芯片采样率）。

**关键结构事实：RAM 只有 64 KB，而 bank 是 155 KB。** 所以样本不可能"装入即静止"——驱动必须边播边覆盖。

## 2. 五次尝试与它们各自的死因

| 版本 | 模型 | 结果 | 死因 |
|---|---|---|---|
| v0 | 按槽位切一段 RAM（`0x2000/0x4000/…` 各 8 KB） | 6 个文件 | 槽位里的内容在歌进行中被改写；长度靠门控猜 |
| v1 | 音符**释放时刻**的窗口 | 6 个文件 | 与 v0 同样的病，只是换了个时刻；0x8000 那几个槽位当时读到的就是静音 |
| v2 | **播放头**：`addr += step/2048`，遇 `0xFF` 停 | 长度变了（8192→6523 等） | 页改写被"事件驱动"地提前/推后，读到的不是真正经过的字节 |
| v3 | **逐通道录音**：静音掩码独奏 + 包络切段 | 1754 → 866 个 burst | 内容对了（用户："像单个乐器"），但一个乐器被切成几十段，且 8 次整曲渲染让加载变慢 |
| v4 | 行改成**流式滚动**（播放头 / 混音输出两种来源） | 会滚动，但"还是别通道的" | 通道归属与切片仍是推断；用户判定"效果不好，放弃" |

最终形态：**不画波形**。行保留音名、按下的键、音高与电平条。

## 3. 为什么这颗芯片比别的难

### 3.1 样本不是"某一刻内存里的一段"

这是全部困难的根源。别的采样芯片（SegaPCM、C140、K053260、MultiPCM）在 VGM 里给出 `start/end`，区间内字节**在整曲内恒定**；RF5C 的 106 个 `0xC1` 页与 `0x68` 拷贝会把新内容写进同一片地址。

于是"取一段完整波形"这个动作，在语义上就不成立：**没有一个时刻的 64 KB 等于这个音符**。

### 3.2 音符极短，且没有"一个波形"的概念

实测（掩码边沿 / `-6` 包络探针）：每通道 30 秒内 **187 段**，每段 **20–60 ms**。驱动每 60–100 ms 重触发一次。所谓"一个音符"是几十毫秒的一小片，用户听到"截了一小块"是**素材的事实**，不是导出的 bug。

### 3.3 寄存器正确 ≠ 听到正确

这一条最耗时间。核心键击探针给出 `St=8000 Loop=8000 Step=0291`，与我们的模型**逐位一致**（10 443 Hz）；而同一地址上芯片读到 `80 80 80 80`（静音），我们的映像是 `99 19 83 97`。

差异出在**RAM 的组装**：我们漏了 `0x68`（流式拷贝）、bank 起点错 8 字节（`+7` 而非 `+15`）、地址没或上 `0x07` 的 RAM bank。补上之后工具与核心逐字节一致——但那时已经用掉了三轮。

### 3.4 多实例与"静音"的假象

应用是**一轨一个播放器**，八颗芯片各自收到同一首歌的写入。曾经在一个"没分到这一轨"的实例上测能量，得到"芯片全零、引擎有声"的悖论，并被写进备忘录当成未解之谜。真相是：**九个实例，不是一颗芯片数了九次**。教训：任何跨实例的静态计数器都会重复这个错误。

## 4. 真正做对的事（可迁移）

1. **测字节，不测能量。** 十一轮失败全部来自"能量/峰值"这类间接指标：归一化基准、窗口位置、实例选择，任一错都会得到看似结论的噪声。判据换成"某时刻某通道的 `Addr` 与该处 RAM 前 8 字节"，问题立刻收敛成二选一。
2. **探针贴在核心的 `Update`/键击上，而不是外围。** 外围看到的是混合结果，无法区分"没写进去"和"写进去但没播"。
3. **一次只改一处，并给出可判定的验收。** "哈希必须不同""长度必须是 X""字节必须是 0x40"这类断言，比"听起来像了"可靠得多。
4. **per-instance 状态。** 任何 `static` 计时器/计数器在播放器架构里都会串台（备忘录 §4 已记录过一次）。
5. **写工具先于写产品代码。** `tools/rf5c_forensic.py` 与 `tools/segapcm_forensic.py` 都只读、可复现，是这两条线里唯一没有返工的部分。

## 5. 反复踩到的工程陷阱（与环境有关）

| 现象 | 后果 | 现在的做法 |
|---|---|---|
| PowerShell here-string 吞掉 `\|\|`，变成 `;` | `if (a; b)` 合法编译，整段逻辑被跳过；出现过 2 次 | 复杂改动写进 `.py` 文件再执行，或用编辑工具；条件拆成具名布尔量 |
| 参数中求值导致越界 | `orderOf(i, n, v[i].x)` 在 `i == n` 时崩溃且不输出 | 前瞻 lambda 内部先判 `index < size` |
| 用行号范围删代码 | 行号随改动漂移 | 用唯一文本锚点 + 计数校验（`count == 1` 才替换） |
| 编译警告被过滤掉 | `C4553`（表达式无效果）正是 `if (a; b)` 的信号 | 构建时保留 `warning C4xxx` 输出 |

## 6. 如果将来重开

按这个顺序，且每一级都必须先有可判定读数：

1. **先确认"谁在响"**：`VGM_RF5C_TRACE=1`（键击打印 `St/Loop/Step/RAM`）贴在有写入且通道 `Enable` 非零的实例上；
2. **再确认"读的是什么"**：`tools/rf5c_forensic.py` 的时间线（已含 `0x68`、bank `+7`、`0x07` 的 RAM bank）与核心逐字节比对；
3. **只有当"某一刻某通道读到的字节"被钉死之后**，才讨论"一个文件是什么"——是每击打一个、还是按内容聚类；
4. 任何"整曲渲染 N 次"的方案都要先量加载/导出耗时（本项目的接受线大约是 1 秒内完成打开）。

## 8. 一句话总结

这颗芯片的问题不在"算法不够巧"，而在**它没有把"一个样本"当作对象存在**：字节随播放流动，音符以几十毫秒为单位开合。为它造一个"样本列表"，等于替驱动做决定，而每一个决定都只能靠听感证伪——四次都被证伪。**及时放弃，把音符层做对，是这条线唯一收敛的答案。**
