# 那层滋滋，是重采样本身

> 2026-11-22。所有 FM 导出都有高频毛刺，**播放没有**。查了五轮，前四轮都只解决了一部分。
>
> 一句话：**播放从不重采样，导出每次都在重采样。** 我们加了一道滤波器去补偿一个不该存在的步骤。

## 一、现象，以及唯一有效的那条线索

| | 面板 | 播放 | 导出 |
|---|---|---|---|
| 有毛刺吗 | — | **没有** | **有** |

**“播放干净、导出不干净”是整轮排查里最有价值的一句话**，因为它把范围压到了两条链的**差异**上：

```
播放：核（跑 host 速率）→ 总线
导出：核（跑芯片速率）→ 量化 → 抽取到 host → 文件
```

**差异只有"核跑哪个速率"和"中间那一步"。** 我一开始没有先把这两条链摊开对比，而是直接猜原因——这是整轮耗时最长的原因。

## 二、四轮误判，每一轮都有一个真实发现

### 第一轮：以为是 8 kHz 升采样

**用户猜的方向是"面板 8 kHz 被升采样"。** 实际方向相反：**55 556 → 48 000 的降采样**，而且是无滤波抽取。

```cpp
out.push_back (values[(i * values.size ()) / count]);   // 挑点，无低通
```

**发现是真的**（24–27.8 kHz 会折叠回来），**但它只是一部分**。加了 15 抽头 Hann 窗 sinc：26 kHz 从 0.707 到 0.001。

**问题还在。**

### 第二轮：以为是归一化

**用户提议解除导出归一化。** 归一化是单一增益，不减真，**但它是放大器**——`1/peak` 会把混叠和量化噪声一起抬起来。一个渲染到 0.06 的 patch 被放大 17 倍，噪声也 17 倍。

**解除之后确实"好多了"**，因为信号不再被放大。**但毛刺还在**，只是变小了。

**这一轮的价值**：它证明了噪声是**加性的**（用户说"调小音量也依然有"），所以不是电平问题。

### 第三轮：以为是量化位深（真 bug，但不是根因）

**用户记得"有个音量寄存器没参与计算"**——那条记忆不对（TL 一直在 patch 里），**但顺着它查出了两个真 bug**：

```cpp
constexpr double kSamplesToFloat = 1.0 / 32768.0;   // 假设 16 位
```

**而 `fmopn` 并不在所有型号上累加到同一宽度：**

| 型号 | 核输出 | ÷32768 之后 |
|---|---|---|
| YM2612 | ±0x2000 | **0.250** |
| YM2203 | ±0x8000 | 0.997 |
| YM2608 | ±0x8000 | 0.997 |
| YM2610 | MAME 核 | 听感定 15 位 |

**YM2612 因此同时承受 -12 dB 和 +12 dB 的量化噪声。** 改成按 `fmOutputBits` 缩放后峰值从 `0.250` 到 `1.000`。

**YM2612 好了，YM2610 还有。**

### 第四轮：以为是滤波器不够好

**Hann 窗的第一旁瓣只有 -31 dB**，纹波落在截止频率附近——而 MAME 核恰好把能量堆在那里。换成 Blackman（-60 dB）+ 31 抽头：26 kHz 从 `0.001` 到 `0.000`。

**还是没解决。**

**这一轮说明的事**：**滤波器再好，也是在补偿一个不该发生的步骤。** 26 kHz 已经削到 0.000 了，剩下的不是混叠。

## 三、根因

**用户提出"是不是该在计算采样点时考虑重采样"，我顺着查了 libvgm 的三个候选：**

| 怀疑对象 | 结论 |
|---|---|
| `nuked` 核的分数重采样器 | 有机制（`rateratio`），**native 时归一为 1.0，不做事** |
| `fmopn` 的 `freqbase` | **不是重采样**，是调整相位增量 |
| `PlayerA` | **不额外重采样**——它让核**按 host 速率启动** |

**所以：播放那条链里没有任何人重采样。导出的链里有一个，而且是我们写的。**

**用户的原话点中了要害**：“在计算采样点的时候就应该考虑到重采样”。**更准的说法是：不该有这一步。**

## 四、解法

**导出时让核直接跑文件的速率**，与播放同构：

```cpp
// NoteRenderShape 的第四个字段
double rate = 0.0;      // 文件将写成的速率，0 = 芯片自己的速率
```

```cpp
const double wantedRate = exportQuality
                              ? (exportRate > 0.0 ? exportRate : noteRateFor (model))
                              : kVisualNoteRate;
```

**`heldAt` 于是无事可做——源和目标同一个数。滤波器保留，但不再触发（它仍守着 `sampleRateChip` 那条路）。**

**一个意外的便宜**：divisor 不用重测。**8 kHz 和 48 kHz 都是非 native**，落在 `freqbase` 的同一分支，面板已经在用的那张表直接沿用。断言加了第三档（`panel` / `chip` / `48k`）来固定这一点。

## 五、教训

### 1. “一个渠道干净、另一个不干净”，先把两条链摊开对比

**这是整轮最该先做的事。** 我先猜了原因（升采样、归一化、量化、滤波器），每次都改一个变量、每次都只解决一部分。

**如果第一步就写下：**

```
播放：核(host) → 总线
导出：核(芯片) → 量化 → 抽取 → 文件
```

**差异会立刻指向"核跑哪个速率"——那是唯一的候选。**

### 2. 当修复需要"越来越好"时，先怀疑修复的必要性

**四轮下来，滤波器的指标一路改善（0.707→0.001→0.000），而问题没有消失。** 那是一个信号：**问题不在被优化的那个量上。**

**"再加抽头会更干净"是错的**——干净的是阻带，脏的是别处。

### 3. 归因要区分"放大器"和"来源"

**归一化放大了噪声，但它不是噪声源。** 解除它让症状变轻，很容易被读成"这就是原因"。

**判据**：**如果调小音量症状随之变小（相对于信号不变），那就是加性噪声；如果只是整体变小，那是放大器。**

### 4. 用户的记忆可能有偏差，但顺着它走常能挖出真 bug

**"音量寄存器没参与计算"这条记忆不准确**（TL 一直在 patch 里），**但排查它的过程找到了 `kSamplesToFloat` 那个真 bug**——那个 bug 同时造成 -12 dB 和 +12 dB 噪声，**和用户最初的"音量偏小"完全吻合。**

### 5. 断言要能测到"用什么速率产生样本"

**`testNotePitchIsWhatWasAsked` 的三档（panel / chip / 48k）是这轮唯一能防止复发的机制**：它不检查噪声，但它检查音高在三个速率下都对——**如果有人把核改回芯片速率再抽样，第三档会红。**
