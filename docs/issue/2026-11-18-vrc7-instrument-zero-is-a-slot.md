# instrument 0 不是音色，是卡带自己填的那一格

> 六个通道、同一个驱动、同一份代码、同一个 OPLL 实例，只有第一个画出波形。
> 三者都相同，说明差异不在代码里，在**喂给代码的字节**里。
>
> 而真正的答案在一次打印之后才出现：`AR = 0`。**attack rate 为零的音色永不 attack** —— 那不是"画得不好"，
> 是"这个声音根本不存在"。

## 一、症状

`15_coffeezoneb.nsf`（VRC7）播放时，键盘页的六个 FM 行是三种状态：

| 通道 | 现象 |
|---|---|
| FM 1 | 波形正常 |
| FM 2 | 只有开头一小段，后面全空 |
| FM 3–6 | 一条直线 |

同一轮还带着一个独立问题：**一有音符，音频线程就卡顿爆音**。

## 二、定位：三轮，每轮都只拿到一个事实

### 第一轮：`state.frequency <= 0` 挡掉了静止通道

读代码时发现这个条件：

```cpp
// 当时的写法（已删除）
if (vrc7Driver == nullptr || state.frequency <= 0.0f)
{
    continue;
}
```

`state.frequency` 来自 `GetFreqHz()`，而 VRC7 的这一项由**当前寄存器**算出：

```101:102:libs/nsfplay/xgm/devices/Sound/nes_vrc7.cpp
trkinfo[trk]._freq = opll->reg[0x10+trk]+((opll->reg[0x20+trk]&1)<<8);
int blk = (opll->reg[0x20+trk]>>1)&7;
```

驱动只在**启动一个音符**时才写音高寄存器，所以静止通道的 `_freq` 是 0。

而这个条件是从 libvgm 那份代码抄来的 —— 在那里它守的是另一件事（"有没有音符在响"）。这里波形画在
`pitchForDrawing`（固定 C5），**根本不需要实际频率**。

删掉条件后：FM3–6 仍然直线。**这一轮只解决了一半。**

### 第二轮：`0x20` 的 bit 5 是 sustain 开关

`0x20` 这一个字节有四个字段：

```1307:1311:libs/nsfplay/xgm/devices/Sound/legacy/emu2413.c
ch = reg - 0x20;
set_fnumber(opll, ch, ((data & 1) << 8) + opll->reg[0x10 + ch]);
set_block(opll, ch, (data >> 1) & 7);
set_sus_flag(opll, ch, (data >> 5) & 1);   // ← bit 5
update_key_status(opll);                    // ← bit 4
```

`noteOn` 重建这个字节时只写了 f-number、block 和 key，**sustain 位被写成 0** —— percussive 模式，
包络穿过 sustain 电平继续衰减。FM2 的"只有开头"正是这个：它的音色衰减快，几十毫秒就掉到底。

改成从驱动写的原始字节里带过来之后，FM2 变长了。**FM3–6 仍然直线。**

### 第三轮：打印寄存器，而不是继续读代码

前两轮都是"读代码 → 推断 → 改 → 看结果"，每次验证的粒度都是**整张截图**。第三轮改成先拿数据：

```
[vrc7] ch0 10=46 20=33 30=25 n=39773 peak=0.0110
[vrc7] ch1 10=F4 20=38 30=05 n=39773 peak=0.0031
[vrc7] ch2 10=22 20=39 30=05 n=39773 peak=0.0000
...
```

三个事实立刻分开：**长度一样**（`n` 全相同，说明渲染都在跑）、**峰值不同**、**`0x30` 不同**。

FM1 是 `0x25`，其余是 `0x05`。`0x30` 的高 4 位是 instrument 号 —— FM1 选的是 2，其余选的是 0。

下一步问芯片自己加载了什么：

```
[drv] ch0 reg30=25 instr=2 AR=15 TL=0 SL=1
[drv] ch1 reg30=05 instr=0 AR=0  TL=0 SL=0
```

**`AR = 0`。** attack rate 为零的包络永远不上升，输出恒为零。这不是"波形画错了"，是这个 voice 从不发声。

## 三、根因：instrument 0 是卡带自己填的那一格

再打印 `0x00–0x07`：

```
custom=80801C01F0F20101
```

**驱动确实定义了 instrument 0。** 这个芯片的 16 个音色里，0 号不是 ROM 表里的一格，而是**卡带通过
`0x00–0x07` 这 8 个字节自己定义的那一格**。

而这 8 个字节**一直在 `vrc7Regs[0x00..0x07]` 里** —— `$9010`/`$9030` 会传来所有寄存器，镜像一个都没漏。

**缺的是把它们带出去。** 构造 `VoicePatch` 时我只放了三个字节：

```cpp
patch->regs.push_back ({ 0x10 + i, vrc7Regs[0x10 + i] });   // 音高
patch->regs.push_back ({ 0x20 + i, vrc7Regs[0x20 + i] });   // block / key / sustain
patch->regs.push_back ({ 0x30 + i, vrc7Regs[0x30 + i] });   // instrument / volume
```

于是驱动被告知"用 instrument 0"，而那个槽里什么都没有。

**修法是两行加一个顺序**：

```cpp
// load 里，在选 instrument 之前
for (const auto& reg : patch.regs)
    if ((reg.first & 0xFF) < 0x08)
        write ((uint8_t) (reg.first & 0xFF), (uint8_t) reg.second);
```

**顺序有讲究**：选 instrument 的那一刻芯片才会重载 patch，所以自定义字节必须先就位。

## 四、三个 bug 叠加，每个都像"修好了"

这是这次最值得记的地方。

| 轮次 | 修了什么 | 现象变化 | 是否根因 |
|---|---|---|---|
| 1 | `state.frequency` 条件 | 部分通道从"不渲染"变成"渲染但空" | 真 bug，但不是根因 |
| 2 | `0x20` 的 sustain 位 | FM2 变长 | 真 bug，但不是根因 |
| 3 | `0x00–0x07` 自定义 patch | 六个通道全部有声 | **根因** |

**每一次修复都真实改变了现象**，所以每一次都像是"成功了"。而实际是三个独立缺陷叠在同一张截图上。

判据本可以更早出现：**第一次修完就该问"为什么 FM3–6 一点变化都没有"**——它们和 FM2 走的是同一条代码路径，
如果条件判断是唯一原因，它们应该和 FM2 一起好转。**没有同步变化，说明还有别的层。**

## 五、为什么测试没抓住

`vgm_nsf_test` 只解析 NSF 头，不播放。`vgm_opn_test` 的波形断言覆盖的是 **libvgm 的 OPN**，不是 VRC7。

而这一类 bug 恰好都有一个共同点：**`noteWaveform` 非空、长度正确、峰值是 0**。

"有数据"和"数据有内容"是两个命题 —— 这个项目已经为它付过一次代价（FM 波形曾在屏幕上是一条直线，
而 `noteWaveform->size()` 大于 100）。这次的形态更隐蔽：**有内容，但内容是静音**。

## 六、修好之后立了什么护栏

**1. `vgm_nsf_probe --vrc7`**

一个可以直接问"六个通道现在是什么状态"的入口，输出频率与波形长度：

```
FM 1     freq=    61.8  noteWave=39773
FM 2     freq=   370.2  noteWave=39773
...
```

定位期间还临时加过两行打印（`vrc7Regs` 的三个字节 + OPLL 的 `AR/TL`）。**那两行是这次真正的转折点，
它们不该只活在一次调试里。**

**2. `noteWaveformRate` 从驱动取**

```cpp
state.noteWaveformRate = (float) vrc7Driver->rate ();
```

原来是 `noteRateFor (vrc7)` —— 两个数字今天相等，但文件声明的采样率和样本实际的采样率是同一件事的
两面，让产生样本的那一方回答，是唯一不会分叉的写法。

**3. 缓存键只在音色变化时移动**

`vrc7Version` 最初被每一次寄存器写入抬高，而驱动每帧都写音高和键控 —— 版本号变成了时钟，四秒波形
每帧重建一次，在音频线程上。现在只有 `0x00–0x07` 和 `0x30` 的高 4 位（instrument）会移动它。

## 七、下次的检查清单

1. **判断"没声音"时，先打印包络的 AR/TL，不要读代码。** `AR = 0` 是一个能立刻排除整类假设的数字。
2. **修完一处，先确认"其他同样症状的对象是否一起好转"。** 没有同步变化，就是还有一层。
3. **`VoicePatch` 要带走哪些字节**：判断依据不是"我以为重要的"，而是**驱动写过、且芯片会读的**。这次的
   `0x00–0x07` 一直在镜像里，只是没被带走。
4. **寄存器镜像是便宜的**：它替我保留了当时没想到的字节。缺的从来不是镜像，是"带出去"的那一步。
5. **缓存键的两个方向都危险**：太宽（每次写都变）会卡顿，太窄（漏掉真正改波形的字段）会永远显示旧值。

## 八、留下的问题

**渲染仍在音频线程。** `captureState` 里跑 6 × 39773 个样本的 OPLL，一次约几十毫秒。缓存命中后不再重算，
但第一个音符仍会掉一帧。

这一条按用户决定单独做重构（把波形渲染移出音频线程），不在本次修复范围内。记账在此，避免它被当成
"已经解决了"。
