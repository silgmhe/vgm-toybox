# 六个波形，39 毫秒，一帧

> 问题：NSF 的 FM 可视化会让音频线程卡顿爆音，而 VGM 的 FM 不会。
>
> 答案：两边都在音频线程渲染，差别不在"谁更小心"，在**门槛的宽窄**和**缓存键的写法**。
>
> 而真正的转折点，是承认自己算不出来——去测。

## 一、症状

`15_coffeezoneb.nsf`（VRC7）播放时，键盘页的六个 FM 行正常显示，但音频线程周期性掉帧。

同一轮里还有一条对照：**VGM 的 FM 可视化不卡**。

这条对照是最有价值的线索。它说明"在音频线程渲染波形"这件事本身不是问题——**VGM 也这么干**。

## 二、之前的进度：记过账，但没记到点子上

`docs/issue/2026-11-18-vrc7-instrument-zero-is-a-slot.md` 第八节写着：

> **渲染仍在音频线程。** `captureState` 里跑 6 × 39773 个样本的 OPLL，一次约几十毫秒。缓存命中后
> 不再重算，但第一个音符仍会掉一帧。

这一条**已经定位到了"在音频线程"和"约几十毫秒"**，也明确记账"按用户决定单独做重构"。

**但它没有区分两种情形**：

| 情形 | 频率 | 症状 |
|---|---|---|
| 冷启动、换音色 | 一次 | 掉一帧 |
| 缓存键失效太频繁 | 每周几秒一次 | **周期性爆音** |

而这正是用户现在报的症状——**是第二种**。所以这份记账虽然准确，却把排查引向了"要不要搬走线程"这个更贵的问题。

## 三、两边其实走同一条路

```
PlaybackEngine::processBlock                    ← 音频线程
  └─ if (stateCaptureWanted)
       trackPlayers[0]->captureState(snapshot)  ← 每块一次
```

| | VGM | NSF |
|---|---|---|
| 实现 | `LibvgmTrackPlayer::captureState` | `NsfPlayer::captureState` |
| 调用者 | 同一个 | 同一个 |
| 线程 | 音频 | 音频 |
| 单次渲染 | OPN 核心 | OPLL 核心，**5.6–6.0 ms** |
| 触发门槛 | `state.frequency > 0` | **无** |

**所以"VGM 不卡"不是因为它在别处渲染**，而是因为下面两处。

## 四、两处不对称

### 4.1 门槛：VGM 只画正在响的，NSF 全都画

```cpp
// LibvgmTrackPlayer::captureState
if (state.voicePatch != nullptr && state.frequency > 0.0f && voiceDriver != nullptr)
```

VGM 只在通道**当前有音高**时才渲染波形。静音行画的是合成示意。

NSF 侧这个门槛**被特意删掉了**——因为它在错误的场合挡掉了静止通道：

> `state.frequency` 来自 `GetFreqHz()`，而驱动只在**启动一个音符**时才写音高寄存器，所以静止通道
> 的 `_freq` 是 0。而这个条件是从 libvgm 那份代码抄来的 —— 在那里它守的是另一件事。
> 删掉条件后：FM3–6 仍然直线。

**这是一次正确的取舍**：波形画在固定音高（`pitchForDrawing`），不需要实际频率。

**代价是固定 6 个全渲染**，不管有没有音。

### 4.2 缓存键：一支比较了旧值，另一支没有

```cpp
if (vrc7Latch < 0x08)
{
    ++vrc7Version;                                  // ← 无条件
}
else if (vrc7Latch >= 0x30 && vrc7Latch <= 0x38
         && (vrc7Regs[vrc7Latch] & 0xF0) != ((uint8_t) value & 0xF0))
{
    ++vrc7Version;                                  // ← 比较了
}
```

注释本身写得很好：

> **Only a change of patch bumps the version.** The pitch and key registers are written every frame
> by a driver with a vibrato... Counting either would rebuild the waveform sixty times a second on
> the audio thread - which is exactly the stutter this line exists to prevent.

**作者想到了这个失效模式，并且防住了 `0x10`/`0x20`/`0x30` 低半字节——但漏了 `0x00–0x07` 的"值没变"这一层。**

## 五、先量：我的假设错了一半

我读到这里时的判断是：

> 如果驱动在每帧都把这八个字节重写一遍，`vrc7Version` 就**每块 +1**，于是 6 × 39773 样本的
> OPLL 渲染**每块都重跑一次**。

**这个判断一半是错的。** 实测（每 100 块打印一次）：

```
[cost] captures=100  renders=12  avg=5.57ms  total=67ms
[cost] captures=100  renders=6   avg=5.97ms  total=36ms
[cost] captures=100  renders=0   avg=0.00ms  total=0ms
[cost] captures=100  renders=6   avg=5.98ms  total=36ms

400 blocks: 9.29 s of audio in 0.28 s wall (3.0% of real time)
```

| 我说的 | 实测 |
|---|---|
| 每次重建约 6 ms | ✅ 5.6–6.0 ms |
| **每块都在重建** | ❌ 每 100 块（2.3 秒）6–12 次 |

**缓存机制一直在工作，是键太宽。** 如果真是每块重建，400 块要 14 秒，实测 0.28 秒。

## 六、修复 A：让"写同样的值"不算改动

```diff
  if (vrc7Latch < 0x08)
  {
-     ++vrc7Version;
+     if (vrc7Regs[vrc7Latch] != (uint8_t) value)
+         ++vrc7Version;
  }
```

三行。周期性重渲染消失，稳态段回到纯音频渲染开销。

## 七、修复 C：一次只建一个

A 之后仍有峰值。**这个峰值和"频率"是两件事**，A 管不到。

实测对照（改一个常量就能来回切）：

```
不限预算   worst block 107: 39.61 ms      ← 超过 23.2 ms 的块时长
预算 = 1   worst block   3:  8.74 ms      ← 远低于
```

**39.61 ms 对应 1.7 个音频块，必掉帧。**

修法是给 `captureState` 一个每块预算：

```cpp
// NsfPlayer.h
mutable int vrc7WaveBudget = 0;

// captureState，VRC7 段开头
vrc7WaveBudget = 1;

// 循环内
const bool stale = cached.samples == nullptr || cached.version != vrc7Version || ...;

if (stale && vrc7WaveBudget > 0)
{
    --vrc7WaveBudget;
    ...渲染...
    cached.version = vrc7Version;     // 只在渲染后重新键住
}
```

**队列是隐式的**：条目**只在渲染后才更新键**，所以没轮到的通道下一块仍然报 stale，自然排队。不需要 dirty 数组，也不需要轮转指针。

## 八、教训

### 8.1 "同一个函数名"不是"同一条路径"

两边都叫 `captureState`，都由 `processBlock` 每块调用，都在音频线程。**结构对称，行为不对称。**

对称的部分让人以为"同类问题，同样处理"；不对称的部分才是答案。

**看到"两边都这样"时，下一步该问的是"两边的门槛一样吗"。**

### 8.2 推断的数字必须测——这是第三次

同一类错误，在这个项目里已经出现过：

| 轮次 | 我的推断 | 实测 | 谁纠正的 |
|---|---|---|---|
| 2026-11-18 | "AR 可能不为 0" | `AR = 0` | 打印 |
| 2026-11-19 | "扫描要几十秒" | **2.67 秒** | 用户："扫描并不会卡住啊" |
| **2026-11-20** | **"每块都重建"** | **每 2.3 秒一次** | 打印 |

**三次都是我把"从代码推出来的"说成了"就是"。**

前两次之后写进过检查清单，但它没有起作用——因为**检查清单是给自己看的，而"我觉得我推对了"是一种很强的感觉**。

**唯一可靠的纠正方式不是自律，是让数字先出现。** 所以这一轮的第一件事应该是加打印，而不是读代码。

### 8.3 总量掩盖峰值

C 做完之后，总耗时**一点没变**：

```
C 之前  0.24 s
C 之后  0.24 s
```

**因为工作量守恒**——同样 6 次渲染，只是分到 6 块里。

我差点据此认为 C 没生效。**是"最坏单块"才看得出 39.61 → 8.74。**

**要衡量"卡不卡"，指标必须是峰值，不是总量。** 一个 40 ms 的尖峰和一个 40 ms 的均匀分布，总量相同，听感完全不同。

### 8.4 一个常量的对照实验

`vrc7WaveBudget = 99` 和 `= 1` 之间的差别，就是 39.61 ms 和 8.74 ms。

**这种"改一行就能来回切"的证据，比任何推理都强。** 而且它留下了复现方法——将来有人说"我这边还是卡"，可以让他把自己的曲子跑一遍这两个值。

### 8.5 缓存键的"太宽"有两种

`2026-11-18` 的检查清单第 5 条写着：

> 缓存键的两个方向都危险：太宽（每次写都变）会卡顿，太窄（漏掉真正改波形的字段）会永远显示旧值。

**这次是"太宽"，但不是字段选错，而是比较方式错了**——字段选得对（`0x00–0x07` 确实改变波形），但**没有比较值**，于是"重发同一个字节"被当成了"改波形"。

**"太宽"有两种形态**：

| 形态 | 表现 |
|---|---|
| 字段选错 | 把不该算的算进去（音量、音高） |
| **比较方式错** | 该比的字段没比值（无条件 +1） |

第二种更隐蔽，因为**字段列表看起来是对的**。

### 8.6 频率和峰值是两个维度

| 修复 | 解决 | 手段 |
|---|---|---|
| A | **多久发生一次** | 让键只在真的变化时才变 |
| C | **单次有多贵** | 把一次拆成六次 |

**A 再彻底也不能让"真换音色"免费；C 再有效也不能阻止"每 2 秒换一次音色"。**

两个都要，但它们解决的是不同的问题——所以 A 做完后不能宣布收工。

## 九、下次的检查清单

1. **先问"两边有什么不一样"，再问"哪边写得不对"。** VGM 不卡这条线索，价值在于它排除了"音频线程渲染"这个整类假设。
2. **先加打印，再读代码。** 一个 `renders=N` 的数字，比半小时的控制流分析可靠。
3. **衡量卡顿用峰值，不用总量。** 工作量守恒时，总量恒等于常数。
4. **想做 A/B 就找一个常量。** 能用一个赋值切换的两个版本，是最好的证据。
5. **缓存键失效，先看它怎么写的，再看它包含什么。** 无条件 `++version` 和"比较后 `++version`"看起来只差一行。
6. **"已经记账"不等于"已经定位到点上"。** `2026-11-18` 的记录准确，但没有区分冷启动和周期性——**记账时要把"多久一次"写进去**。

## 十、留下的

**首次打开键盘页仍有一次 8.74 ms**，那六个波形确实要建。低于一个音频块，不掉帧。

**拖动 FM sustain/release 滑块时，六个波形在约 140 ms 内逐个跟上。** 这是 C 的代价：换来了峰值，让出了即时性。排队期间每行显示它**已有的**波形，不会空白。

**如果那 140 ms 被感知**，`vrc7WaveBudget` 改成 2——峰值 12 ms（仍低于 23.2），延迟减半。

**没有做的事**：把渲染移出音频线程。它需要第二个 OPLL 实例、一个工作线程、结果的双缓冲交换，以及 player 析构时的线程收尾。**在峰值已经低于块时长之后，这笔钱不该花**——先记在这里，等有人真的听见问题再说。
