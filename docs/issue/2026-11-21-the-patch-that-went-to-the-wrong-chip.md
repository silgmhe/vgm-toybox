# 交给错芯片的那份音色

> 六个 FM 通道，同一段渲染代码，只有一行画直线。
>
> 这个"只有"是整件事里最重要的一个词，而我用了六轮才把它当回事。

## 一、症状

`06 BGM 2 (Round 2, 5).vgz`（YM2203），键盘页的 FM 行：

- **Ch 2、Ch 3**：有波形，形状不同，正常
- **Ch 1**：一条直线

听感上三个通道都饱满。

## 二、第一句话就读错了

用户第一次描述是：

> Ch2 是对的，Ch1 和 Ch3 之前都是有波形的，但是波形不正确

我读成了"**两个**通道有问题"。于是去查渲染路径——因为两个坏、一个对，还可能是共用代码里的某个分支。

后面几轮里，用户又说了两次"Ch1 是直线"，直到第三次：

> YM2203 **只有 Ch1** 没有可视化数据，总是一条直线。

**"只有一个通道坏"，这一句话能把问题砍掉九成。**

三个通道共用：渲染函数、`driver`、`hz`、`sustain`/`release`、设置、缓存结构。

**通道独立的只有一样：patch 的字节。**

**一个坏两个好，那渲染一定不是原因。**

## 三、六轮弯路

### 第 1 轮：`frequency > 0` 门槛

```cpp
if (state.voicePatch != nullptr && state.frequency > 0.0f && voiceDriver != nullptr)
```

`frequency` 来自 `GetFreqHz()`，只在 key-on 时被写，所以静止通道报 0，跳过整段渲染，退回单周期。

**这是真 bug**，NSF 侧早就删过同一个条件。删掉之后 `wave=1` 了——**但 `peak=0`**。

**修了，症状没变。**

### 第 2 轮：`core->reset()`

一个核心服务所有行，前一个通道还在 key-on 时后一个 patch 就到了。用两个通道的测试证明了：

```
没有 reset   440.8 Hz   （前一个通道盖过本通道）
有 reset     217.0 Hz
```

**这是真 bug**，也修好了。**对这个症状无效。**

### 第 3 轮：`divisor = 288`

`noteOn` 对所有型号用 144 算 f-number，而 OPNA/OPNB 的核心用 `clock / 288`。

```
改之前   217.0 Hz   （要 440，差一个八度）
改之后   437.4 Hz
```

**又是真 bug，又修好了。对这个症状还是无效。**

### 第 4 轮：两个解码器实例（结论是错的）

打印出了两个不同地址：

```
[cp]  this=00000047E53FE738   ← 有数据
[dec] this=0000021BE2053410   ← captureState 读的
```

我据此判断"数据没到渲染这一侧"，并提出要把扫描的结果搬给播放的解码器。

**这个判断是错的。** `[cp]` 是 `MidiSequenceBuilder` 在扫描时用的临时解码器，`[dec]` 是播放持久的那个——**两者不同是设计如此**，`VgmReplayer` 会把写入重放到 `[dec]` 上。

**地址不同不等于数据缺失。** 我拿"两个对象不同"当成了"第二个没有数据"，而没有去问第二个对象**它自己的**状态。

### 第 5 轮：既然数据有，就看渲染

真正的问题在这一步才被问出来：**patch 里有内容吗，渲染出来是什么？**

```
[fm] ch=0 wave=88889 peak=0.0000 tl=21,41,57,13 alg=3
[fm] ch=1 wave=88889 peak=0.0000 tl=21,41,57,13 alg=3
[fm] ch=2 wave=88889 peak=0.0000 tl=21,41,57,13 alg=3
```

三个 `peak` 都是 0，但 **TL 和 ALG 是正常值**。

**数据在，渲染不出声。** 这把范围从"数据管道"移到了"渲染用的那个核心"。

### 第 6 轮：型号

```cpp
out.model = impl->variant == Variant::ym2612 ? ChipModel::ym2612
          : impl->variant == Variant::ym2608 ? ChipModel::ym2608
                                             : ChipModel::ym2610;   // ← ym2203 在这里
```

**YM2203 的 patch 被标成了 OPNB。**

`OpnVoiceDriver` 按 `patch.model` 启动核心：

```cpp
config.clock = clockFor (model);
ready = SndEmu_Start (deviceIdFor (model), ...);
```

于是三个通道的 patch 都被送进 **`DEVID_YM2610` 的核心**——六通道、两个端口、`0x28` 带 bank 位——而 patch 是三通道、一个端口的布局。**key-on 落不到任何一个通道上。**

```
改之前   ch=0/1/2  peak=0.0000  tl=21,41,57,13  alg=3
改之后   ch=0/1/2  peak=1.0000  tl=21,41,57,13  alg=3
```

**TL 和 ALG 一个字节都没变。同一个 patch，换对的核就出声。**

## 四、修复

| 文件 | 改动 |
|---|---|
| `VoicePatch.h` | 新增 `ChipModel::ym2203`；`noteRateFor` 给 `3993600 / 144` |
| `OpnDecoder.cpp` | `Variant::ym2203` 报自己的型号，不再兜底成 2610 |
| `OpnVoiceDriver.cpp` | `deviceIdFor` 给 `DEVID_YM2203`；`clockFor` 给 3.99 MHz |

**除数仍用 144**——288 是 OPNA/OPNB 的事，OPN 不是。

**七行。**

## 五、教训

### 5.1 先数"几个坏"

**"一个坏两个好"和"两个坏一个对"，是两条不同的排查路径。**

- 全部坏 → 共用路径（渲染、驱动、设置）
- 部分坏 → 通道独立的数据

我读错了第一次描述，之后每一轮都在"两个坏"的框架里找。

**症状里的数量词，比形容词重要。**

### 5.2 "有数据"和"数据有内容"是两件事

`wave=88889` 说明渲染跑完了，`peak=0.0000` 说明产出是静音。

**我只看到 `wave` 就以为数据到了**，直到打印出 `peak` 才分清。

这个项目已经为同一件事付过代价——`2026-11-18` 那份文档里写着：

> "有数据"和"数据有内容"是两个命题 —— 这个项目已经为它付过一次代价（FM 波形曾在屏幕上是一条直线，而 `noteWaveform->size()` 大于 100）。

**第二次犯。**

**量一下峰值，一行代码。**

### 5.3 提过但没做的方案，下一轮先做

`ym2203` 的型号映射，我在第 2 轮就写进了"建议顺序"，标为"最小，约 8 行"。之后三轮我都看到了它，每次都判断"不确定它是主因"，然后去查别的。

**它一直是主因。**

**为什么一直被跳过**：因为我把它归类成"一致性修复"（型号报错了，但看起来不影响功能），而把"卡顿""串音"当成"真 bug"。**优先级排错了。**

**规则**：一个"知道有错、但不确定影响"的地方，应该**先花 10 分钟做掉**，而不是留着它一边猜别处。**修完如果症状还在，那也排除了一项。**

### 5.4 修了症状不变，就该质疑"我在修什么"

四轮里每一次修复都是真的：

| 轮 | 修了什么 | 真的坏吗 | 对这个症状有效 |
|---|---|---|---|
| 1 | `frequency > 0` 门槛 | 是 | 否 |
| 2 | `core->reset()` | 是 | 否 |
| 3 | `divisor = 288` | 是 | 否 |

**每一次都改善了别的东西，所以每一次都像"前进了一步"。**

这就是最难的地方：**"修了但没效果"和"修得不够"看起来一样。** 区别在于——**如果修复没有改变症状的形状，那它可能根本不在同一条路径上。**

**判据**：修完之后，**症状有没有任何变化**（哪怕更糟）？没有 → 换路径，不要在这条上再找一层。

### 5.5 地址不同不等于数据缺失

第 4 轮我看到两个解码器地址不同，就断定"数据没到"。

**实际上**：扫描用一个临时解码器，播放用一个持久的，**这是设计**。

**教训**：看到一个"意外"的差异时，先问"这个差异是不是正常的"。**我把它当成了异常，而它是我没读过的设计。**

### 5.6 "看起来只是分类"的东西，决定用哪个核心

`ChipModel` 的职责看起来像"给 patch 贴个标签，方便命名"。**它其实是 `SndEmu_Start` 的参数**——**标签就是路由**。

同一个 patch，标 `ym2610` 就进 OPNB 核心，标 `ym2203` 就进 OPN 核心。**布局不同，一个出声一个静音。**

**凡是"这个枚举值拿去查一张表"的地方，它就不只是分类。**

## 六、下次的检查清单

1. **症状里的数量词先落定**：几个通道？全部还是部分？**部分坏 = 数据问题，全部坏 = 路径问题。**
2. **第一件事是量峰值，不是看长度。** `wave.size() > 0` 只证明跑完了。
3. **"提过但没做"的项，排到最前面。** 它悬着的时间越长，越可能是答案。
4. **修完症状形状没变 → 换路径**，别在同一条上找第三层。
5. **看到意外的结构差异，先假设它是设计。** 先读，再下结论。
6. **枚举值查表的，都是路由。**

## 七、留下的

**YM2203 现在有自己的 `ChipModel`**，但 `OpnDecoder::Variant` 还有 `ym2610b` 同样被兜底成 `ym2610`——**同一个形状的隐患，只是还没遇到出声问题的曲子。**

**OPM（YM2151）和 OPL 家族的 `ChipModel` 值仍然闲置**：`deviceIdFor` 和 `clockFor` 里写着它们，但没有任何解码器产出。**如果将来有人只补了枚举值，它们会走进正确的核心、用错的寄存器写入**——这正是 `2026-11-18` 那份文档警告过的形态（"补了 `ChipModel` 的值，它就会悄悄错"）。

**这两条都不该只记账。** 第一条是七八行的事，第二条需要先有 `OplDecoder::capturePatch`。
