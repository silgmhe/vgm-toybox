# 一颗芯片的问题，不是一类芯片的规则

> 2026-11-23。YM3812 的导出调好之后，我把结论推广给了 YM2151 和 YM2413。
> 结果是连续的返工：滋滋回归、电平两次改错、一个音色被误诊，最后全部回退到 `0e7abc5`。
>
> **这篇记的是推广这一步错在哪，不是那几个数字。**

## 一、发生了什么

| 步 | 我做的 | 结果 |
|---|---|---|
| 1 | OPL2 导出偏大、略闷 → 归纳出"**导出 = 播放**" | 对 OPL2 成立 |
| 2 | 把这条规则应用到 YM2151 与 YM2413：位宽改 16、速率改文件速率 | **YM2151 滋滋回归** |
| 3 | 恢复 YM2151 的 native + FIR | 滋滋好了，**电平掉 4 dB** |
| 4 | 补 +4 dB 路径增益 | 用户**要求回退** |

**四次提交，三次都在修补前一次引入的问题。**

## 二、四个具体的错

### 1. 把一颗芯片的四个观察，推广成三颗芯片的规则

OPL2 的现象（偏大 2–3 倍、FIR 让高频暗 1.15 dB）**只对 OPL2 成立**。它们的根源是"这颗核的幅度尺度"和"这颗核的自带插值"，**不是一条普适原理**。

**我当时说的是"按听觉为准"，听起来像原则；但我落地的是一行对三个型号生效的分支。**

### 2. 用算术去改一个已经被耳朵校准过的值

`ym2151 = 14`、`ym2413 = 12` 都是**用户听过并确认**的。我用"libvgm 是 int16、单声部占 1/9"的算术把它们改成 16。

**算术没错，错的是我把"算出来的应该"当成"比听过的实际"更有权威。** 之后 YM2413 被量出"小 6 dB"、YM2151 被量出"小 4 dB"——正是这个替换的代价。

### 3. 删掉了文档里已经写明的结论

`docs/issue/2026-11-22-the-opm-resamples-itself.md` 第 70 行写着：

> **播放为什么干净**：`PlayerA` 让核按 native 跑，然后用**它自己的、带滤波的重采样器**转换到 host。

**我上一轮把这条特例删了，而删它的理由正是"要跟播放一致"——那句话在同一份文档里。**

**改动之前先搜文档**，这次搜一次就能避免第 2、3 步。

### 4. 一次动三个变量

那一轮同时改了：**位宽**、**速率路径**、**去直流**。出问题时无法归因，只能一个个试回来，于是产生了 15 位、+4 dB 这样的补偿。

**一次只改一颗芯片、一个变量**，出问题才能定位。

## 三、教训（下次直接用）

| # | 规则 |
|---|---|
| 1 | **一次只改一颗芯片。** 改完用耳朵 A/B，再动下一颗。 |
| 2 | **耳朵校准过的数值，不因为算术更漂亮而改。** 算术与耳朵冲突时，先问"我的参照系和他的是不是同一个"。 |
| 3 | **"导出 = 播放"不是一条规则，是一张按核的表。** `PlayerA` 对每个核做的事不同：有的 native + 滤波，有的直接按请求速率生成。 |
| 4 | **改之前先搜 `docs/issue`**：同一颗芯片的问题可能已经修过一次。这次是第二次踩 OPM。 |
| 5 | **连续两次"补偿"就是方向错了。** 出现第二个补偿（15 位之后又 +4 dB），应当回退到上一个用户验证过的提交，而不是继续加。 |

## 四、回退后的状态（`0e7abc5`）

| 芯片 | 位宽 | 速率路径 | 谁验证过 |
|---|---|---|---|
| YM2151 | **14** | native + FIR | **用户的耳朵**（滋滋那次） |
| YM2413 | **12** | native + FIR | **用户的耳朵**（第二轮） |
| YM3812 | **16** | 文件速率 | **用户的耳朵**（"和播放一致"） |

**三颗芯片现在走三条不同的路，这不是不一致——这是三次独立测量的结果。**

**若将来有人想"统一"它们，请先读这一页。**

## 五、一句话

> **一颗芯片的耳朵结论，是那颗芯片的数据，不是一类芯片的公理。**
> 我这次不是算错了，是把"一个观察"升级成了"一条法律"。
