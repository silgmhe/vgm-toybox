# 卡顿就是错过截止时间

> 2026-11-23。用户说"播放有轻微的卡顿感"。**这是耳朵的结论，不是程序的结论。**
>
> 这篇是把"顿一下"翻译成**可测量的判据**，以及把探针塞在哪里、怎么读的方法论。
> 音频/UI 线程的阻塞类问题会反复出现，值得有一份固定的做法。

## 一、先分清：卡顿有两种，修法完全不同

| | 谁错过了截止时间 | 现象 | 硬指标 |
|---|---|---|---|
| **A. 音频线程** | `audioDeviceIOCallback` 没在**缓冲区周期**内填完 | 爆音、断音、滋啦声 | **xrun / underrun 计数** |
| **B. 消息线程** | 绘制没在**帧预算**内完成 | 画面跳、滚动顿、行不刷新 | **单帧耗时** |

**两者可以同时发生，也可以只发生一个。** 本例是 **B**：音频一直没炸，是键盘页在
`captureState` 里一次性渲染了 14 行波形，**单帧 250 ms**。

## 二、把"顿一下"写成数字

### 截止时间的定义

- **音频**：`T_audio = bufferFrames / sampleRate`。48 kHz、256 帧 → **5.33 ms**。
  一次 callback 的耗时 `D` 超过它 → **一次 xrun**。
- **消息线程**：`T_ui = 1 / 60 = 16.7 ms`（或 120 Hz 的 8.3 ms）。`D` 超过它 → **掉一帧**。

**利用率** `U = D / T`。稳态要求 `U < 0.8`（留 20% 给抖动和系统调度），而不是 `U < 1.0`——
`U` 贴着 1.0 的系统在负载稍变时就会开始丢。

### 感知阈值（工程经验值，不是数学定理）

| 单次阻塞 | 音频上的感知 | 画面上的感知 |
|---|---|---|
| **< 1 ms** | 多数情况不可闻 | 不可见 |
| **1–5 ms** | 偶发"咔"（一次样本缺口） | 1 帧，几乎不可见 |
| **5–20 ms** | 明显爆音 | 掉 1 帧，快速滚动时可见 |
| **20–100 ms** | 断一下 | 明显一跳 |
| **> 100 ms** | 停顿 | 用户会说"卡住了" |

**本例的实测是 250 ms/帧**，远超"说卡住了"的门槛；用户的原话是"轻微的卡顿感"，
**说明主观描述的量级不可靠**——所以必须测。

### 周期性 vs 随机

拿到"每次工作的耗时序列"后，看**间隔分布**：

- **周期性尖峰** → 定时任务（每帧渲染、每 N 帧刷新）
- **随机尖峰** → 分配、锁争用、文件/网络 IO、日志
- **单调增长** → 泄漏或缓存未命中恶化

## 三、怎么定位：先分叉，再缩小

**第 1 步 · 分叉**

| 观察 | 说明 |
|---|---|
| 关掉面板就正常 | 消息线程（B） |
| 关掉面板仍爆音 | 音频线程（A） |
| 只在某个芯片/某首曲子 | 该芯片的渲染成本（本例） |
| 只在高负载时 | 预算不足，不是单点 bug |

**第 2 步 · 二分**：逐个关闭可疑功能（面板、拖拽预览、导出线程），看症状是否消失。
**这一步不需要改代码**，先用开关把范围砍到一半。

**第 3 步 · 计数**：只对**剩下的那一半**塞探针。

## 四、探针怎么塞（音频/UI 通用三条铁律）

### 1. 只在边界计时，不在内部计时

计时点放在"进入某个函数 / 退出该函数"，不要在循环里 `now()` 几千次——
**探针本身的开销会改变被测量的东西**（观察者效应）。

### 2. 音频线程上不做任何可能阻塞的事

`printf` / `fprintf` / 字符串拼接 / `new` / 加锁 —— 都可能**自己造成一次 xrun**。

- 音频线程只做：`std::atomic` 累加（`worstUs`、`lateCount`、`count`）
- 打印交给**消息线程**：每 60 帧读一次原子量并输出

### 3. 报 `max / p99 / count`，不报平均

**均值会抹平尖峰，而尖峰才是用户听见的东西。** 一个 250 ms 的卡顿放在 400 帧里，
平均只增加 0.6 ms——**完全看不见**。

## 五、具体模板

### A. 音频线程（不能打印）

```cpp
// 音频回调里
const auto t0 = juce::Time::getMillisecondCounterHiRes ();
renderAudio (buffer, frames);
const auto dt = juce::Time::getMillisecondCounterHiRes () - t0;

// 只做原子累加
worstCallbackMs.store (std::max (worstCallbackMs.load (), dt), std::memory_order_relaxed);
if (dt > bufferPeriodMs * 0.8) { ++lateCount; }

// 消息线程每 60 帧打印一次
std::fprintf (stderr, "[audio] count %d  worst %.2f ms  late %d  period %.2f ms\n",
              count, worstCallbackMs.load (), lateCount.load (), bufferPeriodMs);
```

**验收判据**：`lateCount == 0` 且 `worstCallbackMs < 0.8 × bufferPeriodMs`。

### B. 消息线程（可以打印，但要按帧汇总）

```cpp
// 每帧进入时
const auto frameStart = juce::Time::getMillisecondCounterHiRes ();

// 可疑调用前后
const auto t0 = juce::Time::getMillisecondCounterHiRes ();
doExpensiveThing ();
const auto dt = juce::Time::getMillisecondCounterHiRes () - t0;
totalMs += dt;
++workCount;                    // 本帧做了几次

// 每帧结束时
std::fprintf (stderr, "[frame] %d  work %d  total %.2f ms\n", frame, workCount, totalMs);
```

**关键不是"总时间"，而是"每帧做了几次"**——本例第一帧 14 次 × 26 ms，
这个"次数"直接把问题指到了缓存失效策略上。

**验收判据**：`max frame ms < 16.7`，`p99 < 8`，**连续超限帧数 == 0**。

## 六、本例的完整链路（数据 → 结论 → 修法 → 复测）

| 步 | 得到的事实 | 推出的结论 |
|---|---|---|
| 1 | OPL2 曲：每行 **0.4 ms**；OPLL 曲：每行 **25–31 ms** | 不是通用问题，是**某颗核**的问题 |
| 2 | 同一帧渲染 **14 行**（9 旋律 + 5 鼓） | 一帧 **250 ms**，远超 16.7 ms |
| 3 | 后续帧又各 12、12、5 行 | **不是一次性**，是每发一批音就再来一次 |
| 4 | 缓存键是 patch 指针，`patchVersion` 每次寄存器写入 +1 | **多行同时失效**是触发条件 |
| 5 | 修法：每 33 ms 最多渲一行 + OPLL 窗口 1.5 s → 0.5 s | 单帧最坏 ~9 ms |
| 6 | 复测：400 帧里 **12 次渲染**，一次一个 | 达标 |

**注意第 1 步的价值**：它把"整个播放引擎都慢"排除掉了，只用一次对照实验
（换一首不同芯片的曲子）。**先找对照组，再决定要不要读代码。**

## 七、反模式（这次差点踩的）

| 反模式 | 后果 |
|---|---|
| 先在 `render` 里加 `printf` | 自己制造 xrun，测到的是探针 |
| 只看平均耗时 | 250 ms 的尖峰被平均成 0.6 ms，看不见 |
| 只测一次正常运行 | 卡顿发生在"多音齐发"的瞬间，稳态测不出来 |
| 用"感觉更顺了"验收 | 主观量级不可靠（本例用户说"轻微"，实际 250 ms） |
| 先改代码再测 | 会同时动多个变量，最后无法归因（这个月在别处已经踩过） |

## 八、可直接抄用的验收清单

```
音频线程
  [ ] lateCount == 0（超过 80% 周期的回调数）
  [ ] worstCallbackMs < 0.8 × bufferPeriodMs
  [ ] 音频线程内无 printf / new / 加锁
  [ ] 测试覆盖"歌曲开头、多音齐发、seek 之后"三个最坏点

消息线程
  [ ] max frame ms < 16.7（60 Hz）
  [ ] p99 frame ms < 8
  [ ] 连续超限帧数 == 0
  [ ] 每帧的"重活次数"有显式上限（不是"希望它别太多"）

测量口径
  [ ] 报 max / p99 / count，不报平均
  [ ] 有对照组（另一颗芯片 / 关掉功能 / 另一首曲子）
  [ ] 探针本身的开销 < 被测量值的 5%
```

## 九、一句话

> **"卡"不是一种感觉，是一次截止时间被错过。**
> 先问"哪个线程、错过了哪个截止时间、错过了多久"，再问"为什么"。
> 没有这三个数，任何优化都只是在赌。
