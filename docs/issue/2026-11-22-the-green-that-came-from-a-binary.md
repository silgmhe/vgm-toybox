# 那个绿，是编译出来的吗

> 2026-11-22。一次"审查顺手跑一下测试"，最后变成两天：`ctest` 显示 54/54，而真实源码编译出来是
> **26 红**。修完之后是 54/54——**这次是真的**。
>
> 这篇记录的是**测试本身**的问题，不是引擎的问题。引擎的五个缺陷记在
> `docs/review/2026-11-22-mixer-isolation-review.md`。

## 一、第一层：绿来自二进制，不是代码

`build/plugin/vgm_core_test.exe` 的 mtime 是 **11-15**，而源码是 **11-22**。

```
vgm_core_test.exe   11-15 16:13
FmVoiceDriver.cpp   11-22 16:51
```

它**根本编译不了**——`fatal error C1083: 无法打开包括文件 "emu/EmuStructs.h"`，因为它编了
`FmVoiceDriver.cpp` 却没有 libvgm 的 include 目录。而 `ctest` 里 `core` 是第 3 项，**跑的是七天前那个
可执行文件**，所以它一直是绿的。

`vgm_mixer_test` 同样：那 28 个 `engine.*` 一直在跑旧二进制。重建之后 **26 个立刻变红**。

**这一层最贵，因为它让后面所有的判断都失去依据。** 我引用过的每一个 "54/54" 都要打折。

**判据只有一句：这个绿，是这次编译出来的吗？**

## 二、第二层：断言写的不是"应当"，是"我曾经看到过"

`every track sits on the seek target` 要求十三个 track 的位置**精确相等**（< 2 ms）。实测：

```
seek to 1.00 s -> position 1.00 s, spread 1.0000 s
```

**它从来没有、也不可能通过**：libvgm 的 `VGMPlayer::SeekToTick` 只能向前解析，而 `ParseFile` 开头
就是 `if (_playState & PLAYSTATE_END) return;`——**已经播到结尾的实例无法向前移动**。16 个实例给出
三种答案（`44100` / `10240` / `0`）。

**一条永远红的断言比没有断言更糟**：它让 26 个红一起亮，看不出哪个是真的；久了就没人看。

**改法**：断言换成**成立且应当成立**的不变量——"没有 track 跑在传输前面"——把缺口**计数并打印**，
再写一条带触发条件的 TODO。**打印出来让人看见，比断言锁死更好。**

## 三、第三层：断言找错了对象

九个 `.vgm: <chip> / Ch N note 0 exists` 的失败，真实原因不是"没有音符"，而是**那一行改名叫
`FM 1` 了**：

```cpp
// LibvgmSongInstance：把 melodicCount 当成了 FM 数
: ((channel < melodicChannels ? "FM " : "Ch ") + ...)
```

**断言按名字查轨道，产品改了名字，断言就开始报"缺音符"。** 用户实测 MIDI 完全正常——他一直在告诉我
答案，而失败信息把它指向了错误的方向。

**两条教训：**

1. **按身份查，不要按名字查。** 名字是给人看的，会改；`TrackId` 不会。
2. **失败信息要说清缺什么。** `note 0 exists` 有四种可能的原因（没这条轨道 / 有轨道没音符 /
   名字改了 / 探针窗口没覆盖），报的是同一句话。

## 四、这一轮里，测试抓到了什么、漏掉了什么

| 缺陷 | 谁先发现 |
|---|---|
| NSF 开混音器整首静音 | **测试**（重建之后） |
| N163 芯片静音无效 | **用户**（测试当时被另一个 bug 掩盖，绿得毫无意义） |
| 长 NSF 拖进度条冻结 | **用户**（测试里有这条断言，跑的是旧二进制） |
| 采样声部叫 `FM 1` | **测试**（但报成了"没有音符"，误诊很久） |

**三个真缺陷里两个是用户先发现的。** 而测试"发现"的那两个，都是在二进制度重建之后才说话。

**结论不是"测试没用"，而是"测试只在①它真的跑了 ②它的断言写对了 的时候才说话"。**

## 五、可操作的规则

1. **门禁必须重建它跑的每一个二进制。** 一个"暂时编不过"的目标要从 ctest 里删掉，而不是让它绿着。
2. **新断言写下去之后，故意把它弄红一次。** 这一轮每条新断言都这么验过：
   `targetRate` 改成 0、`pan` 关掉、`targetRate` 传 `0.0`、`exportWavetables` 忽略目标速率……
   **没被打破过的断言，不知道它在守什么。**
3. **不可能成立的断言，改成能成立的不变量 + 打印缺口 + TODO 触发条件。** 不要留着当"已知问题"——
   它会被淹在别的红里。
4. **断言按 id 查对象；按名字查的地方，失败信息必须区分"找不到"和"找到了但为空"。**
5. **一个 fixture 跑 115 条断言 × 28 个输入 = 一处系统性故障点亮一片。** 读失败时要先**按 fixture 归组**：
   这一轮 26 个红其实只有三件事。
6. **fixture 是手写/生成的，它测试的是"设计时的期望"，不是"现在的行为"。** 期望和现实冲突时，先说
   清楚哪一个是应当的，再改另一个。

## 六、和既有文档的关系

- `the-register-width-nobody-checked`：位宽凭记忆 → 这里补上了**测试层的对应规则**（断言凭记忆写，
  等于把旧行为上锁）。
- `the-view-menu-that-had-two-sources`：一份数据两个写者 → 这里是**一个通过状态两个来源**（代码 /
  旧二进制）。
- `2026-10-25-nsf-dc-offset`：直流底数让"静音"的断言不成立 → 那一轮选择**在测试里绕开**（量 `acRms`），
  这一轮证明**绕开的地方也要写清楚绕的是什么**，否则下一个人会以为是引擎没坏。

## 七、一句话

> **在任何一次"测试全绿"被引用之前，先重建。**
> 这一轮的全部误判，都是从一句没有验证过的 "54/54" 开始的。
