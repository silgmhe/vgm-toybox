# 读写文件都用编辑器能力，不写脚本

**读**和**改**是两件事，规则相同：用工具自带的能力，不要绕一圈去写脚本。**遇到工具做不到的事，再上脚本**——而不是默认先用脚本。

## 一、读文件

用 `read_file`，不要用 `python -c "open(...).read()"` 或 `Get-Content`。

### 为什么

- **行号是工具给的**：`read_file` 每行带行号，引用代码时有据可依；脚本输出要自己拼 `%4d|` 的格式，拼错了就是另一份数据。
- **编码是工具的事**：脚本读文件要自己指定 encoding。本项目里 `libs/libvgm` 和 `libs/nsfplay` 混着 UTF-8、Shift-JIS 注释和 BOM，选错一次就把日文注释读成乱码，**而写回去就会真的破坏文件**——2026-10-25 那次 `Ootake_PSG.c` 就是这么坏的。
- **`read_file` 顺带给出诊断**：未保存的编辑、linter 报错，读文件时一起看到。
- **`offset` / `limit` 比 `lines[a:b]` 更明确**：直接说"从第 200 行读 40 行"，脚本里是索引运算，差一位就错了。

### 例外（这时候用脚本是对的）

- **需要看原始字节**：判断编码、找 BOM、确认换行符是 CRLF 还是 LF。
- **二进制文件**：验证产物里是否含某个字符串、比对构建输出。
- **工具读不出正确内容**：文件不是文本、或编码工具不支持——**先试 `read_file`，坏了再换**。

### 跨文件查找

用 `search_content`（ripgrep），不要用 `Get-ChildItem | Select-String` 或 python 遍历。

需要**语义**而不是文本匹配时（找定义、找引用、看符号结构），用 MCP 索引工具，见第三节。

## 二、改文件

改一个已有文件时，用精确文本替换、局部重写，不要写一段 Python 或 PowerShell 去 `replace` 文件内容。

### 为什么

- **匹配是猜的**：脚本里的 `old` 字符串是我根据读到的一行手抄的，tab 数量、行尾、空格差一个就 `assert` 失败；`replace_in_file` 拿的是文件里的真实字节。
- **失败会留下一半**：脚本常写成"多个替换依次执行、最后统一写回"，中途断言失败就整份不写——或者更糟，检查在写回之前但改动的顺序有依赖，写回的是半成品。原生编辑一次一处，失败即无改动。
- **整份写回会动到没读过的部分**：`write` 一个文件等于重声明它的全部内容，包括我这一轮没读过的段落，以及换行符（CRLF/LF）。
- **临时脚本要清理**：`build/patch_*.py` 这类文件跑完就没用了，留在树里是噪声，忘了删还会被后续 `git add -A` 带进提交。

### 怎么做

- 改已有文件：先 `read_file` 取真实内容，再用 `replace_in_file` 做局部替换。匹配失败就重新读那一段，不靠猜。
- 新建文件、或确实要整份重写：`write_to_file`。
- 大段新增（新函数、新章节）：`replace_in_file` 也够用，把锚点选在唯一的一行上。

### 例外

- **仓库里的生成脚本**（`plugin/Tests/assets/make_*.ps1`）：它们是产物的一部分，负责从零生成二进制资源，不是临时的改文件工具。
- **确实需要程序化改写**：跨几十个文件的正则替换、或按规则生成的表格。做之前说明为什么原生编辑不合适，一次做完，且不要留在 `build/` 下。

## 三、优先用索引工具，而不是搜索

环境里装了 **serena** 和 **codegraph** 的 MCP 时，涉及"这个符号在哪、谁在用、它的结构是什么"的问题，先用它们，不要拿文本搜索硬找。（下表是这两个工具惯用的能力名，实际调用时以当时暴露的工具为准。）

| 要回答的问题 | 工具 | 不要用 |
|---|---|---|
| 这个函数定义在哪 | serena `find_symbol` / `find_definition` | `grep "void Foo"`——同名重载、注释、字符串都会命中 |
| 谁调用了它 | serena `find_referencing_symbols` | `grep "Foo("`——漏掉间接调用，命中文档 |
| 这个文件有哪些符号 | serena `get_symbols_overview` | 从头读到尾 |
| 这段代码的调用链 | codegraph | 手工追 header |
| 这个模块怎么组织 | codegraph 的模块视图 | 逐个目录 `ls` |

**为什么值得多一步**：

- **文本搜索不认识作用域**。`UINT32` 那次，全仓 7242 处命中里绝大多数是 libvgm 自己的类型，真正要改的是 21 处带命名空间限定的——**索引工具能区分，grep 不能**。
- **名字是会重名的**。`paint`、`read`、`load` 这种词在整个仓库里有几十个定义，`grep` 出来的第一个通常不是要的那个。
- **跨文件的结构问题（谁依赖谁、这个改动会影响什么）只有索引知道**。

**什么时候仍然用 `search_content`**：找字符串字面量（`"mixer.hint"`）、找配置文件里的键、找注释里的某个词、统计某个模式的分布。**索引工具不索引这些。**

## 一句话

**默认用工具，遇到工具的边界再上脚本——并且说明为什么要越过这条线。** 反过来（默认写脚本，工具当备选）会同时得到三样东西：慢、易错、以及一堆要清理的临时文件。
