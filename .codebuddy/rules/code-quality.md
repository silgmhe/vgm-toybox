# 代码要写给人读

一份代码的寿命内，被读的次数远多于被写的次数；读它的人可能是三个月后的你。以下要求按重要性排序，越靠前越不能妥协。

## 1. 先让人看懂，再让机器跑

- **名字说明意图，不说明实现**：`rowHeight` 而不是 `k48`；`kPulseRegisterStride` 而不是 `i * 4`。
- **一处一个概念**：一个函数只做一件事；一次布局、一次绘制、一次计算，各归各的函数。
- **不要用注释弥补糟糕的命名**。注释解释**为什么**，命名承担**是什么**。

## 2. 注释写"为什么"，并且只写一次

- 写：取舍的理由、不符合直觉的行为、硬件/协议的限制、曾经踩过的坑。
- 不写：`// increment i`、复述代码、与实现同义的废话。
- **一个坑只解释一次**。重复的解释会在两处逐渐不一致。

## 3. 高内聚、低耦合

- 领域逻辑（算术、协议、状态机）不放在 UI 里；UI 里不出现芯片名字。
- 跨模块只传**值**：结构体、参数、回调。不要为了省一个参数把整个 panel 传进去。
- 谁拥有状态，谁负责它；绘制函数不修改状态，计算函数不画东西。

## 4. 可扩展：加东西应该只改一处

新增一种格式、一个视图、一个设置项，应当是**加一行或加一个文件**，而不是在四处改代码并祈祷它们的顺序一致。

- 表驱动优于 `if/else` 链和裸 `static_cast`。
- 已有先例：`contentViews()`（视图注册表）、`BackendRegistry`（后端注册表）、`KeyboardLayout`（音名与音域）、`WaveShape`（波形合成）。新代码沿用这个形状。

## 5. 不留技术债，有就当场还

- 发现"先这样，以后再说"的写法，要么现在改掉，要么在同一个提交里写下 TODO 和触发条件。
- 已知缺陷不要用补丁掩盖：绘制循环里的 `if (x > max) continue;` 会藏住上游算错的值。**把不变量放回它该在的地方**，并给它一个测试。
- 删掉不再被引用的代码、文案键、常量；"以后可能有用"的东西由版本库保管。

## 6. 可测试：纯逻辑必须能被调用

- 算术、映射、合成、布局一律写成**可以传参调用的函数**，不依赖窗口、不依赖单例。
- 只有能被调用，才可能被断言；只有能被断言，才不会靠截图发现错误。
- 反例（本项目真实发生过）：音域跨度、行布局、波形合成曾埋在 private 嵌套类里，只能"画出来看"，一晚因此返工 7 次。

## 7. 数据与呈现分离，颜色一律走主题

- 面板只画"收到的数据"，不推断来源芯片。
- **任何颜色都必须来自 `theme::`**。组件里出现 `juce::Colour (0x…)`、`juce::Colours::red`、`colours::black.withAlpha (…)` 这类就地取值，一律视为缺陷，不因为"只有这一处"而通融。
- 允许的例外只有三类，且都要在代码里**具名并注明理由**：
  1. `juce::Colours::transparentBlack` —— 表示"没有颜色"，不携带任何设计决定；
  2. **素材自身的墨色** —— 例如托盘 SVG 以黑色绘制，`replaceColour` 里的黑色是源文件的墨色，不是我们选的颜色；
  3. **操作系统契约** —— 例如 Windows 模板图标必须是白色，由外壳按任务栏明暗反转；换成主题色会让它在深色任务栏上消失。
- 不在构造函数里 `setColour`（主题切换时不会重设）。全局控件交给 `ToyboxLookAndFeel`，组件私有颜色在 `paint()` 里现取现用。

### 要让一个颜色"可管理"，四步
1. 在 `Theme.h` 的 `Palette` 里加字段，并在**注释里写清它和别的角色的关系**（例如"琴床永远比卡片深"）；
2. 在 `Theme.cpp` 的 `kLight` 和 `kDark` 两份初始化列表里各加一行；
3. 在 `Theme.h` 加 `inline juce::Colour xxx (void) { return palette().xxx; }`；
4. 全局语义的（滚动条、焦点框、禁用态）在 `ToyboxLookAndFeel` 里 `setColour` 一次；组件私有的在 `paint()` 里取。

### 两个真实事故（都是这条规则的反例）
- **初始化顺序错位**：往 `Palette` 结构体末尾加字段，却把初始化行插在 `keyBed` 之前——从那行起**所有**颜色都错位，症状表现为"键盘颜色不对"，错误却发生在三层之外的初始化列表。加字段时，初始化行必须与结构体声明**同位置**，或者干脆在后面追加并注明。
- **两处各自定义**：Mixer 的滚动条用了配色方案的蓝，Keyboard 自己写了一个灰，同一个手势两种颜色。同一个语义**只能有一个来源**，否则第三个组件会给出第三种答案。

### 提交前自检
```powershell
# 除 Theme.cpp 外不应有字面量颜色（transparentBlack 除外）
Select-String -Path plugin/Source/**/*.cpp -Pattern "Colour \(0x|Colours::(?!transparentBlack)"
```

## 7.5 测试策略：核心用断言，界面用眼睛

- **核心逻辑**（解析、时序、映射、合成、布局算术）必须有单元测试，覆盖边界与历史缺陷。
- **界面**不做像素级断言。像素断言会把"外观"钉死，之后每次调整间距、配色、字号都要重写测试，改 UI 的成本会高过它挡住的风险。
- 界面的验证方式是 `vgm_app_test` 的 harness：驱动真实编辑器、`shot` 出图，**真的看那张图**（见 `ui-visual-check.md`）。
- 两者的分工：单元测试保证"算得对"，截图保证"看得见"。任何一边缺失，另一边的盲区就会变成 bug——本项目两边都发生过：算术错到 meter 高 0（截图发现），越界到 C9（单测发现）。

## 8. 提交即最小可读单元

- 一个提交解释一件事：改了什么、为什么、放弃过什么。
- 提交说明写"为什么"，代码注释写"为什么"，两者都不复述 diff。
- 不把格式化、重命名和功能改动混在一起。

## 9. 重构不得夹带行为变更

- 标题写着 refactor / split / rename 的提交，**不允许同时改变运行时行为**。看到了顺手要改的东西，要么单独开一个提交，要么把标题写成 fix/feat。
- 如果行为变更无法拆分（例如换实现必然带来数值差异），必须在提交说明里**单列一段**："这个提交改变了什么行为、影响哪些输入、用什么证据验证"，并补上对应的用例。
- 反例（本项目真实事故）：`cbaf588` 标题是「refactor: split the VGM MIDI decoders into one class per chip family」，同一提交把单通道静音掩码从「两半分别计算」改成「两半同掩码」。理由写在注释里（OPL4 需要），方向也对，但它夹在重构里，评审时读标题的人不会去看掩码；结果是 YM2610 的 SSG 漏进了 FM 1-3 轨道，直到一位听众报「FM 上有 DPCM 串音」才被发现。

## 10. 位域、掩码、通道映射类改动必须跨型号验证

- 这类代码的共同点：**语义由"另一个东西的编号系统"决定**，本地看完全正确，换个芯片/设备就错。写完必须问：还有谁的编号规则不一样？
- 至少覆盖两类对象：**联动设备与主设备通道数相同**（OPL4：联动的 OPL3 通道 n 就是主设备的 n）和**不同**（YM2610：主设备 13 通道，联动的 SSG 只有 3 通道）。
- 只在一种芯片上验证过的掩码改动，视为未验证。现有用例的容差也要看一眼：`[3]` 的"等增益求和 < 0.5 dB"就放过了这次 0.16% 的漏音——**容差比缺陷大，等于没有断言**。

## 11. 「读当前状态」之前，先问所有权在谁手里

`std::move` 之后源对象**仍然合法可读**，只是不再表示任何东西——moved-from 是「有效且未指定」，编译器不会报，测试也不会绿变红。

于是会出现：**界面有 13 行波形，导出说「没有可导出的波形」，而 `46/46` 全绿。**

**按顺序问三个问题：**

1. 我读的这个成员，上一次赋值是谁？
2. 那次赋值之后它还是权威的吗——有没有被 move 走、有没有被 `clear()`？
3. 界面上显示这份数据的功能，读的是同一个对象吗？

**同一个页面上的两个功能，只要读的不是同一个对象，就迟早会分叉。** 让它们读同一份（例如 panel 的 `drawnSnapshot()`），比让它们各自「保持同步」可靠。

**相关的一半**：一个字段决定「有没有」之前，先 grep「谁填它」。

```powershell
Select-String -Path plugin\Source -Pattern '\.wave =|\.wave\.push'
```

一个后端填了，不代表其余都填；空值在那里是**常态**，不是缺陷。曾经因为只看这一个字段，导出功能对绝大多数芯片**从未**有效过。

案例：`docs/memo/2026-10-28-the-shell-a-move-leaves-behind.md`

## 12. 一个寄存器的宽度，去实现里读，不要凭记忆截位

`$4013` 在真机 2A03 上只有低四位有效。但这一支援的播放核心和 FamiStudio 用的 NotSoFatso 都按八位算：

```cpp
// libs/nsfplay/xgm/devices/Sound/nes_dmc.cpp:622
dlength = (len_reg << 4) + 1;      // len_reg = val & 0xff

// reference/FamiStudio/ThirdParty/NotSoFatso/NSF_Core.cpp:321
mWave_TND.nDMCLength = (v << 4) + 1;
```

`& 0x0F` 于是把 689 字节的军鼓切成 177——**那正好是底鼓的长度**。

**这就是它四轮没被识破的原因：177 不是错数，是另一个声音的正确长度。** 用户说「军鼓不对」，波形"像但不是"，而每个环节单独看都自洽。

**规则：**

1. **写掩码之前，先在"被模拟的那份代码"里 grep 这个寄存器**，看它取几位。规格记忆和实现冲突时，跟实现。
2. **一个数对不上，先问"它是不是别人的"**。自洽的错值比明显的错值更难发现。
3. **固定缓冲的大小从取值范围推**（`241`、`4081`），不从观测值推。把某首歌算出的 `193` 写进 `std::array`，就是把越界写进类型定义。
4. **断言里只写"应当"，观测值先打印出来看**。曾经把 `length == 17` 和"upper bits are dropped"写进断言，等于给错误上了锁——`ctest` 一直是绿的，而功能是坏的。

案例：`docs/memo/2026-10-30-the-register-width-nobody-checked.md`

## 检查清单（提交前自问）

- [ ] 三个月后的我，能否只看函数名就说出它做什么？
- [ ] 这段算术/映射，有没有一个测试能直接调用它？
- [ ] 新增同类东西时，是否只需改一处？
- [ ] 是否留下了"先这样"的补丁而不自知？
- [ ] 注释里是否在重复代码已经说清楚的事？
- [ ] 有没有第二份重复的表、常量或颜色？
- [ ] 新加的颜色是否走了四步（Palette 字段 → 两份初始化 → 访问器 → 使用处），初始化行与字段**同位置**？
- [ ] 提交标题是 refactor，diff 里是否混进了行为变更？混进了就拆开。
- [ ] 动了掩码/位域/通道映射，是否在**通道数不同的**另一颗芯片上也验证过？
- [ ] 这条断言的容差，是否小于它本该抓住的缺陷？
- [ ] 我读的这个成员，是否可能已经被 move 走或 clear 掉？
- [ ] 界面能看见的数据，我这一处读的是同一个对象吗？
- [ ] 我截的位宽，是否在**被模拟的那份代码**里确认过，而不是凭规格记忆？
- [ ] 固定缓冲的大小，是从取值范围推的，还是从某次观测值推的？
- [ ] 这条断言写的是"应当"，还是我观测到的现状？
